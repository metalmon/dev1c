# iroh-ssh: что это и нужен ли он нам

Вопрос владельца: использовать крейт `iroh-ssh` или говорить по iroh своим протоколом.

## 1. Крейт существует, но это не от n0

- **crates.io**: https://crates.io/crates/iroh-ssh — версия 0.2.12, лицензия MIT, описание «ssh without ip», ключевое слово `networking`. Всего загрузок 6 834, за последний период 261. Создан 25.06.2025, последнее обновление версии — 05.06.2026.
- **Репозиторий**: https://github.com/rustonbsd/iroh-ssh — автор `rustonbsd`, третья сторона, не организация n0 (авторы самого iroh). 333 звезды, 25 форков, 12 открытых issues, последний push 17.10.2026 (две недели назад на момент написания) — живой проект. Лицензия в репозитории указана как MIT (в одном из описаний встретилась формулировка «MIT/Apache 2.0», но официальный `license` в GitHub API — только MIT; это несовпадение я не разрешил, не нашёл второго файла лицензии).
- Есть минимум два смежных проекта с похожим именем, не путать: `irosh` (github.com/shedrackgodstime/irosh, «SSH sessions over Iroh peer-to-peer transport» — отдельная реализация) и `iroh-ssh-android` (github.com/futpib/iroh-ssh-android, Android-клиент поверх того же iroh-ssh). Их отдельно не исследовал — вне вопроса.

## 2. Что он делает по сути

Это **не своя реализация SSH и не чистый перенос потока** — это прокладка-мост с настоящим SSH на обоих концах:

```
SSH-клиент → ProxyCommand → QUIC-туннель (iroh, p2p) → iroh-ssh сервер → локальный sshd (порт 22)
```

Источник: README репозитория (https://github.com/rustonbsd/iroh-ssh).

- На машине **обязателен установленный и работающий sshd** (порт 22 по умолчанию, настраивается `--ssh-port`). `iroh-ssh server` сам SSH-сервером не является — он только принимает QUIC-соединение по iroh и перенаправляет байты на локальный sshd.
- На стороне клиента `iroh-ssh proxy` играет роль `ProxyCommand` для обычного `ssh` — то есть реальный OpenSSH-клиент как обычно делает handshake, аутентификацию по ключу/паролю/сертификату и шифрует сессию SSH-протоколом, а iroh у него под капотом просто вместо TCP-сокета.
- Итог: `authorized_keys`, SSH-ключи, сертификаты, пароли — всё это обычный SSH, ничего не упрощено и не обойдено. iroh-ssh добавляет только способ физически дотянуться до порта 22 без публичного IP.

## 3. Что он даёт сверх голого iroh

Из README и чеклиста статуса проекта:

- Готово: интерактивный сервер и сервер с `--persist` (постоянный ключ/идентичность вместо эфемерной), клиентское подключение по Endpoint ID, пароль как метод аутентификации (транзитом — это аутентификация sshd, не iroh-ssh), служебный режим (service/daemon) для Linux и Windows.
- Не готово: service-режим для macOS отмечен как нереализованный.
- **Не нашёл** отдельных подкоманд для проброса произвольных портов (кроме сквозного пробрасывания именно SSH-порта), выполнения одиночных команд без интерактивной сессии, или передачи файлов (scp/sftp) как собственной функции — всё это, если нужно, идёт через обычный SSH/scp уже после того, как ProxyCommand поднял канал, то есть это свойства SSH, а не iroh-ssh.

## 4. Зрелость и предупреждения

- Явных пометок «experimental» или предупреждений о безопасности в README **не нашёл**.
- Модель безопасности описана прямо: секретность держится на Endpoint ID — у кого есть ID, тот может достучаться до порта 22; дальше аутентификация — обычная SSH. Это равносильно «порт открыт тому, кто знает адрес», только адрес — криптографический идентификатор узла, а не IP.
- Windows отдельно заявлен как поддерживаемая платформа, включая режим службы (`iroh-ssh service install`). Известных проблем именно на Windows **не нашёл** — ни в README, ни в быстром обзоре issues (12 открытых issues не разбирал по содержимому, это вне объёма короткого исследования).

## 5. Альтернативы в экосистеме (туннель/проброс порта поверх iroh, без SSH)

Три живых кандидата, оценка по GitHub на 01.11.2026:

| Крейт | Автор | Что делает | Звёзды / форки / open issues | Последний push | Лицензия |
|---|---|---|---|---|---|
| [pai-sho](https://github.com/cablehead/pai-sho) | cablehead | Проброс TCP-портов между своими машинами поверх iroh, один долгоживущий демон на несколько портов, без аккаунта и без открытого входящего порта | 94 / 4 / 1 | 28.10.2026 | лицензия не указана в репозитории |
| [forwiroh](https://github.com/trufae/forwiroh) | trufae | Port forwarding и VPN поверх iroh, пара QR-кодом с телефона до домашней машины | 14 / 2 / 0 | 01.11.2026 | MIT |
| [iroh-tunnel](https://github.com/naicoi92/iroh-tunnel) | naicoi92 | P2P-туннель TCP/UDP поверх iroh | 4 / 1 / 11 | 01.11.2026 | Apache-2.0 |

Все три — чистый перенос потока/дейтаграмм без встроенного SSH: ни одна не тащит sshd и не разбирает SSH-протокол. Самый зрелый по звёздам и соотношению открытых issues к форкам — pai-sho; iroh-tunnel при той же свежести коммитов несёт заметно больше нерешённых issues относительно размера проекта.

Также существует `portmapper` (crates.io) — но это библиотека для поддержания проброса локального порта через UPnP/PCP/NAT-PMP, используется самим iroh внутри, к p2p-туннелированию через iroh не имеет отношения как «альтернатива iroh-ssh».

## 6. Главный вопрос: что SSH-поверх-iroh даёт сверх самого iroh

У iroh уже есть: аутентификация по ключу узла (Ed25519, TLS по raw public key — ключ и есть адрес), сквозное шифрование (QUIC + TLS 1.3) и мультиплексирование потоков в одном QUIC-соединении (https://docs.iroh.computer/what-is-iroh, https://docs.iroh.computer/protocols/using-quic).

На этом фоне `iroh-ssh` (и любой «SSH поверх iroh») добавляет:

1. **Второй слой аутентификации пользователя внутри узла** — SSH разбирает, *какому пользователю системы* разрешён вход (ключ в `authorized_keys`, сертификат, пароль). У голого iroh аутентификация только на уровне узла («это тот самый endpoint»), пользователей и прав внутри неё нет — это надо строить своим протоколом заново, если не берётся SSH.
2. **Готовую интерактивную оболочку и экосистему вокруг неё** — pty, завершение сессии по сигналу, `scp`/`sftp`, агент-форвардинг, X11-форвардинг, `~/.ssh/config`, привычные флаги — весь инструментарий OpenSSH, который иначе пришлось бы реализовывать самостоятельно поверх потока iroh.
3. **Совместимость с существующей инфраструктурой на машине** — она просто работает поверх уже настроенного `sshd`, с теми же `authorized_keys`, теми же политиками, тем же логированием входов, что уже есть на сервере.

Если это не нужно — а именно: не нужен отдельный слой «пользователь системы + его права», не нужен готовый интерактивный шелл/scp/sftp клиент-экосистема, не нужна совместимость с существующим `sshd` — то SSH поверх iroh не даёт ничего, что не даёт уже сам iroh плюс свой минимальный протокол команд. Транспортная часть (шифрование, аутентификация узла, мультиплексирование) у SSH и у iroh избыточно пересекается: SSH-поверх-iroh шифрует и аутентифицирует дважды — один раз на уровне iroh (узел), второй раз на уровне SSH (сессия/пользователь).

**Вывод для проекта**: раз туннель сегодня нужен не для входа произвольного системного пользователя с правами по `authorized_keys`, а для доставки собственного протокола коннектора до среды (как сейчас делает `russh`-клиент до среды с известной стороной), встраивание реального SSH поверх iroh добавляет главным образом совместимость с привычками (готовый клиент, готовый `sshd`), а не новую возможность, которой не было бы у iroh. Для целевого сценария — пробросить поток до уже доверенного узла по известному ключу — говорить по iroh своим протоколом (как делают `pai-sho`/`iroh-tunnel`/`forwiroh`, просто проброс потока) выглядит ближе к задаче, чем тащить `iroh-ssh` и второй слой SSH-аутентификации, который не используется.

## Решение владельца 1.11: свой протокол поверх iroh

`iroh-ssh` отвергнут, и решающим оказался не довод про две системы аутентификации (он верен, но мягок), а факт из этого исследования: **крейт не реализует SSH, он доставляет байты до настоящего `sshd` на порту 22**. Значит на машине человека должен быть установлен и настроен OpenSSH-сервер с `authorized_keys` и правами — работа, от которой мы как раз и обещали избавить бухгалтера. Это прямое столкновение с мерой успеха продукта.

Чего лишаемся: интерактивной оболочки, `scp`/`sftp`, проброса агента, `~/.ssh/config`. Из этого нам не нужно ничего — оболочку на чужой машине мы не даём принципиально, файлы едут своей синхронизацией, а соединение и так проверено по ключу узла.

Спецификация своего протокола — `docs/superpowers/specs/2026-11-01-protocol-design.md`.

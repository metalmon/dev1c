# `1c-connect`: переключатель MCP и локальный режим

Дата: 2026-10-19. Ветка `main`. Поверх спек окна
(`2026-10-16-gpui-connect-design.md`, раздел «Режим работы»), демо-стенда
(`2026-10-19-demo-stand-design.md`) и user flow (`2026-10-18-user-flow.md`,
пп. 1 и 2 «куда гребём не туда»).

## Зачем

У разработчика один агент в Zed и несколько проектов, у каждого своя база.
Сегодня, чтобы агент смотрел на другую базу, надо править настройки Zed или
держать поднятыми отдельные MCP под каждый проект. `1c-connect` становится
органом управления этой обвязкой: **один переключатель включает MCP для
текущего проекта**, база и каталог исходников задаются в его же «Параметрах»,
смена проекта — смена полей и «Сохранить». Настройки Zed не трогаются
никогда: там навсегда `nc localhost 777N` и `778N`.

То же окно, тот же переключатель и та же логика работают в двух местах:

- **туннельный режим** (Windows рядом с реальной базой): MCP включены =
  туннель в среду поднят и мосты принимают подключения;
- **локальный режим** (внутри образа, стенд с учебной платформой или любая
  платформа на той же машине): MCP включены = `1c-connect` сам слушает
  `777N`/`778N` на loopback и на каждое подключение Zed запускает
  `mcp-1c`/`vrunner-mcp` на текущую базу. Туннеля и SSH нет.

Ограничение учебной платформы «один сеанс Предприятия на базу» — частный
случай, не повод для особой механики: если вызов агента упёрся в лимит
(человек держит 1С открытой), ошибка платформы идёт строкой в журнал и
ответом агенту как есть. С обычной платформой всё работает так же, просто
без этой ошибки.

## Цели

- Переключатель «MCP» в карточке состояния с одним смыслом в обоих режимах.
  Выключено — порты закрыты, Zed показывает серверы упавшими и сам
  переподключается, когда включат (решение заказчика 2026-10-19).
- Смена проекта/базы через «Параметры» + «Сохранить»: следующее подключение
  Zed получает MCP уже на новую базу.
- Локальный режим как полноценный: мосты, установка расширения, проверка,
  журнал — без SSH, с линуксовыми путями и учебным конфигуратором.
- Стенд перестаёт держать свои socat-мосты: `777N`/`778N` принадлежат
  `1c-connect`.

## Не-цели

- Списки баз, профили проектов, «последние базы» — нет. Одна активная база,
  одно поле.
- Пауза агента, автоматическое закрытие 1С, арбитраж «агент или человек» —
  нет. Переключатель включает и выключает MCP, остальное — ошибки платформы
  в журнале.
- Кнопка «Открыть Zed» — не здесь (user flow п. 2 решается отдельно; внутри
  образа Zed и так главное окно).
- Серверные базы (`сервер\база`) — поле принимает, проверка подключения —
  как сейчас; отдельной работы здесь нет.
- Ничего из перечисленного не зависит от ОС: локальный режим
  проектируется **сразу под Linux и под Windows** (решение заказчика
  2026-10-19). На Windows он тоже сценарий: человек поставил образ рядом с
  собственной базой на той же машине — туннель ему не нужен, MCP слушают
  loopback, `1cv8.exe` и база местные. Разница ОС живёт в трёх местах:
  поиск платформы, уборка дочерних процессов и способ поднять HTTP-сервис
  базы (ключ `/HTTPPort` против своего Apache, см. ниже).

## Анти-цели

- Правка `settings.json` Zed из `1c-connect`.
- Второй набор команд и экранов для локального режима. Разница режимов —
  в одном модуле «как доставить stdio MCP на порт», остальное общее.
- Опрос по таймеру там, где есть событие.

## Что есть сейчас (проверено по коду и стенду)

| Часть | Как работает | Что мешает |

| `bridge::mcp_command(cfg, kit)` | `mcp-1c --base <base_url> --user --password`; `vrunner_command(cfg, tools)` — `oscript … mcp.os` с `cwd = project`; `connection_args(cfg)` подставляет `ibconnection`/`db-user`/`db-pwd` | база берётся из `cfg` в момент запуска процесса — смена базы = перезапуск мостов |
| `cfg::Host.mode` | читается, проверяется (`tunnel`/`local`), сохраняется; поведения нет | — |
| Стенд (`config/1c/stand.sh`) | пишет `1c-connect.toml` с `mode = "local"`, `base_path`, `base_url = http://127.0.0.1:808N/base/hs/mcp-1c`, `project`, `db_user`; публикует базу (`publish`: `default.vrd` + свой Apache на `808N`); слушает `777N`/`778N` через `socat`, запуская `1c-stand mcp N` / `vrunner N`; запускает `1c-connect --tray` при входе | два хозяина у портов; база зашита в скрипт |
| `ops_host::Extension`, `verify::run` | `mcp_exe` различает ОС; `find_1cv8` ищет Windows-платформу; факты проверки — про SSH, `1cv8.exe`, Windows-инструменты | в образе половина фактов не имеет смысла |
| Карточка состояния | одна строка: кружок, заголовок по `session::State`, «Прервать», переключатель туннеля | заголовки говорят о туннеле |

## Решения

### Переключатель = «MCP включены»

Состояние окна — `session::State`, как сейчас, но смысл: `Up` — MCP
принимают подключения, `Off` — порты закрыты. Заголовки карточки:
«MCP выключены» / «Включаю…» / «MCP включены» / «Переподключаю» /
«MCP выключены» (после сбоя — причина строкой в журнал, как сейчас).
Подсказка трея и пункт «Подключить/Отключить» меняют слова на
«Включить MCP / Выключить MCP». Автоподключение при запуске остаётся —
«включать MCP при запуске».

### Два транспорта под одним сеансом

`session::start(cfg, kit, sink, on_state)` выбирает по `cfg.host.mode`:

- `tunnel` — как сейчас (SSH, remote forward, переподключение);
- `local` — `tokio::net::TcpListener` на `127.0.0.1:777N` и `127.0.0.1:778N`;
  на каждое принятое соединение — тот же `bridge::pipe_jsonrpc` с теми же
  `mcp_command`/`vrunner_command`. Состояния: `Connecting` на миг,
  `Up` когда оба слушателя подняты, `Failed(why)` если порт занят («порт
  7771 занят: остановите socat стенда или другой 1c-connect»). `Retrying`
  в локальном режиме не бывает. `779N` (веб) в локальном режиме не
  поднимается: пункт «Открыть веб-клиент» убран (см. ниже), а внутри
  образа база и так на `localhost`.

**Половинчатого состояния нет.** Если второй слушатель не встал, первый
закрывается и сеанс идёт в `Failed` — как уже устроено в туннельном
транспорте.

### Один владелец рабочего места

Порты `777N`/`778N` рабочего места занимает **ровно один коннектор**, и
выигрывает тот, кто успел первым (решение заказчика 2026-10-20). Разобрано
по коду и конфигурации sshd образа:

- локальный коннектор слушает `127.0.0.1:777N`; удалённый, подключаясь
  туннелем как то же рабочее место, просит у sshd образа проброс на тот же
  адрес (`GatewayPorts clientspecified`, `PermitListen localhost:777N`).
  Тихого перехвата не бывает: занятый адрес sshd не отдаёт;
- **локальный первым** — удалённый получает отказ проброса. Сегодня окно
  скажет «другой туннель», что неправда, а в контейнере не скажет ничего.
  Надо: текст называет соперника («рабочее место занято коннектором внутри
  среды»), и строка об отказе пишется в журнал на стороне контейнера;
- **удалённый первым** — локальный получает занятый порт при включении MCP
  и должен сказать то же самое своими словами («рабочее место занято
  коннектором с машины разработчика»);
- **повторов при столкновении нет.** Туннель сегодня переповторяет проброс
  после обрыва; из-за этого уснувший и проснувшийся ноутбук отберёт порт у
  локального коннектора, и агент в контейнере молча переедет на чужую базу.
  Столкновение на порту — терминальный отказ, а не повод для повтора;
  повторы остаются только для обрыва связи;
- зависший проброс спящей машины sshd держит около трёх минут
  (`ClientAliveInterval 30` × `CountMax 6`), после чего порт освобождается
  сам; это и есть ответ на «почему порт занят, а на той стороне никого».

**Безголового владельца нет** (решение заказчика 2026-10-20, вариант 1):
порты живут, пока работает коннектор, то есть пока человек вошёл в среду и
MCP включены. Для случая без рабочего стола у коннектора есть запуск без
окна (`1c-connect serve`, тот же сеанс и те же мосты, без трея и окна) —
его зовут руками или из скрипта стенда. Стенд перестаёт поднимать свои
`socat` при старте контейнера; его смоук-тест сам запускает `serve` перед
проверкой портов.

**Остановка сеанса обязана убить всё, что родила.** Сегодня это умеет
только Windows (`job::Job` — Job Object), на Linux тот же тип — пустышка,
и в туннельном режиме это сходило с рук: процессы жили на той стороне SSH,
а обрыв сеанса закрывал каналы. В локальном режиме так нельзя:
`oscript`/`vrunner` и платформа держат файловую базу, и забытый процесс
займёт единственный сеанс — ровно то, ради чего всё затевалось. Поэтому:

- закрытие `TcpListener` **не** рвёт уже принятые соединения (в отличие от
  SSH-канала) — сеанс ведёт свой список живых мостов и закрывает их сам;
- каждый мост в локальном режиме запускается в своей группе процессов
  (`setsid`/`CommandExt::process_group(0)` на Linux, Job Object на
  Windows) и при закрытии гасится целиком (`killpg(SIGTERM)`, через 5 с
  `SIGKILL`);
- `job.rs` получает рабочую реализацию для Linux вместо заглушки.

Это не отдельная работа «потом»: без неё локальный режим не считается
сделанным (вывод проверки строителем 2026-10-19).

### Смена проекта = перезапуск сеанса

Сеанс перезапускается после сохранения параметров, если он был поднят.
Точность ради строителя: это делает не `save_host` (он только пишет toml),
а вызывающий код окна — проверка строителем 2026-10-19 поймала это
неверное утверждение. Новые мосты стартуют с новым `cfg`; закрытие
слушателей рвёт stdio-соединения Zed, Zed переподключается и получает MCP
на новую базу. В журнал — «MCP перезапущены: база <путь>».

**Кнопка «Сохранить» заблокирована, пока идёт операция.** Иначе смена базы
посреди выгрузки меняет `cfg` под работающим потоком, а вызов агента
умирает без внятного ответа (найдено ревью 2026-10-19).

### HTTP-сервис базы ведёт коннектор — на обеих ОС

`mcp-1c` ходит в базу через HTTP-сервис, значит у активной базы он должен
быть. Сегодня это самый тяжёлый шаг установки: человек идёт в Конфигуратор
публиковать базу на Apache или IIS (user flow п. 4). Решение заказчика
2026-10-19: **коннектор поднимает HTTP-сервис сам, и на Linux, и на
Windows** — шаг исчезает из пути человека целиком.

Параметр `[host] publication`:

- `"auto"` (умолчание) — сервис поднимает коннектор **своим httpd под
  пользователем, одинаково на обеих ОС**: свой конфиг, свой порт
  (`808N` по рабочему месту), свой журнал, модуль платформы
  (`wsap24.dll`/`wsap24t.dll` на Windows, `wsap24t.so` в образе). Ни
  установки веб-сервера, ни службы, ни прав администратора. На Linux это
  то, что уже делает стенд; на Windows бинари Apache (около 14 МБ) едут в
  комплекте.
- `"webserver"` — база уже опубликована кем-то (корпоративный Apache или
  IIS), `base_url` задан руками, коннектор только проверяет ответ. Это
  нынешнее поведение Windows, оно остаётся для тех, у кого публикация уже
  есть.

**Ключ `/HTTPPort` выбыл.** Спайк 2026-10-20 на этой машине: ключ принят
молча и не поднимает ничего. Проверено дважды — коммерческая 8.3.27.1786
(Бухгалтерия) и учебная 8.5.1.1150 (УНФ): база открывается полностью,
процесс не слушает ни одного порта; строки `HTTPPort` нет ни в одном из
235 модулей учебной платформы (402 МБ просмотрено), `ibsrv` там тоже нет.
Документированный аналог — автономный сервер `ibsrv` (серверный
компонент, с 8.3.23 не бета): в учебной платформе отсутствует, на машине
заказчика возможен, но требует серверной установки. Поэтому опора —
собственный httpd.

**Публикация в корень своего порта, а не в подкаталог.** У каждого
рабочего места свой порт, поэтому корень свободен: `base="/"`,
`DocumentRoot` на каталог публикации, `<Directory>` с
`SetHandler 1c-application`.

**Веб-клиент на учебной платформе не открывается, и пункт меню убран.**
Страница приходит, но её скрипты платформа отдаёт с 404 — и так же, когда
публикацию делает её собственный `webinstt.exe`, а не наш конфиг. Файлов
веб-клиента нет ни в одной из двух установок учебной платформы: ни на
Windows (604 `.js` — только ресурсы встроенного браузера толстого
клиента), ни в томе образа на Linux (ноль `.js` при наличии модулей
`wsap*t.so`). В официальном перечне ограничений учебной версии веб-клиент
не упомянут, то есть подтвердить ограничением вывод нельзя. Решение
заказчика 2026-10-20: раз подтверждения нет и работоспособность нигде не
доказана — **пункт «Открыть веб-клиент» из меню трея убран** (код и
`web_url`/`open_web` удалены). На HTTP-сервисы это не влияет: сервис
расширения отвечает, агент работает.

**Комплект.** Переносимый Apache (bin + modules + `conf/mime.types`,
172 файла, 14 МБ) едет строкой `httpd/` в Windows-комплекте `1c-connect`
рядом с `vrunner/` и `git/`; `pack.sh` тянет архив Apache Lounge с
закреплённой суммой SHA-256, как уже делает для MinGit и nssm, и
выбрасывает лишнее (docs, htdocs, cgi-bin). Локальная копия для отладки
уже лежит в `dist/ci/1c-connect/httpd`. Минимальный набор модулей,
проверенный спайком: `authz_core`, `authz_host`, `alias`, `mime`, `dir`
плюс модуль платформы; `mime` требует `conf/mime.types`, без него httpd
не стартует.

**Атрибуты публикации обязательны, иначе у агента случайные отказы.**
Проверено спайком: без них HTTP-сервис держит сеанс между вызовами, а
учебная лицензия даёт один сеанс «Предприятия» на базу — второй вызов
подряд возвращает HTTP 500 с телом платформы про предельное количество
подключений. С ними вызовы идут. В `default.vrd` обязательно:

```xml
<httpServices publishByDefault="true" publishExtensionsByDefault="true">
	<service name="MCPService" rootUrl="mcp-1c" enable="true"
			reuseSessions="dontuse" sessionMaxAge="1" poolSize="1" poolTimeout="1"/>
</httpServices>
```

`publishExtensionsByDefault="true"` — сервис mcp-1c живёт в расширении;
`reuseSessions="dontuse"` и пул из одного соединения с минимальным
временем жизни — чтобы сервис занимал базу только на время запроса. Эти
атрибуты принимает только элемент `service`, на контейнере платформа
отвергает весь файл.

Проверено на публикации, сделанной человеком из Конфигуратора
(спайк 2026-10-20): галочка «публиковать сервисы расширений» встаёт в
раздел веб-сервисов, в разделе HTTP-сервисов перечисляются только штатные
сервисы конфигурации, и наш адрес отвечает 404 даже с паролем; сами
сервисы получают `reuseSessions="autouse"` и пул из десяти соединений.
То есть публикация руками не годится не из-за лени человека, а по
существу — ещё один довод за то, что дескриптор пишет коннектор.

`base_url` в режиме `"auto"` **вычисляется, а не хранится**:
`http://localhost:808N/hs/mcp-1c`. Писать его в toml нельзя — значение
затрёт `carried_base_url` при следующем «Сохранить», а `publication()`
вернёт корень и адрес станет бессмысленным (найдено ревью 2026-10-19).

Операция `host.publication` (строка на вкладке «Проект», рядом с
расширением) показывает состояние сервиса и поднимает его. Вызывается при
включении MCP, при «Сохранить» с изменённой базой (до перезапуска сеанса)
и из «Установить». Решение автора: на Linux механика копируется из стенда
в Rust (`ops_host`), а не зовётся скриптом — стенд после этого свою
публикацию не трогает.

**Сеансы и загрузка конфигурации.** Своего сеанса «Предприятия» коннектор
не держит: его берёт и отпускает httpd на время запроса (см. атрибуты
выше). Поэтому особого танца с опусканием сеанса не нужно — `cf_load` и
`infobase_update` идут как сегодня, а отказ платформы, если человек в этот
момент сидит в 1С, уходит агенту текстом и строкой в журнал.

**Проверка.** Факт «веб-сервер» в режиме `"auto"` заменяется на «httpd
рабочего места отвечает»; факт «публикация и расширение»
(`base_url/version`) остаётся в обоих режимах — он и есть доказательство,
что агент базу видит.

**Что подтвердил спайк 2026-10-20** (Windows, учебная 8.5.1.1150, база УНФ
из `unf-ready.dt`, переносимый Apache из `C:\cargo-target\httpd-spike`,
расширение поставлено двумя командами конфигуратора, как в образе):
публикация своим httpd поднимается без установки и без прав
администратора; настоящий `mcp-1c` 1.22.3 отдал девять инструментов,
вернул сведения о конфигурации и выполнил запрос к данным. Отдельно
замечено: `get_metadata_tree` на УНФ не уложился в полторы минуты —
учитывать в таймаутах.

### Гигиена сеансов: ничего не держать дольше вызова

Требование заказчика 2026-10-20. Забытый сеанс «Предприятия» держит базу и
лицензию, и человек в неё не войдёт — в 1С это известная боль. Сегодняшний
спайк дал живой пример: оборванный вызов моста оставил два тонких клиента,
которые продолжали держать базу, пока я их не снял руками. Правила:

1. **Пул запрещён.** Атрибуты публикации (выше) заставляют HTTP-сервис
   брать базу только на время запроса. Без них сервис держит сеанс между
   вызовами агента — это и есть первая причина потерянной лицензии.
2. **Всё, что коннектор запустил, живёт в его группе.** httpd, `mcp-1c`,
   `oscript`/vrunner и порождённые ими процессы платформы — в Job Object
   на Windows и в группе процессов на Linux; выключение MCP и выход гасят
   дерево целиком с коротким сроком на мягкое завершение.
3. **Уборщик при включении MCP.** Перед тем как занять порты, коннектор
   снимает **свои** хвосты прошлого запуска — по собственному списку
   (файл с идентификаторами процессов рядом с комплектом, пишется при
   запуске потомка и чистится при его сборе), а не поиском по имени
   `1cv8`. В журнал: «подобраны хвосты прошлого запуска: N».
4. **Чужое не трогаем никогда.** Процесс платформы, который коннектор не
   запускал, — это 1С человека; её не гасят ни при каких условиях.
5. **Периодическая уборка.** На том же тике, что рисует карточку:
   потомок, переживший свой вызов и не привязанный ни к одному живому
   соединению моста, снимается, и об этом пишется строка в журнал.
6. **Проверка говорит, кто держит базу.** Факт «в базе открыт сеанс» —
   сведение, не провал: человек должен понимать, почему агент получает
   отказ.

### vrunner в локальном режиме (спайк 2026-10-20)

Второй мост (`778N`) — `vrunner-mcp` (`oscript … mcp.os`, AutumnMCP 1.0.0,
61 инструмент). Проверено на Windows с учебной платформой и базой УНФ:
`extensions_list` с аргументами моста (`ibconnection`, `db-user`,
плюс `v8version`) отработал примерно за три минуты. Два вывода:

- **vanessa-runner ищет платформу по стандартным именам.** Он берёт
  каталог платформы и требует рядом `1cv8c.exe` (на Linux `1cv8c`);
  у учебной платформы бинари называются `1cv8t.exe`/`1cv8ct.exe`, и без
  подмены имён любой вызов падает с «Не установлен тонкий клиент». В
  образе это уже решено симлинками (`/opt/1cv8` → учебная), на Windows
  нужен тот же приём — жёсткие ссылки `1cv8.exe`/`1cv8c.exe` рядом с
  оригиналами. Коннектор в локальном режиме обязан это обеспечить (или
  честно сказать, что платформа не годится); версия выбирается
  аргументом `v8version`.
- **Часть инструментов vrunner поднимает сеанс «Предприятия»**
  (`extensions_list` — в режиме 1С:Предприятие). На учебной лицензии это
  тот самый единственный сеанс: пока шёл вызов, открытый веб-клиент
  получил «Нарушение прав доступа». То есть конкуренция за сеанс бывает
  не только «человек против агента», но и «инструмент против
  веб-клиента»; поведение прежнее — ошибка платформы в журнал и агенту,
  коннектор ничего не арбитрирует.

### Расширение и проверка в локальном режиме

- **`find_1cv8` сегодня безусловно ищет платформу в `Program Files`** — на
  Linux факт «платформа» не «теряет смысл», а падает. Функция становится
  кроссплатформенной: на Windows — как сейчас (каталог версии и bin/1cv8.exe в обоих Program Files),
  на Linux — `/opt/1cv8/x86_64/<версия>/1cv8` и
  `/opt/1cv8t/x86_64/<версия>/1cv8t` (учебная), версии сортируются
  как числа, берётся старшая; путь можно задать руками переменной
  `ONEC_PLATFORM`. В образе `/opt/1cv8` — симлинк на `/opt/1cv8t`, то есть
  это одно дерево, а не две платформы: поиск обязан это терпеть и не
  показывать одну платформу дважды. Установка расширения — тот же
  `mcp-1c --install`, бинарь по ОС, на Linux под `xvfb-run -a`, если нет
  `DISPLAY` (конфигуратору нужен дисплей).
- Факты `verify::run` по режиму: общие — параметры, платформа, комплект
  инструментов, каталог проекта, Gitea; туннельные — SSH-адрес, `1cv8.exe`;
  локальные — публикация отвечает (`GET base_url/version`), расширение
  установлено, порты `777N`/`778N` слушает именно этот процесс (или
  свободны, если MCP выключены), «1С с этой базой открыта» как `info`
  (не провал: это и есть ситуация лимита, человек должен знать).
  **`verify::ORDER` — позиционный массив с проверкой длины**, поэтому
  факты сначала получают имена, а уже потом делятся по режимам
  (найдено ревью 2026-10-19).

### Ошибки платформы — в журнал и агенту

`bridge` уже отдаёт агенту ответ инструмента как есть. Текст лимита
сеансов («превышено предельное количество подключений») проходит без
перевода; окно добавляет строку `Warn` в журнал: «агент не вошёл в базу:
<текст платформы>; если 1С открыта у вас — закройте её». Это единственное
место, где учебная платформа упоминается в поведении, и оно же сработает на
обычной платформе при любом отказе входа.

### Стенд после этого

`1c-stand` перестаёт слушать `777N`/`778N` и запускать `mcp`/`vrunner` сам:
эти ветки скрипта уходят, остаются `seed` (toml, копия бинаря), платформа и
`connect` (запуск `1c-connect --tray`). Публикацию стенд тоже больше не
ведёт — её пишет коннектор под пользователем, а `start)` стенда сегодня
поднимает Apache от root с каталогом в `/run`, куда рабочему месту хода
нет (найдено ревью 2026-10-19): каталог публикации и файлы сервера
переезжают в домашний каталог рабочего места.

Две сопутствующие правки на стороне стенда: «включать MCP при запуске»
выставляется в состоянии комплекта (это **не** ключ toml — `autoconnect`
живёт в состоянии, `Kit::state_set`), а смоук-тест стенда, который сегодня
проверяет порты сразу после старта контейнера, сам запускает
`1c-connect serve` перед проверкой.

Любой новый ключ `[host]` (включая `publication`) обязан появиться и в
`1c-connect.example.toml`: `render` печатает только те ключи, что есть в
образце, а `deny_unknown_fields` превращает незнакомый ключ в отказ
загрузить файл целиком (найдено ревью 2026-10-19).

### Окно

Меняются слова (переключатель, карточка, трей) и набор строк «Проекта»
(HTTP-сервис базы — строка в обоих режимах при `publication = "auto"`).
Подменю «Режим работы» в трее — по спеке окна, делается здесь же: выбор
пишет `mode` в toml и перезапускает сеанс. Спека окна при этом говорит,
что в локальном режиме переключателя нет, — её надо поправить тем же
коммитом (найдено ревью 2026-10-19).

Слова, которые сегодня говорят о туннеле и обязаны поменяться вместе с
переключателем: `session::State::label()` и строка журнала о переходе
сеанса (она ещё и печатает адрес среды и имя рабочего места — в локальном
режиме этих полей в окне нет).

**Поля «Параметров» зависят от режима** (как и планировала спека окна;
проверка строителем нашла, что эта спека говорила обратное — исправлено):
туннельный — все семь, как сейчас; локальный — только про базу и проект
(каталог базы, пользователь и пароль базы, каталог исходников). Адрес
среды, пароль и имя рабочего места в локальном режиме не показываются:
они ничего не делают. Рабочее место при этом остаётся в toml — от него
считаются номера портов `777N`/`778N`.

## Порядок работ

Одной задачей это не делается: внутри лежат три разных куска, и резать их
надо по живому, а не по алфавиту.

1. **Транспорт и жизненный цикл** — два слушателя, один владелец рабочего
   места, рабочая уборка потомков на Linux, слова и поля по режиму,
   `find_1cv8` по обеим ОС, факты проверки. Публикация на этом шаге
   остаётся `"webserver"`, то есть как сегодня. Это уже работает в образе
   с первого дня и ничем не рискует.
2. **Публикация `"auto"`** — свой httpd, дескриптор с обязательными
   атрибутами, строка операции, `base_url` вычислением, Apache в комплекте
   Windows. Проверено спайком, но трогает упаковку и стенд.
3. **Подменю «Режим работы»** и правка спеки окна — последним, когда
   поведение режимов уже есть.

## Что остаётся строителю

- Как разделить `session.rs`: `transport::tunnel` / `transport::local` с
  общим `pipe_jsonrpc`, или две ветви в `start` — по размеру кода.
- Детали завершения дочерних процессов мостов на Linux при остановке
  сеанса.
- Формат строки «Проекта» для публикации и тексты фактов проверки по
  режиму.
- Где взять версию платформы для путей `/opt/1cv8t/x86_64/<версия>`:
  каталог единственный — брать первый.

## Проверки

- `session`: локальный транспорт на свободных портах принимает соединение,
  гонит `initialize` в фиктивный mcp-скрипт и закрывается по `stop`; занятый
  порт → `Failed` с текстом; смена `cfg` между сеансами меняет `--base` у
  `mcp_command` (проверяется по аргументам команды).
- `verify`: набор фактов по режиму (тест на два `mode`).
- `ops_host::Publication`: на Linux `default.vrd`/конфиг Apache по образцу
  стенда — текстовое сравнение с эталоном; на Windows — аргументы запуска
  `ENTERPRISE /F … /HTTPPort …` и выведенный `base_url` (чистая функция,
  без запуска платформы).
- Уборка: после `stop` ни одного живого потомка моста (на Linux — проверка
  группы процессов на фиктивном долгоживущем скрипте).
- Живой прогон на стенде (Linux): вход → трей → MCP включены → агент в Zed
  видит базу → человек открывает 1С → вызов агента падает с текстом лимита
  в журнале → закрыл 1С → агент снова работает → сменил базу в
  «Параметрах» → агент на новой базе.
- Живой прогон на Windows: `publication = "auto"` на непубликованной базе →
  MCP включены → `base_url` выведен, `version` отвечает, Apache и IIS не
  установлены → «Загрузить из git» опускает и поднимает сеанс → агент снова
  видит базу.

## Решения заказчика (2026-10-19)

- Переключатель включает MCP для текущего проекта; лимит сеансов учебной
  платформы — обычная ошибка в журнале, не особая механика.
- Выключено = порты закрыты, Zed переподключается сам.
- Базу и проект выбирают в «Параметрах», списков баз нет.
- HTTP-сервис активной базы поднимает `1c-connect` на обеих ОС
  (`publication = "auto"`): Windows — ключ платформы `/HTTPPort`, без
  Apache и IIS; Linux — свой Apache рабочего места. Стенд публикацию
  больше не трогает. `"webserver"` остаётся для уже опубликованных баз.
- Локальный режим проектируется сразу под обе ОС.

# Среда разработки 1С на сервере

Комплект поднимает на одном сервере два контейнера:

- **среда** — рабочие места 1С по RDP (`dev1`, `dev2`, `dev3`), Gitea с репозиториями, SSH для туннеля к инструментам 1С;
- **сервер модели** — локальная модель для агентов в редакторе, на видеокарте этого же сервера.

Сервер закрыт от интернета: всё, что нужно, едет в комплекте, кроме файла
модели и того, что ставит администратор сервера (см. ниже). Дальше —
Ubuntu 24.04, x86-64, права `sudo`.

Весь разговор с комплектом идёт одной программой `dev1c-setup`. Она же, если
двоичный файл в контуре не разрешён, напечатала раздел «Ручной путь» в конце
этой страницы: те же действия командами `docker`.

## Что нужно до начала

**1. Docker Engine уже установлен и отвечает.** Движка в комплекте нет — он
ставится до нас, и на сервере без интернета пакеты приносят с собой. Подойдёт
любой из двух наборов:

- пакеты Ubuntu 24.04: `docker.io`, `containerd`, `runc`;
- пакеты Docker (`download.docker.com`): `docker-ce`, `docker-ce-cli`,
  `containerd.io` — вместе с их зависимостями.

Проверка на месте:

    docker version                 # должен ответить раздел Server
    dpkg -l | grep -E 'docker|containerd'

Если видно «permission denied» — пользователь не в группе `docker`:

    sudo usermod -aG docker $USER      # и войти заново (или newgrp docker)

**2. Драйвер NVIDIA уже установлен на самом сервере.** Драйвера в комплекте
нет: он подбирается под карту, этим занимается администратор сервера. В
Ubuntu пакет называется `nvidia-driver-<номер>-server` (серверный вариант, без
графической части) — номер берётся тот, что поддерживает вашу карту.

    nvidia-smi                     # модель карты, память, версия драйвера
    dpkg -l | grep nvidia-driver

В заголовке `nvidia-smi` есть «CUDA Version» — нужно **12.8 или новее**: образ
сервера модели собран с CUDA 12.8. Ядра в образе собраны под Ampere (30xx) и
Blackwell (50xx), для остальных карт новее Turing драйвер собирает их сам при
первом запуске — это добавляет минуту к первому старту сервера модели.

**3. NVIDIA Container Toolkit — он в комплекте.** Без него карту видит
операционная система, но не контейнер:

    sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker

**4. Файл модели. Его в комплекте нет.** `.gguf` для агентов приносит
заказчик: файл весит гигабайты и выбирается под карту. Положите его в каталог
комплекта и назовите в `dev1c.toml`:

    [model]
    file = "Qwen3-Coder-30B-A3B-Q4_K_M.gguf"

Пока там пусто, установка останавливается словами «модель не выбрана:
`[model] file` — файл в комплекте». Файл копируется в том `dev1c-models` на
установке, из каталога комплекта его потом можно убрать.

**5. Четыре порта подряд свободны.** Первый задан в `dev1c.toml`
(`[server] port`, по умолчанию 3390), дальше по порядку: RDP, Gitea, сервер
модели, SSH для туннеля — 3390, 3391, 3392, 3393. Заняты — поставьте другой
блок (см. «Правка dev1c.toml»).

**6. Память сервера.** Установка ставит контейнеру среды предел из
`[server] memory` — по умолчанию `24g`. Значит, оперативной памяти на сервере
нужно не меньше **32 ГБ**: 24 ГБ среде, остальное — хосту и кэшу сервера
модели (он берёт до 8 ГБ от свободной памяти). Памяти меньше — уменьшите
предел: `./dev1c-setup change memory=16g`.

**7. Видеопамять.** Модель живёт целиком на карте, и окно контекста — тоже. В
видеопамяти должны поместиться: файл `.gguf` целиком, окно не ниже
`[model] fit_ctx` (по умолчанию 65536 токенов) и запас 2 ГБ, который сервер
оставляет на чужую нагрузку. Не помещается — установка останавливается и
называет окно, которое вышло. Карта, занятая чем-то ещё (рабочий стол, другая
модель), отдаёт настолько меньше: `./dev1c-setup check` печатает занятую и
полную память карты.

**8. Место на диске.** Образ едет архивом (`dev1c-image.tar.gz`) и после
`docker load` занимает в `/var/lib/docker` примерно столько же ещё раз.
Модель — отдельно, в томе. Тома лежат там же, в `/var/lib/docker`.

## Что скопировать и куда

Комплект копируется целиком, одним каталогом — программа ищет свои файлы
рядом с собой:

    scp -r dev1c-kit-linux <логин>@<сервер>:/srv/dev1c-kit

Или флешкой — тогда скопируйте каталог в `/srv/dev1c-kit`. Все команды
дальше выполняются из этого каталога:

    cd /srv/dev1c-kit
    chmod +x dev1c-setup            # если бит исполнения потерялся по дороге

## Проверить, что довезли целиком

    sha256sum -c checksums.txt

Каждая строка должна кончаться на `: OK`. В списке нет `dev1c.toml` — его
правят на месте, и его сумма менялась бы от каждой правки. То же самое
проверкой из комплекта: `./dev1c-setup verify`.

Битый или недовезённый файл — копируйте комплект заново; архив образа на
гигабайты обрывается чаще всего.

## Правка dev1c.toml

Обязательное — одно: `[model] file`. Остальное имеет значения по умолчанию,
и каждое поле в файле объяснено комментарием рядом. Правки удобнее делать
программой: она проверяет значение и применяет только то, что разошлось.

    ./dev1c-setup change port=4000           # другой блок портов
    ./dev1c-setup change memory=32g          # предел памяти контейнера среды

## Три команды

    ./dev1c-setup status     # что уже есть и что мешает; на машине ничего не меняет
    ./dev1c-setup install    # грузит образ, создаёт тома, копирует модель,
                             # поднимает и замеряет сервер модели, собирает
                             # контейнер среды, ждёт его службы и проверяет
    ./dev1c-setup check      # проверки по фактам; отчёт — last-check.txt

`install` на чистом сервере идёт долго: архив образа — минуты, копирование
модели в том — минуты, замер сервера модели — до пяти минут (модель читается
с диска на карту). Повторный запуск делает только то, чего не хватает.

Все три работают по SSH без терминала (`ssh сервер '/srv/dev1c-kit/dev1c-setup install'`):
вопросов, на которые некому ответить, они не задают. Единственное исключение —
удаление данных: без терминала оно отказывается и просит ключ `--yes`.

## Что нормально увидеть

`status` до установки перечисляет операции и причины, а не «шагов: 0». На
чистом сервере с комплектом, каким он приехал, — то есть с пустым
`[model] file`:

    Комплект: /srv/dev1c-kit

      image      Образ среды          не сделано
      volumes    Тома данных          не сделано
      model      Файл модели          нельзя: модель не выбрана: [model] file — файл в комплекте
      llama.container Контейнер модели     нельзя: модель не выбрана: [model] file — файл в комплекте
      container  Контейнер среды      нельзя: сервер модели ещё не замерен (шаг llama.answers); без его чисел контейнер собирать нельзя

    Применить то, чего не хватает: dev1c-setup install

Три «нельзя» до установки — норма, а не поломка, и две из них снимает
`[model] file`. Назовёте модель — те же строки станут такими:

      model      Файл модели          не сделано
      llama.container Контейнер модели     нельзя: образ oktaplus/dev1c-llama:latest не загружен: он едет в том же архиве, что и образ среды

Оставшиеся два «нельзя» ждут того, что `install` делает раньше них: загружает
образ из архива и замеряет сервер модели. После установки в этих строках стоит
«сделано».

В конце `install` — адреса, которые диктуют разработчикам (адрес сервера
программа подставляет свой):

    Среда запущена:
      Рабочие места   mstsc /v:192.168.1.10:3390  —  dev1/dev1, dev2/dev2, dev3/dev3
      Репозитории     http://192.168.1.10:3391
      Сервер модели   http://host.docker.internal:3392/v1 (Qwen3-Coder-30B-A3B-Q4_K_M)
      Для 1c-connect  192.168.1.10:3393

`check` — нумерованный список фактов; `[info]` — не провал, а сведение:

      1. [ ok ] движок контейнеров: docker 29.8.2
      2. [ ok ] контейнер: работает
      3. [ ok ] рабочие места (RDP): порт 3390 принимает соединение
      4. [ ok ] Gitea: http://127.0.0.1:3391/ отвечает 200
     10. [ ok ] видеокарта: NVIDIA RTX ..., занято ... МиБ, драйвер ...
     12. [ ok ] модель в настройках Zed: провайдер custom, модель ...

    Пройдено 16, провалено 0. Отчёт: /srv/dev1c-kit/last-check.txt

## Когда не получилось

Программа называет преграду и команду, которая её снимает — на сервере без
интернета спросить нас по ходу не выйдет. Что встречается:

- «Docker отвечает «в доступе отказано»: пользователь не в группе docker» —
  `sudo usermod -aG docker $USER`, затем войти заново.
- «Служба Docker не отвечает: демон не запущен или сокет недоступен» —
  `sudo systemctl restart docker`.
- «Драйвер NVIDIA на сервере не отвечает (nvidia-smi молчит)» — карту не видит
  сама операционная система. Из комплекта это не лечится: нужен администратор
  сервера с драйвером под эту карту.
- «Драйвер на сервере работает, но видеокарта не видна внутри контейнера» —
  `sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker`.
- «Не найден архив образа: …» или «Не найден файл модели: …» — в сообщении
  назван путь, куда программа смотрела. Архив — значит комплект довезли не
  целиком; файл модели — значит `.gguf` не лежит в каталоге комплекта под тем
  именем, что в `dev1c.toml`.
- «модель не выбрана: `[model] file` — файл в комплекте» — пункт 4 выше.
- «образ oktaplus/dev1c-llama:latest не загружен: он едет в том же архиве, что
  и образ среды» — `./dev1c-setup install` загрузит архив целиком.
- «сервер модели ещё не замерен (шаг llama.answers); без его чисел контейнер
  собирать нельзя» — сначала должен подняться сервер модели: контейнер среды
  получает его числа переменными.
- «сервер выделил окно N токенов при нижней границе fit_ctx = M: на этой карте
  модель с такими параметрами не помещается» — карты не хватает на такую
  модель. Либо модель меньше или с более плотным квантованием, либо ниже
  граница: `./dev1c-setup change model.fit_ctx=...`.
- «порт N занят другой программой — задайте другой блок:
  `dev1c-setup change port=4000`».

Куда смотреть:

- `setup.log` в каталоге комплекта — все команды движка и их вывод, по порядку;
- `last-check.txt` — отчёт последней проверки;
- `docker logs dev1c-llama` — сервер модели (почему не поднялся, какое окно взял);
- `docker logs dev1c` — среда (gitea, xrdp, sshd).

Снять среду: `./dev1c-setup clean --stack` (контейнер, данные на месте) или
`./dev1c-setup clean --data --yes` (и тома — репозитории, проекты, настройки).

## Ручной путь

Этот раздел печатает сама программа при сборке комплекта: ниже — те же
команды, которые выполнил бы `./dev1c-setup install`, в том же порядке. Они
для случая, когда наш двоичный файл в контуре запускать не станут.

Перед тем как вставлять:

- выполняйте из каталога комплекта: пути в командах относительные;
- `.gguf` лежит в каталоге комплекта под тем именем, что в `dev1c.toml`; ниже
  он назван `модель.gguf`, подставьте своё;
- значения портов, имён и предела памяти в командах взяты из `dev1c.toml` того
  комплекта, с которым приехала эта страница; поправили `dev1c.toml` — правьте
  и команды;
- `--env-file llama.env` — файла нет в комплекте, его создаёт установка. Для
  ручного пути сделайте сами, ключ придумайте любой: он закрывает сервер
  модели от остальной сети этого сервера.

      printf 'LLAMA_API_KEY=%s\n' "$(tr -dc a-f0-9 </dev/urandom | head -c 32)" > llama.env

- `docker rm -f …` на первой установке отвечает «No such container» — так и
  должно быть, дальше по списку;
- `-p <адрес>:3392:8080` — адрес моста `docker0` этой машины; в командах стоит
  тот, что был на машине сборки комплекта. Свой: `docker network inspect
  bridge -f '{{(index .IPAM.Config 0).Gateway}}'`. Этот же адрес — тот, по
  которому сервер модели потом отвечает: подставьте его и в команды;
- **последняя команда неполна.** `docker run` контейнера среды напечатан без
  пяти переменных `CUSTOM_*`: до замера сервера модели их никто не знает.
  Вставите список как есть — среда поднимется, рабочие места и репозитории
  заработают, а агент в редакторе промолчит. Что дописать — в разделе «Шаг,
  который нельзя вставить» сразу после команд;
- `--cache-ram` и `--fit-target` — числа, замеренные на машине сборки
  (половина свободной памяти под кэш; запас на карте под чужую нагрузку).
  Работать будет и так; под сервер их считает `./dev1c-setup install`.

### Шаг, который нельзя вставить: числа модели

Сколько модель получит контекста, решает не комплект, а карта: сервер модели
подбирает окно сам, под то, что на карте свободно. Поэтому последний шаг —
единственный, который нельзя приготовить заранее.

Поднимите сервер модели (команда выше) и спросите его. Ключ — тот, что в
`llama.env`. Адрес и порт — те самые, что стоят в `-p <адрес>:3392:8080` в
команде сервера модели выше: на петле (`127.0.0.1`) он не отвечает, порт
опубликован на адресе моста `docker0`.

    curl -s -H "Authorization: Bearer <ключ>" http://<адрес из -p>:3392/props

В ответе `default_generation_settings.n_ctx` — окно в токенах, которое карта
дала на самом деле. Если оно меньше `fit_ctx` из `dev1c.toml` — модель на этой
карте не помещается, и дальше идти незачем.

Из этого окна берётся `max_tokens` — сколько контекста получает агент в
редакторе. Программа считает его сама и печатает строкой:

    [ ok ] окно 65536 токенов, слотов 3, модель <имя>; Zed получает max_tokens = ...

Если считаете сами, держитесь проверки, которой программа это и проверяет:
`max_tokens × agents + 8192 ≤ окно` (`agents` — из `dev1c.toml`, 8192 — запас
на ответ модели).

Эти числа и адрес сервера модели дописываются к `docker run` контейнера среды
пятью переменными — их нет в командах выше, потому что до замера их никто не
знает. Без них среда поднимется и редактор будет работать, а агент промолчит:

    -e CUSTOM_API_URL=http://host.docker.internal:3392/v1 \
    -e CUSTOM_API_KEY=<ключ из llama.env> \
    -e CUSTOM_MODEL=<имя модели: --alias из команды сервера модели> \
    -e CUSTOM_MAX_TOKENS=<число из замера> \
    -e CUSTOM_MAX_OUTPUT_TOKENS=8192

Внутри контейнера эти переменные подставляются в настройки редактора
(провайдер `custom`). Если среда уже собрана без них — пересоберите контейнер
среды той же командой с добавленными `-e`: тома, а с ними репозитории и
проекты, остаются на месте.

Проверить вышедшее можно и чужими руками: `./dev1c-setup check` смотрит на те
же факты — отвечает ли сервер модели, подставлены ли провайдер и модель в
настройки редактора, сходятся ли три числа.

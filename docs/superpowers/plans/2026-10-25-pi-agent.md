# Агент pi в образе стенда — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** в образе стенда появляется команда `pi` — терминальный агент с теми же скиллами, инструкциями и серверами MCP, что у агента в панели Zed, и с моделью с нашего `llama-server`.

**Architecture:** бинарь pi собирается отдельной стадией Dockerfile и копируется в образ (Node в поставку не едет). Скиллы не требуют работы — они уже лежат в `/etc/skel/.agents/skills`, штатном месте Agent Skills, которое pi читает сам. Инструкции — тот же файл `config/agents-global.md`, скопированный вторым назначением. Серверы MCP — отдельный файл `config/pi/mcp.json`, совпадение которого с настройками Zed держит тест. Модель — своё расширение на обычном JavaScript: родной llama-провайдер pi требует поля `status` в ответе `/models`, которого одномодельный сервер не отдаёт.

**Tech Stack:** Docker multi-stage, Node 22 (только в стадии сборки), POSIX sh, JavaScript (расширение pi), Rust (тест совпадения mcp.json с настройками Zed), python3 (заглушка сервера в проверке).

**Spec:** `docs/superpowers/specs/2026-10-25-pi-agent-design.md`

## Global Constraints

- Версия pi пинуется: **v1.4.0** (релиз 2026-10-21). Источник — `pi-1.4.0-source.tar.gz` из релиза, рядом `SHA256SUMS`.
- Сборка бинаря: `./scripts/build-binaries.sh --offline-model-data --platform linux-x64 --out "$PWD/out"`.
- Node нужен **только** в стадии сборки. В итоговом образе Node и npm быть не должно — это проверяется шагом в задаче 1.
- Расширение — на **JavaScript**, не на TypeScript: от бинаря тогда не требуется загрузчик TS.
- Каталог настроек pi: `~/.pi/agent`. Файлы: `AGENTS.md`, `mcp.json`, `settings.json`, `extensions/`.
- Инструменты pi не ограничиваем (режим YOLO, решение заказчика 25.10.2026). Границей остаётся контейнер.
- Тема pi — `system`, это её умолчание; своей палитры не пишем.
- Онбординг не трогаем: его файлы правит другая задача. Строка про pi идёт только в `config/agents-global.md`.
- Все новые скрипты в образе проходят существующую проверку `head -1 … | grep -qx '#!/bin/sh'` и попадают в список `chmod +x` (Dockerfile, около строки 374).

**Расхождение со спекой, принятое здесь:** спека говорила добавить переменную `LLAMA_BASE_URL` в `/etc/environment`. Она не нужна: `LLAMA_BASE_URL` читает **родной** провайдер pi, а у нас своё расширение, и оно берёт адрес из уже раскладываемых точкой входа `LLAMA_API_URL` (штатная форма) и `CUSTOM_API_URL` (удалённая). Новая переменная — лишнее обещание.

## Review Focus

- **Сервера модели нет** (`LLAMA_API_URL` не задан или адрес не отвечает): `pi` обязан запуститься и сказать, что модели нет, а не упасть. Тест — задача 3.
- **`/models` без `meta.n_ctx`** (чужой шлюз, не llama.cpp): расширение обязано не регистрировать модель вовсе, а не регистрировать её с нулевым окном. Тест — задача 3.
- **Дом создан прежним образом**, каталога `.pi` в нём нет: точка входа обязана создать его и отдать пользователю, а не оставить root-овским. Тест — задача 2.
- **Человек правил `settings.json` pi**: действует общее правило отпечатка — файл заменяется, прежний остаётся рядом как `.bak`. Тест — задача 2.
- **На месте `~/.pi` символическая ссылка**: точка входа обязана отказаться и не писать по ссылке — то же правило, что для `.config` (entrypoint.sh, «skipping … symlink»). Тест — задача 2.

fn pi_declares_the_same_mcp_servers_as_zed() {

    p.sort();

### Task 3 — задача 3: расширение «одномодельный llama.cpp»

**Files:**

- Create: `config/test-pi-stub.py` (заглушка сервера для проверки)

**Interfaces:**
- Consumes: `/usr/local/bin/pi`, раскладку настроек из задачи 2.
- Produces: провайдер, который pi показывает как модель с окном из `meta.n_ctx`.

**Почему расширение вообще:** родной llama-провайдер pi берёт список моделей через `GET /models` и требует поля `status.value` (`packages/coding-agent/src/extensions/llama/client.ts`). Одномодельный `llama-server` этого поля не отдаёт — проверено живым запросом к сборке `b11734`:

```json
{"object":"list","data":[{"id":"GLM-4.7-Flash-UD-Q4_K_XL","owned_by":"llamacpp",
  "meta":{"n_ctx":161024,"n_ctx_train":202752}}]}
```

Окно при этом **уже в ответе** — в том самом поле `meta.n_ctx`, которое pi и читает. Объявлять его нигде не надо, и это обязательное свойство: объявленное число — снимок на момент установки, а сервер пересчитывает окно при каждом старте.

- [ ] **Шаг 1: написать заглушку сервера `config/test-pi-stub.py`**

Аргумент `--shape` с двумя значениями: `ok` и `no-meta` (из `/models` убран `meta`). Третий случай — «сервера нет» — заглушке не нужен: проверка целится в закрытый порт.

- [ ] **Шаг 4: написать `config/pi/extensions/llama-single.js`**

Экспортирует `export default function (pi) { … }` и вызывает `pi.registerProvider(…)`. Что делает:

## Что остаётся выяснить по ходу

Спека требует сказать это вслух, а не обнаружить на стенде: **предел времени на вызов инструмента**. У серверов MCP в настройках Zed он задан (300 с, а у `vrunner` 3600 с — выгрузка ЕРП идёт десятки минут), а в форме `mcp.json` у pi такого поля в документации не видно. Если его там нет, `vrunner` через pi упрётся в умолчание, и это надо записать в спеку как известное ограничение, а не оставить на усмотрение того, кто однажды будет ждать выгрузку.

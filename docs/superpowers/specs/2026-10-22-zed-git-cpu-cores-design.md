# Git из Zed не должен занимать больше двух ядер

**Дата:** 2026-10-22. **Повод:** заказчик — «Давай отключим гит в Zed», затем
«развести по ядрам процессы», затем «просто ограничь количество ядер для гита
до 2-х».

## Что измерено

Все числа — на живом контейнере `dev1c`, рабочее место dev1, проект
`/home/dev1/project` (184 556 файлов, `src/` — 66 958 файлов, `.git` — 117 591
файл), 2026-10-22.

**Zed сам опрашивает git каждые ~2–5 с.** Команда:

```
git -c core.fsmonitor=false -c log.showSignature=false --no-optional-locks \
    --no-pager status --porcelain=v1 --untracked-files=all --no-renames -z -- <pathspec>
```

18 запусков за 45 с. Файлов в репозитории за 10 минут не менялось — то есть
это **поллинг, а не реакция на изменения**.

**Pathspec — вот где вся цена.** В него попадают каталоги выгрузки:
`src/<Объект>/Ext`, `src/<Объект>/Forms` — 7 316 путей. Один такой
`git status` — **31.2 с**. Плоский `git status -- .` по тому же репозиторию —
1.3 с. Разница в 24 раза — это ровно число путей.

**Zed запускает вызовы параллельно**, и они бьют по CPU всех ядер сразу:

| Сценарий (8 × `git status` параллельно) | wall | CPU / wall | CPU всего |
|---|---|---|---|
| без ограничения | 2.19 с | **7.56 ядра** | 16.56 с |
| `taskset -c 6,7` | 4.22 с | **2.09 ядра** | 8.81 с |

Ограничение не только перераспределяет ядра: суммарный CPU git падает на
**47 %** — снимается конкуренция за кэш ФС и дублирующая работа. wall
растёт почти вдвое, и это правильный размен: git — фоновая задача.

## Что уже проверено и отвергнуто

| Вариант | Результат |
|---|---|
| `"git": {"disable_git": true}` | Прячет UI git (панель проекта, outline, вкладки). **Поллинг продолжается**: A/B на живом стенде — 14 вызовов git до флага и те же 14 после, набор команд идентичен (`remote`, `worktree`, `for-each-ref`, `symbolic-ref`, `show`, `stash`, `status`, `cat-file`, `config`, `rev-parse`). Это баг апстрима: [#13304](https://github.com/zed-industries/zed/issues/13304), [#43861](https://github.com/zed-industries/zed/issues/43861) |
| `GIT_CEILING_DIRECTORIES` для Zed | Zed игнорирует: репозиторий всё равно открыт, 14 вызовов, 32.7 с |
| `GIT_INDEX_THREADS=1` | Без эффекта (0.73–0.87 с). Цена — обход untracked, он однопоточный; потоки тратятся на загрузку индекса |
| Исключить `**/Ext/**` и `**/Forms/**` из `file_scan_exclusions` | Pathspec не уменьшается (6 000–11 000 путей): в него попадают сами каталоги. Замер: entries воркспейса 97 294 → 54 787, но `status` так и ~30 с |
| Шим, схлопывающий pathspec в `:/` | `status` 31 → 3.9 с, но Zed следом зовёт `git diff --numstat HEAD -- :/` — **63 с и 56 с** на каждый вызов (диффинг всего репозитория). Отвергнуто: вредит больше, чем лечит |
| Ограничить `LP_NUM_THREADS` | Отвергнуто заказчиком: сервер многоядерный, срезать потоки — лечить симптом |

**Вывод:** фоновые вызовы git из Zed 1.24.4 отключить нельзя — ни настройкой,
ни трюком с путями. Остаётся одно: сделать их дешёвыми по последствиям.

## Цели

1. Git, запущенный из Zed, **никогда не занимает больше двух ядер** — сколько
   бы вызовов Zed ни поставил параллельно.
2. Git **уступает** Zed, ОС и 1С: он фоновая задача, а не равноправный
   сосед по процессору.
3. Git **пользователя в терминале** работает как раньше — без ограничений.
4. Решение не зависит от числа ядер, движка контейнеров и прав доступа:
   считается в рантайме, при любом отказе работает, просто без cap.

## Не-цели

- Эксклюзивные ядра для git. Заказчик прямо отказался: git делит ядра с
  остальными, он просто ограничен двумя.
- Ограничивать сам Zed или его потоки.
- Менять конфигурацию контейнеров, `docker run` и compose — cap живёт
  внутри образа.
- Добиваться, чтобы фоновая работа git исчезла: 30 с на `status` останутся,
  просто станут растянутыми и фоновыми.

## Решение

### 1. Обёртка `/usr/local/bin/git`

Новый файл `config/git-cpuset.sh`, устанавливается в образ как
`/usr/local/bin/git` — он перекрывает `/usr/bin/git` в `PATH` (`/usr/local/bin`
в `PATH` идёт раньше). Настоящий git вызывается по абсолютному пути.

Логика:

1. **Реальный git** — `/usr/bin/git`.
2. **Кто зовёт.** Обёртка смотрит цепочку предков в `/proc` (`PPID` →
   `/proc/<pid>/stat` → …, до 8 уровней) и ищет процесс с `zed` в имени
   (`zed-editor`). Не нашли → `exec /usr/bin/git "$@"` без изменений: git
   клиента в терминале не затронут.
3. **Набор ядер для git.** `DEV1C_GIT_CPUS` (переопределение вручную, например
   `DEV1C_GIT_CPUS="0,1"`) либо последние два CPU из собственной маски
   процесса (`/proc/self/status` → `Cpus_allowed_list`, например `0-7` → `6,7`).
   Берётся из маски самого процесса, поэтому набор всегда корректный
   подмножеством того, что доступно, — `taskset` расширять маску не нужно.
4. **Запуск:** `exec taskset -c <набор> nice -n 19 ionice -c 3 /usr/bin/git "$@"`.
   - `taskset` ограничивает суммарную параллельность git двумя ядрами;
   - `nice -n 19` — git не вытесняет ни Zed, ни ОС;
   - `ionice -c 3` — git не забирает дисковый I/O у 1С и конфигуратора.
5. **Отказы.** Если `taskset` недоступен или ядро не даёт установить маску —
   обёртка запускает git без ограничения (функциональность не теряется).
   Если `nice`/`ionice` отсутствуют — они просто не применяются.

### 2. Выключен UI git в Zed

В `config/zed-settings.json` уже добавлено:

```json
"git": {
  "disable_git": true,
  "git_gutter": "hide"
}
```

Панель git, outline, вкладки git-статуса и скроллбар с диффом не рисуются
(это и была исходная просьба «отключим гит в Zed»). Фоновые вызовы при этом
продолжаются — их и ограничивает пункт 1.

### 3. Что не меняется

- Zed **не прибивается** к ядрам.
- Ядра **не резервируются** под git.
- Права доступа контейнера не меняются (`taskset` сужает маску и без
  `CAP_SYS_NICE`; расширять её не нужно).
- `docker run`, compose, `setup/dev1c-setup` — без правок.

## Универсальность

| Ситуация | Поведение |
|---|---|
| 8 ядер (текущий стенд) | git получает `6,7` |
| 32 ядра (вероятный прод) | git получает `30,31` |
| 2 ядра | git получает оба; ограничивать нечего, ограничение становится в уступку по приоритету |
| Нестандартная маска (`0-3,8-11`) | берутся последние два из неё: `10,11` |
| `taskset` запрещён | git работает без cap, приоритет сохраняется |
| Docker или podman | без разницы — ограничение внутри образа |

Ручное переопределение: `DEV1C_GIT_CPUS="0,1"`.

## Проверки приёмки

1. **Ограничение держится.** Под Zed одновременно работает несколько вызовов
   git: `ps -o pid,psr,ni,comm` показывает `psr` только из выбранной пары,
   `ni=19`, `cls` — idle-класс I/O.
2. **Параллельность.** A/B-замер на тех же восьми параллельных `git status`:
   `CPU/wall` не больше ~2.1 ядра против 7.56 без обёртки; суммарный CPU
   ниже.
3. **Git пользователя не затронут.** `git status` в терминале: `ni=0`,
   маска процессов не ограничена.
4. **Откат.** С обёрткой, у которой `taskset` не сработал, git всё равно
   выполняет команды и возвращает корректный код возврата.
5. **Zed работает.** Панель проекта, поиск, терминал, git-вкладки по
   прежнему открываются; ошибок в `Zed.log` не больше, чем до изменений.

## Что остаётся за рамками

- **Воркспейс Zed.** Корень нагрузки на процессор — не git, а панель
  проекта: 128 475 записей воркспейса дают 358–391 % ядра в покое, пустой
  проект — 0 %. Это отдельная работа (см. спеку про GPU и рендер).
- **Фоновая работа git.** 30 с на `status` с 7 316 путями никуда не денутся:
  снять можно только уменьшив пути в pathspec, а это упирается в структуру
  выгрузки.
- **Апстрим.** Настоящее отключение поллинга git — баг
  [#13304](https://github.com/zed-industries/zed/issues/13304); когда
  починят, обёртка станет не нужна, но не мешает.

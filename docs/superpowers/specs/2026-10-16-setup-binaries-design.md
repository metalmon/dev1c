# Два установщика: `dev1c-setup` и `1c-connect`

Дата: 2026-10-16. Заменяет раздел «Конфигураторы» в
`2026-10-13-dev1c-image-design.md`.

## Зачем

Среда разворачивается скриптами (`dev1c.sh`, `dev1c.ps1`, `pack.sh`) и
инструкцией `SETUP.md`. На пилоте платформы Вольт это уже ударило: другое
окружение, и всё перестало работать, а скрипт с инструкцией не умеют сказать,
что именно и почему. Нужно то же, что сделано для Вольта в `volt-setup`: один
файл, который знает состояние машины по фактам, печатает план до того, как
что-то тронуть, и заканчивает проверками, а не обещаниями.

Второе: доступ агента к платформе 1С. Проверено, что `mcp-1c` читает живую
базу через HTTP-сервис расширения; но разработчики ходят каждый со своей
флешкой и своей базой, сервер про их базы знать не должен. Значит, всё, что
касается 1С, живёт на машине с платформой, и запускается там одной программой.

## Решения

- **Две программы, два комплекта.** `dev1c-setup` ставит среду на машине с
  Docker, запускает администратор один раз. `1c-connect` лежит на флешке у
  разработчика и запускается каждый день на машине с 1С. Аудитории и комплекты
  разные, общего кода мало.
- **Один файл параметров на комплект** — `dev1c.toml` и `1c-connect.toml`.
  Скрипты, `.env`, `.env.example` и `SETUP.md` удаляются: два способа запуска
  расходятся, это ровно то, от чего бежим.
- **На сервере нет ни одного параметра про 1С.** `mcp-1c` работает на машине
  с платформой, не в контейнере. Контейнер видит его через туннель как TCP-порт,
  Zed подключается к нему через `nc`. Порт выводится из имени рабочего места.
- **Без ключей, со встроенным SSH.** Туннель под учёткой `dev` с паролем из
  toml, как сейчас; клиент встроен в `1c-connect` (`russh`), системный
  `ssh.exe` не используется: это необязательный компонент Windows с разным
  поведением по версиям, а пароль он берёт только с клавиатуры. Пароль —
  граница пилота, ключи не добавили бы ничего, кроме кода подключения.
- **Стек** Rust + Tauri, скелет скопирован из `volt-setup`: операции с
  состоянием и планом, комплект с контрольными суммами, окно и CLI как две
  тонкие оболочки над операциями.

## Комплекты

```
dev1c-kit/                       администратору, один раз
  dev1c-setup.exe, dev1c-setup   программа (Windows, Linux)
  dev1c.toml                     параметры, единственный источник
  dev1c-image.tar.gz             образ

1c-connect/                      разработчику, на флешку
  1c-connect.exe                 программа (Windows)
  1c-connect.toml                параметры
  mcp-1c-windows-amd64.exe       MCP-сервер живой базы, той же версии, что
  MCP_HTTPService.cfe              расширение; версия пинована в Dockerfile
  checksums.txt
  (этап 2: oscript/, vanessa-runner/)
```

## Общий каркас (crate `common`)

Из `volt-setup` без изменений по смыслу:

- **Операция** (`op.rs`): `id`, `title`, `state(ctx)`, `plan(ctx)`,
  `apply(ctx)`, `revert`/`revert_apply` с уровнем очистки, `always_run`.
  Состояние: `Done(значение)`, `Missing`, `Drifted{from,to}`, `Blocked(почему)`.
  Из этого получаются `status` (спросить состояние), `install` (применить
  `Missing` и `Drifted`), `change` (применить только разошедшееся), `clean`
  (откатить в обратном порядке), `--dry-run` (напечатать план).
- **Комплект** (`kit.rs`): где лежит, файл состояния, журнал команд.
- **Целость** (`integrity.rs`, `verify`/`checksums`): список сумм при сборке
  поставки, сверка у заказчика.
- **Окно** (`gui.rs`, `ui/`): экраны состояния, плана, выполнения с живым
  журналом, проверок, очистки. HTML, CSS и JS без сборщика.
- **Ctx**: конфигурация, комплект, `dry_run`, приёмник событий (консоль или
  окно), вопросы человеку (в CLI — с клавиатуры, в окне — диалог, в тестах —
  ответ по умолчанию).

Не берём: сертификаты, брандмауэр, `hosts`, ключи администратора, резервные
копии, Keycloak, glossa.

Тексты по-русски. Каждое поле toml объясняет себя комментарием, подписи в окне
говорят то же; ошибки говорят, что делать. Пример `dev1c.toml` в комплекте
генерируется из структуры `Cfg`, чтобы поля и комментарии не расходились.

## `dev1c-setup`

### Параметры

```toml
# Среда разработки 1С. Правится только этот файл; всё остальное выводится.
[server]
port = 3390          # первый из четырёх портов подряд: RDP, Gitea, модель, SSH
memory = "24g"       # предел памяти контейнера
gpu = true           # false, если видеокарты нет: модель на процессоре
engine = "docker"    # или "podman"

[model]
file = "model/Qwen3.5-4B.gguf"   # относительно комплекта; пусто — модель удалённая
# url  = "https://model.example.com/v1"   # вместо file: OpenAI-совместимый сервер
# key  = ""                                # его ключ
# name = ""                                # имя модели, как сервер его называет
```

`[model]` с `url` даёт контейнеру `CUSTOM_API_URL`, `CUSTOM_API_KEY`,
`CUSTOM_MODEL` и `LLAMA_ENABLED=0`; с `file` — ничего, entrypoint находит файл в
томе сам. Ничего про 1С здесь нет и не появится.

### Команды

```
dev1c-setup                     окно
dev1c-setup status              что сделано, без изменений на машине
dev1c-setup install             применить всё, чего не хватает
dev1c-setup change port=4000    изменить параметр и применить только разошедшееся
dev1c-setup check               проверки по фактам; код возврата 1 при провале
dev1c-setup clean --stack       снять контейнер, данные оставить
dev1c-setup clean --data        плюс тома; спросит имя контейнера
dev1c-setup verify | checksums  целость комплекта
```

У всех `--dry-run`. `DEV1C_KIT` указывает на комплект, если программа лежит не
в его корне.

### Операции

| id | делает | состояние по факту | clean |
|---|---|---|---|
| `env` | движок есть, версия, место на диске, порты блока свободны или заняты нашим контейнером | всегда выполняется | — |
| `image` | `docker load` из комплекта | образ с нужным тегом загружен | data |
| `volumes` | `dev1c-home`, `dev1c-gitea`, `dev1c-models` | тома есть | data |
| `model` | копирует `model/*.gguf` в `dev1c-models` | в томе файл того же имени и размера | data |
| `container` | `docker run` с портами, `--init`, capabilities, `--device /dev/fuse`, GPU по флагу, переменными из toml | контейнер запущен из этого образа с этими портами и переменными; иначе `Drifted` | stack |
| `services` | ждёт `gitea`, `xrdp`, `sshd`; при локальной модели `llama-server` | процессы живы | — |

Аргументы `docker run` те же, что в `dev1c.ps1` сегодня; они переезжают в
`ops.rs` вместе с комментариями, почему каждый нужен.

### Проверки (`check`)

Факты, не коды возврата: RDP-порт принимает соединение; Gitea отвечает по
HTTP; в настройках Zed у `dev1` стоит нужная модель и провайдер; `nc` есть в
образе; sshd слушает порт туннеля и пускает `dev` (проверка `ssh -N` с паролем
не автоматизируется, проверяется баннер). Про 1С сервер не проверяет ничего —
нечего.

Итоговый экран: адреса рабочих мест, Gitea, модели, порт SSH, и фраза для
разработчика: «на машине с 1С запустите `1c-connect`, адрес сервера такой-то».

## `1c-connect`

### Параметры

```toml
# Подключение машины с 1С к среде разработки. Лежит рядом с 1c-connect.exe.
[host]
server = "192.168.1.10:3393"   # адрес среды и её SSH-порт: печатает dev1c-setup
workstation = "dev1"           # ваш логин в среде: dev1, dev2 или dev3

base_path = "C:\\Bases\\Buh"   # путь к файловой базе или сервер\база
db_user = "Администратор"      # пользователь базы для конфигуратора и сервиса
db_password = ""
base_url = "http://localhost/Buh/hs/mcp-1c"   # адрес опубликованной базы здесь
# dump = "C:\\Bases\\Buh-src"  # выгрузка конфигурации: включает поиск по коду
```

Из `workstation` выводятся порты: `dev1` → 7771 (mcp-1c), 7781 (vrunner-mcp,
этап 2) и 7791 (веб-клиент базы); `dev2` → 7772/7782/7792; `dev3` →
7773/7783/7793. Из `base_url` — порт веб-сервера и имя публикации.

### Команды

```
1c-connect                  окно: поля, «Подключиться», состояние, «Отключиться»
1c-connect status
1c-connect install          расширение в базу
1c-connect uninstall        снять расширение из базы
1c-connect connect          туннель плюс мост; держит, пока не закрыли
1c-connect check
```

У всех `--dry-run`.

### Операции

| id | делает | состояние |
|---|---|---|
| `host.env` | есть `1cv8.exe` и его версия, `mcp-1c.exe` в комплекте той же версии, что ждёт образ; сервер из toml отвечает на SSH-порту | всегда |
| `host.extension` | `mcp-1c.exe --install <base_path> --db-user --db-password`; `uninstall` → `1cv8 DESIGNER /DeleteCfg -Extension MCP_HTTPService` | `base_url/version` отвечает; публикации нет → `Blocked` с текстом, где в конфигураторе нажать (публикацию программа не делает и не снимает) |
| `host.tunnel` | встроенный SSH-клиент (`russh`): подключается к серверу под `dev` с паролем из toml, сверяет отпечаток хоста с `known_hosts` комплекта (первый раз запоминает), запрашивает `tcpip-forward` на `777N`; при обрыве переподключается с нарастающей задержкой | подключён, «работает с 12:40»; отказ в пробросе → «порт 7771 уже занят: у кого-то ещё поднят туннель `dev1`» |
| `host.bridge` | на каждый входящий канал проброса запускает `mcp-1c.exe --base <base_url> --user --password [--dump]` и соединяет его stdio с каналом; локального порта на хосте нет | число открытых каналов |
| `host.web` | второй проброс в той же SSH-сессии: `779N` → веб-сервер этой машины (порт из `base_url`), обычный TCP. В контейнере Firefox открывает `http://localhost:779N/<публикация>/` — веб-клиент 1С той же базы, чтобы смотреть правки, не выходя из RDP-сессии | проброс принят |

`connect` = `host.tunnel`, который сам раздаёт каналы `host.bridge`, и ждёт.
Закрыл окно или консоль — ничего не осталось: ни службы, ни автозапуска, ни
записей в системе, ни слушающих портов. Это требование «на хосте ничего
лишнего». Пароль `dev` лежит в toml на флешке, как и пароль базы.

`uninstall` снимает расширение и удаляет `known_hosts` из комплекта.

Проверить до начала работ: `russh` договаривается по алгоритмам с OpenSSH из
Debian 13 в нашем контейнере (ключ хоста ed25519, `PasswordAuthentication`).
Это первый шаг этапа 3, до остального кода `1c-connect`.

### Проверки

`base_url/version` отвечает версией расширения; SSH-соединение установлено,
проброс принят сервером; `mcp-1c` запускается и отвечает на `initialize`
(проверяется локально, без сети: процесс со stdio в трубу).

## Диагностика: `check` у каждой программы

Чтобы не утонуть в диагностике, у обеих программ `check` устроен одинаково и
является первым ответом на любое «не работает»:

- Пронумерованный список фактов, каждый с результатом и, при провале, с тем,
  что делать и на какой стороне: «6. Туннель: sshd на сервере не пустил
  `dev` — проверьте адрес и порт в `1c-connect.toml`; `dev1c-setup check` на
  сервере покажет, слушает ли он».
- Порядок от основания к вершине: окружение → комплект → программа/контейнер →
  сеть → 1С. Первый провал объясняет последующие, так и печатается.
- Отчёт пишется в файл в комплекте (`last-check.txt`: версия программы,
  версии образа и `mcp-1c`, toml без паролей, список фактов, хвост журнала).
  Разработчик присылает файл, а не описание. Окно показывает тот же список и
  кнопку «Сохранить отчёт».
- `check` ничего не меняет и не спрашивает; его можно гонять сколько угодно.

Разделение сторон явное: `1c-connect check` отвечает за машину с 1С и туннель
до сервера, `dev1c-setup check` — за контейнер и за то, виден ли порт
рабочего места внутри (`nc -z localhost 777N` в контейнере: «туннель `dev1`
поднят / не поднят»). Вместе два отчёта покрывают цепочку целиком.

## Что меняется в образе (делается первым, отдельным коммитом)

- `mcp-1c` из образа убирается; `MCP_1C_*` из entrypoint, скриптов и `.env`
  тоже.
- В настройках Zed два сервера с `nc`: `1c` → `localhost:777N`, `vrunner` →
  `localhost:778N`; `N` подставляет entrypoint по имени пользователя при
  раскладке настроек в домашний каталог (как сейчас подставляет модель).
- `sshd`: `PermitListen` на девять портов для `dev` (777N, 778N, 779N); чужой
  порт отказывается сразу, с понятной ошибкой у клиента.
- Известное ограничение пилота: порты на loopback видны всем пользователям
  контейнера, так что `dev2` технически может подключиться к `localhost:7771`
  и работать с базой `dev1` под его учёткой, зашитой в `1c-connect` на той
  стороне. Размен осознанный, в одном ряду с общей учёткой `dev`. Путь
  апгрейда без смены схемы: проброс в unix-сокет в каталоге пользователя
  (`-R /run/dev1c/dev1/1c.sock`, `StreamLocalBindUnmask 0117`, каталог
  `0770` группы `dev1`) и `nc -U` в настройках Zed; `russh` это умеет.
- `pack` кладёт в `1c-connect/` Windows-бинарь и `.cfe` версии из Dockerfile,
  как сейчас в `host/`.
- CI: вместо shell-проверок `build.yml` — `dev1c-setup install --dry-run`,
  настоящий `install` с заглушкой модели, `check`.

Цена для разработчика: туннель упал → `nc` завершился → Zed покажет «сервер
недоступен»; после `connect` сервер перезапускается кнопкой в Zed.

## Код

`setup/` — Cargo workspace: `common`, `dev1c-setup`, `1c-connect`. Свои
модули: `ops.rs` сервера; `ops_host.rs`, `tunnel.rs` (подключение, проверка
отпечатка, `tcpip-forward`, переподключение; порядка 150–200 строк) и
`bridge.rs` (процесс со stdio, копирование в канал и обратно, порядка 60
строк) у `1c-connect`. Зависимости: `clap`, `serde`, `toml`, `anyhow`,
`sha2`, `reqwest` для проверок HTTP, `russh` с `tokio` у `1c-connect`, `tauri`
опционально.

CI собирает три бинаря (`dev1c-setup` под Windows и Linux, `1c-connect` под
Windows) рядом с образом; `pack` раскладывает два комплекта.

## Проверки кода

`cargo test` без Docker: разбор toml и вывод переменных контейнера; порты по
рабочему месту; `bridge` на эхо-процессе через локальный сокет; состояния и
план операций. Серверные операции — в CI после сборки образа. Хостовые — на
этой машине с Бухгалтерией, в CI платформы нет.

## Локальная модель: по спеке `volt-llama`

Добавлено 2026-10-16. Как служба модели ставится и сверяется, решено в
соседнем проекте: `e:\zeroclaw\_local\spec-volt-llama.md` (замеры на 3060 Ti,
Qwen3.5-4B). `dev1c-setup` обязан уметь то же самое; правила оттуда, которые
здесь действуют дословно:

- **Окно выбирает `llama.cpp`, не мы.** `-c` не задаётся; `--fit on`,
  `--fit-ctx 65536` как нижняя граница, `--fit-target 1024` МиБ (2048, если на
  карте рабочий стол). Подбор меньше `--fit-ctx` — неудача установки, не
  оговорка. Нынешний entrypoint образа задаёт `--ctx-size 196608` руками —
  это именно та раскладка, которая на замерах даёт 4 ток/с; его надо
  переписать на `--fit`.
- **Три слота с общим кэшем:** `--parallel 3 --kv-unified`, `--cache-ram` =
  меньшее из 8192 и половины свободного ОЗУ хоста, никогда `-1` и не `0`.
  Остальные ключи по таблице спеки (`-t 3 -b 2048 -ub 512 --flash-attn on
  -ctk q8_0 -ctv q8_0 --ctx-checkpoints 32 --jinja --reasoning-budget 0`,
  сэмплирование `--temp 0.7 --top-k 40 --top-p 0.95 --min-p 0.3`).
- **Установщик измеряет и говорит, не крутит хост.** До запуска: `nvidia-smi`
  (карта, память, драйвер), проверка проброса `docker run --rm --gpus all
  <образ> nvidia-smi` (на Windows это и есть настоящая проверка), ОЗУ хоста.
  После запуска: `/props` → реальное окно; один длинный запрос →
  `timings.prompt_per_second` → таймаут расчётом, не на глаз; повторный
  `nvidia-smi` — заняли почти всё, предупредить про вытеснение.
- **Три числа обязаны сойтись:** окно сервера из `/props`, окно провайдера в
  настройках Zed равно ему, бюджет одного агента × слоты + генерация ≤ окно.
  Не сходится — `check` говорит числом.

**Решено 2026-10-16: ллама не в образе, а соседним контейнером.** Из
образа `dev1c` уходят CUDA и llama.cpp (около 630 МБ и единственная причина
давать контейнеру среды видеокарту). Модель поднимает `dev1c-setup`
операцией `llama` из нашего тонкого образа `dev1c-llama` (`Dockerfile.llama`,
уже в ghcr) с томом `dev1c-models`; `docker save` кладёт оба образа в один
tar, комплект остаётся одним файлом. Причины: одна карта — один сервер на
оба проекта (на этом стенде `volt-llama` уже обслуживает тот же том);
llama.cpp меняется еженедельно, среда — нет; установщик модели пишется один
раз по спеке `volt-llama`. Для Zed модель всегда «удалённая»: провайдер
`custom`, адрес соседнего контейнера; ветка `llama.cpp` в настройках и
`LLAMA_ENABLED` в entrypoint упраздняются.

**Кто управляет окном.** Проверено по документации и по бинарю Zed в
образе: Zed сам сжимает длинные треды сводкой прежних сообщений
(`agent.auto_compact`: `enabled`, `threshold`), когда тред подходит к
порогу. Это и есть «редкое и крупное» сокращение истории, которого требует
спека лламы (любая правка начала истории — полный пересчёт кэша, поэтому
резать надо редко и помногу). Разделение обязанностей:

| Кто | Что решает |
|---|---|
| `llama.cpp` (`--fit`) | ёмкость: слои на карте, пул, итоговое окно |
| Zed (`auto_compact`) | содержание: когда и как свернуть историю |
| `dev1c-setup` | чтобы числа у них сошлись |

**Синхронизация — работа установщика, и именно она обычно ломается.** После
запуска `llama` установщик читает `/props` и получает реальное окно `W`;
ответ `G = 8192`; `A = [model] agents` (умолчание 1, см. «Хватит ли окна»).
Отсюда в настройки Zed каждого рабочего места
(`openai_compatible.custom.available_models[0]`): `max_output_tokens = G`,
`max_tokens = W / A − G − запас` (запас на приблизительный счёт токенов у
Zed), `auto_compact.threshold` ниже `max_tokens`. Значения идут тем же путём, что имя модели: переменные
контейнера → заготовки в `settings.json` → entrypoint. `check` сверяет три
числа и говорит ими: окно сервера из `/props`, `max_tokens` в Zed, их
произведение со слотами. Таймаут запроса считается из
`timings.prompt_per_second`, не ставится на глаз.

Модель в комплект не кладём: файл лежит в томе `dev1c-models`. Отдельный
план после `1c-connect`.

**Хватит ли окна на кодинг.** Оценка для 5090 (32 ГБ) и Qwen3.6-35B-A3B в
Q4, архитектура взята по Qwen3.5-35B-A3B (сверить по метаданным GGUF): 10
слоёв с KV из 40, 2 KV-головы по 256 → около 11 КБ на токен в Q8_0; веса
≈ 21 ГБ; под KV остаётся ≈ 9 ГБ ≈ 800 тысяч токенов. То есть на 5090 окно
упирается в родной предел модели (262 144), а не в память, и `--fit` отдаст
его целиком.

Сколько нужно агенту: русский BSL токенизируется по 2–3 символа на токен,
модуль в 100 КБ — около 40 000 токенов, плюс ≈ 15 000 фиксированных (скиллы
17 КБ ≈ 8 тысяч токенов, AGENTS.md, описания инструментов). Жёсткое деление
окна на три слота дало бы 262 144 / 3 − 8192 ≈ 79 000, рабочих ≈ 64 000 —
для 1С мало: один большой модуль и немного выдачи `rg`. Поэтому:

- **Окно на три не делим.** С `--kv-unified` простаивающий слот отдаёт пул,
  и занятый агент берёт окно целиком; деление — страховка от вытеснения,
  когда все трое работают разом, а вытеснение стоит пересчёта (на 5090 ≈
  полминуты на 160k), не отказа. Бюджет агента `max_tokens = W − 8192 −
  запас`; параметр `[model] agents` (умолчание 1) делит, только если его
  включили явно. Цель — не меньше 128 000 на агента, лучше 200 000.
- **Резерв — окно больше родного.** Память на 5090 держит около 800 тысяч
  токенов этой модели; Qwen3.6 с YaRN заявляет до миллиона. `--fit-ctx
  524288` с rope-yarn даёт 512k и 170k на агента даже при делении на три.
  Качество на длинных контекстах проверить замером до того, как опираться.
- **Фиксированные расходы** резать: описания скиллов до стиля superpowers
  (пункт STATUS), это 5–6 тысяч токенов в каждом запросе.

Замеры облачного эндпоинта (шлюз над vLLM, Qwen3.6-35B-A3B-AWQ,
2026-10-16, с этой машины): предел **65 536** токенов (vLLM называет его сам
при переполнении); промпт 53 тысячи токенов — первый токен через 2,4 с,
префил ≈ 22 000 ток/с вместе с сетью; генерация 140–160 ток/с. У vLLM нет
деления окна на слоты, поэтому нынешние `max_tokens = 55 296` и
`max_output_tokens = 8192` в настройках Zed верны и для трёх агентов разом;
холодный ход на полном бюджете ≈ 10 с. Оговорка: пресет шлюза
`thinking_general` сначала думает, и размышление расходует выходные токены —
8192 на ответ надо считать вместе с ним, а лучше выключить размышление для
агента (`reasoning-budget 0`, как и в спеке лламы).

Замечание про порты туннеля: агент (модель) порта не выбирает и не видит —
`nc localhost 777N` запускает Zed из настроек домашнего каталога того
пользователя, под которым идёт сессия. Перепутать рабочее место агент не
может; перепутать может только человек, вписав чужой `workstation` в
`1c-connect.toml`, и тогда sshd откажет ему в занятом порту.

## Трей у `1c-connect`

Добавлено 2026-10-16. `connect` работает часами, окно ради него держать
незачем: программа сворачивается в системный трей. Значок показывает
состояние (подключён / не подключён — вторая версия серая), подсказка —
«dev1 → 192.168.1.10:3393: подключён 12 мин» или причину, почему нет
(время — от момента подключения; часов без зависимостей у программы нет). Меню:
«Подключить», «Отключить», «Проверить», «Открыть веб-клиент»
(`http://localhost/<публикация>/` локально), «Выход». Двойной щелчок —
окно. Tauri 2 даёт трей штатно (`TrayIconBuilder`); закрытие окна не
останавливает туннель, останавливает только «Выход».

Значок — значок Zed (из образа, `/opt/zed.app/share/icons`) со
значком-статусом в углу: подключён / нет. Решение заказчика (2026-10-16):
для разработчиков Zed в новинку, и связь «значок Zed в трее = моя связь со
средой» помогает привыкнуть. Оговорка, не про UX: значок Zed — товарный
знак Zed Industries, лицензия кода его не покрывает. Для пилота в закрытом
контуре это риск нулевой; для поставки наружу — спросить разрешения или
заменить на марку OktaPlus (`config/brand/oktaplus-mark-light.svg`).
`tauri icon` делает все размеры из одного PNG.

## Машины разработчиков — Windows

Зафиксировано 2026-10-16. `1c-connect` собирается только под Windows;
Linux-сборка существует ради живого теста туннеля в CI. Всё в комплекте
разработчика — Windows-сборки: `mcp-1c`, переносимые OneScript и
vanessa-runner (этап 5), MinGit.

Отсюда упрощение, которое стоит взять: самый неудобный шаг для разработчика
сегодня — публикация базы на веб-сервере (Apache или IIS, права,
конфигуратор от администратора). На Windows платформа умеет поднять
HTTP-сервисы из клиента без веб-сервера: `1cv8.exe ENTERPRISE /F <база>
/HTTPPort 8080` (ключ недокументированный, только Windows; так его
использует и сам mcp-1c при разработке). Режим `[host] publication`:

- `"httpport"` (умолчание для пилота) — `1c-connect connect` сам запускает
  сеанс Предприятия с `/HTTPPort`, `base_url` выводится
  (`http://localhost:<порт>/hs/mcp-1c`), шаг с публикацией исчезает. Цена:
  открытая сессия Предприятия на время подключения (лицензия — та же, в
  которой разработчик и так работает) и недокументированность ключа;
- `"webserver"` — как сейчас: опубликованная база, `base_url` задаётся.

`check` в режиме `httpport` не требует веб-сервера; факт «веб-сервер»
заменяется на «сеанс с /HTTPPort отвечает».

## Путь файлов: git, не туннель

Добавлено 2026-10-16. Выгрузку конфигурации делает платформа (`1cv8
DESIGNER /DumpConfigToFiles`), зовёт её vanessa-runner из комплекта
`1c-connect` на машине разработчика (этап 5, порт 778N). Файлы ложатся в
каталог проекта на той машине. В контейнер они едут **через Gitea**, а не
через туннель: Gitea опубликован на порту 3391 сервера и виден с машины
разработчика напрямую; на ЕРП выгрузка — сотни тысяч файлов, и проект в
контейнере обязан лежать в домашнем каталоге, не на проброшенном диске.

Круг работы:

1. машина с 1С — `vrunner` выгружает в каталог проекта, `git push` в Gitea;
2. контейнер — агент `git pull` в `~/proj`, правит, коммитит, `git push`;
3. машина с 1С — `git pull`, `vrunner` грузит в базу инкрементально; список
   изменённых файлов для `-listFile` даёт `git diff` между загруженным и
   текущим коммитом.

Шаги 1 и 3 агент запускает через `vrunner-mcp`; `git` на машине
разработчика приезжает в комплекте переносимым (MinGit), как и OneScript.
Учётка Gitea разработчика — та же, что рабочее место (`dev1`/`dev1`).

## Окна и трей (этап 4)

Добавлено 2026-10-16. Обе программы — те же бинари: без аргументов окно,
с аргументами командная строка (как `volt-setup`). Окно — тонкая оболочка
над теми же операциями и проверками: логики развёртывания в нём нет, оно
зовёт команды и рисует события.

**Сборка.** Tauri 2, страница без сборщика (`ui/index.html`, `app.css`,
`app.js`, `withGlobalTauri`), `tauri.conf.json` и `capabilities/default.json`
в корне каждого пакета, `build.rs` зовёт `tauri_build` только при
`feature = "gui"`. `gui` входит в `default`: двойной щелчок по файлу из
комплекта обязан открыть окно. В CI окно собирается только под Windows;
Linux-сборки (`dev1c-setup` для сервера, `1c-connect` для живого теста
туннеля) идут с `--no-default-features`, чтобы не ставить на раннер
webkit2gtk. Релизная сборка — `windows_subsystem = "windows"`; для команд
консоль возвращается через `AttachConsole` (копия `setup_console` из
`volt-setup`), в отладочной сборке консоль остаётся всегда.

**Значки.** `1c-connect` — значок Zed (`crates/zed/resources/app-icon.png`
из репозитория Zed, см. оговорку в разделе «Трей»), `dev1c-setup` — марка
OktaPlus, растрированная из `config/brand/oktaplus-mark-light.svg`. В
репозитории лежат `icons/icon.png` (512) и `icons/icon.ico`; `tauri icon`
не нужен, ICO делается Pillow один раз. Значок трея со статусом не
рисуется заранее: программа берёт тот же PNG и дорисовывает кружок в углу
(зелёный — подключён, серый и обесцвеченный значок — нет) в памяти.

**`1c-connect`: сеанс.** Общая часть окна и команды `connect` — модуль
`session`: `State` (`Off`, `Connecting`, `Up{since}`, `Retrying(why)`,
`Failed(why)`) переходит по событиям `tunnel::run` (это чистая функция с
тестом), `start(cfg, kit, log, on_state)` поднимает поток со своим
`tokio`-рантаймом, `Session::stop` опускает туннель и ждёт поток. Мост
(`mcp-1c` на 777N, веб-сервер на 779N) переезжает из `main.rs` в
`session::serve`. Команда `connect` = `start` + ожидание Ctrl+C или
завершения сеанса + `stop`; окно хранит `Session` в состоянии приложения.
Предупреждения моста («mcp-1c завершился…») идут только в журнал и
состояние не меняют.

**Вид.** Решение заказчика (2026-10-16): Windows 11 / Fluent — Segoe UI,
светлая тема, акцентные синие кнопки, карточки с мягкой тенью, шкала
отступов 4/8/12/16/24; компоновка «шапка-статус + вкладки», ничего не
прокручивается, кроме содержимого вкладки. Один `app.css` на оба окна
(копия в каждом пакете).

**`1c-connect`: флайаут.** Это хелпер, живущий в трее, и окно у него — как
быстрые настройки Windows: без рамки, 440×680, всплывает у правого нижнего
угла рабочей области (над панелью задач, отступ 12 px), прячется, когда
теряет фокус или его закрывают; левый щелчок по значку показывает его
снова (щелчок по открытому — закрывает: потеря фокуса уже спрятала окно
мгновение назад, и программа это помнит). В панели задач его нет. Шапка —
полоса со значком, именем и ✕, под ними карточка состояния: индикатор,
одно состояние («Не настроено» / «Не подключён» / «Подключаюсь…» /
«Подключён · N мин» / «Переподключаюсь»), одна строка причины или маршрута
(«адрес · рабочее место» или «mcp-1c → порт, веб-клиент → порт») и один
переключатель туннеля — заперт, пока адрес среды не задан. Отдельных кнопок
«Подключить»/«Отключить» и предупреждений нет: противоречий между ними не
бывает по построению. Начало сеанса, отказ и отключение пишутся в журнал.
Вкладки: «Параметры»
(`server`, `workstation`, `password`, `base_path`, `db_user`, `db_password`,
`base_url`, `dump`, «Сохранить» — `Cfg::validate` + `render` в
`1c-connect.toml`), «Расширение» (состояние операций, «Установить», «Снять», «Веб-клиент»),
«Проверка» (факты, пишет `last-check.txt`), «Журнал»; бейджи на вкладках — провалы проверки и
непрочитанные строки журнала. Открывается на «Параметрах», пока адрес не
задан, иначе на «Журнале». Внизу — «Выход»
(опускает туннель). Вопросы окно не задаёт (`AlwaysDefault`).

**`1c-connect`: трей.** Как в разделе «Трей»: значок со статусом, подсказка
«dev1 → адрес, подключён с 12:40» или причина, меню «Подключить»,
«Отключить», «Проверить» (открывает окно и запускает проверку), «Открыть
веб-клиент», «Выход»; левый щелчок — окно. Закрытие окна крестиком —
скрыть, не выйти. Без аргументов программа всегда появляется окном и
значком в трее одновременно.

**`dev1c-setup`: окно.** Обычное окно 1040×800 с той же шапкой-полосой:
имя, индикатор «Среда работает / установлена не полностью / не
установлена», «Проверить» и «Установить» справа. Вкладки: «Операции»
(состояния `Done`/`Missing`/`Drifted`/`Blocked`; «Применить изменения» =
`change`, «Снять контейнер», «Удалить данные…» — подтверждение вводом имени
контейнера в поле рядом), «Параметры» (`[server]` и `[model]`, «Сохранить»
в `dev1c.toml` с комментариями через `render`), «Доступ» (RDP, Gitea,
модель, порт для `1c-connect`), «Проверка», «Журнал».

**События.** Движок отдаёт `Event` в `sink`; окно получает их как
`dev1c:line`/`conn:line` (`kind` = ok/warn/fail/say/cmd) и `…:done`
с текстом ошибки или без. `Output` в окно не идёт — только в `install.log`.
`1c-connect` дополнительно шлёт `conn:state` при каждом переходе сеанса.

**Проверки.** `session::State::next` — таблица переходов тестом;
дорисовка значка — тест на размер и цвет углового пикселя; остальное —
Windows-сборка в CI и запуск руками.

## Сервер инференса (этап 5)

Решения заказчика 2026-10-16: сервер модели ставит `dev1c-setup`, и у него
три формы на выбор в `dev1c.toml` и в окне; код пишется заново по спеке
`volt-llama` (у установщика Вольта подсматриваем команды `nssm`, чтение
`/props`, токен файлом — не копируем).

**Три формы, параметр `[model] serve`.**

| `serve` | что это | модель | адрес для Zed |
|---|---|---|---|
| `"host"` (умолчание) | `llama-server` службой этой машины: Windows — `nssm` из комплекта, Linux — юнит systemd | `file` — полный путь к `.gguf` на диске этой машины, читается на месте | `http://host.docker.internal:<port>/v1` |
| `"docker"` | контейнер `<имя>-llama` рядом со средой из образа `oktaplus/dev1c-llama` (в том же tar комплекта), `--gpus all` | `file` — файл в комплекте, копируется в том `<имя>-models` (монтировать папку хоста — плохая идея, решено) | тот же `host.docker.internal`, порт — третий порт среды (`port + 2`) |
| `"remote"` | чужой OpenAI-совместимый сервер | — | `url`, `key`, `name` как сейчас |

На Linux (движок без Docker Desktop) контейнер среды получает
`--add-host=host.docker.internal:host-gateway`; служба хоста слушает не
петлю, а адрес моста (`docker network inspect bridge`, обычно 172.17.0.1):
он виден контейнерам и самой машине, но не сети. На Windows служба слушает
`127.0.0.1`: замерено 2026-10-16 на этой машине — Docker Desktop 4.95
доставляет `host.docker.internal` до службы на петле хоста (слушатель на
127.0.0.1:1235 ответил контейнеру `dev1c` кодом 200). Один адрес для обеих
форм — один код в entrypoint и одна строка в `check`.

**Хостовая форма.** Каталог `C:\dev1c\llama` (Linux: `/opt/dev1c/llama`):
`llama-server` с библиотеками CUDA из `llama/bin/<ряд ОС>` комплекта,
`nssm.exe` из `llama/nssm.exe` комплекта (чужой `nssm` на машине не
берётся — контур закрытый), токен `dev1c-llama.token` с закрытыми правами
(`icacls` / `chmod 600`), журнал `llama.log` (ротация средствами `nssm`).
Служба `dev1c-llama`, автозапуск, перезапуск при падении, `AppDirectory` —
этот каталог. Параметры запекаются в запись службы; правка `file`, `port`
или `agents` — это расхождение (`Drifted`) и пересоздание службы. Порт
занят чужой программой — `Blocked` до регистрации, не после.

**Командная строка** — по спеке `volt-llama`, без `-c`: `--fit-ctx 65536`
(`[model] fit_ctx`), `--fit-target 1024` (2048, если `nvidia-smi` в покое
показывает занятую карту — рабочий стол), `--parallel 3 --kv-unified`,
`--cache-ram` = меньшее из 8192 и половины свободного ОЗУ (не меньше 1024,
никогда `-1`/`0`), `--ctx-checkpoints 32 -b 2048 -ub 512 --flash-attn on
-ctk q8_0 -ctv q8_0 --jinja --reasoning-budget 0 --temp 0.7 --top-k 40
--top-p 0.95 --min-p 0.3 --metrics --api-key-file <токен> --alias <имя>`,
`--host`/`--port` по форме. Имя модели для Zed — `[model] name`, по умолчанию
имя файла без расширения. Чистая функция `serve_args` с тестом: нет `-c`,
есть `--fit-ctx`, токен путём.

**Измерения и синхронизация** (обе локальные формы, операция
`llama.answers`, выполняется всегда):

1. до запуска — `nvidia-smi` (карта, память, драйвер; нет карты —
   `Blocked`: модель для агентов на процессоре неработоспособна), для
   `docker` ещё `docker run --rm --gpus all <образ> nvidia-smi`;
2. после запуска — `/health` до 5 минут (модель читается с диска), `/props`
   → окно `W` и слоты; `W < fit_ctx` — неудача установки, числом;
3. один длинный запрос (≈1800 токенов, метка в начале, `cache_prompt:
   false`) → `timings.prompt_per_second`; меньше 500 посчитанных токенов —
   не замер;
4. числа для Zed: `G = 8192`, `A = [model] agents` (умолчание 1),
   `max_tokens = W / A − G − 2048`. Сжатие истории Zed делает сам: по
   документации `agent.auto_compact.threshold` — доля от окна модели
   (умолчание `"90%"` от `max_tokens`) или число токенов; нам хватает
   умолчания, установщик его не трогает. Таймаута у Zed нет;
   `prompt_per_second` идёт в отчёт как справка о скорости;
5. результат — в `install.state` (`llama.window`, `llama.prefill`,
   `llama.max_tokens`): контейнер среды получает их переменными
   `CUSTOM_MAX_TOKENS` и `CUSTOM_MAX_OUTPUT_TOKENS` вместе с
   `CUSTOM_API_URL`/`CUSTOM_API_KEY`/`CUSTOM_MODEL`; entrypoint
   подставляет их в заготовки `settings.json` вместо нынешних констант
   55296/8192. Изменились числа — контейнер разошёлся с заданным и
   пересоздаётся (как при смене адреса модели). Поэтому операции модели
   идут в списке **до** операции контейнера.

**Проверки `check`** (к нынешним): «видеокарта» (`nvidia-smi`), «сервер
модели» (`/health`, `/props`: окно, слоты, модель), «три числа»: окно
сервера из `/props` = окно, под которое выставлен `max_tokens` в
`settings.json` рабочих мест, и `max_tokens × A + G ≤ W` — не сходится,
факт провален числом.

**Операции** (`serve = "host"`): `llama.bin` — файлы из комплекта в каталог
(сверка версии `llama-server --version` с комплектом → `Drifted`);
`llama.service` — регистрация и запуск (`Missing`/`Drifted`/`Blocked`);
`llama.answers` — измерения выше. `serve = "docker"`: `llama.image` (из того
же tar), `llama.container`, `llama.answers`. `remote`: ничего. `clean
--stack` снимает службу/контейнер, файлы и модель остаются; `--data`
удаляет каталог `llama` и том моделей.

**Окно.** На вкладке «Параметры» группа «Модель для агентов» — выбор формы
(три переключателя), поля по форме: `host` — путь к `.gguf` на этой машине;
`docker` — файл в комплекте; `remote` — адрес, ключ, имя. Общие: `agents`,
`fit_ctx`, порт для `host`. Операции модели — в общем списке; «Доступ»
показывает адрес сервера модели и имя модели; «Проверка» — три факта выше.

**Комплект.** `pack.sh` докладывает `llama/bin/windows-x64-cuda13`
(`llama-b11606-bin-win-cuda-13.4-x64.zip` + `cudart-llama-bin-win-cuda-13.4-x64.zip`)
или `llama/bin/linux-x64-cuda13` под ОС комплекта и `llama/nssm.exe`
(nssm 2.24-101 из репозитория, `setup/dev1c-setup/vendor`, с приколоченным
SHA-256 — nssm.cc часто недоступен, только для Windows); сборка `b11606` — та
же, что у образа `dev1c-llama`. Модель в комплект не кладётся.

**Образ.** После того как хостовая форма проверена, из образа `dev1c`
уходят CUDA и `llama.cpp` (база — `debian:13` вместо `dev1c-llama`),
`LLAMA_ENABLED` и ветка `llama.cpp` в `settings.json`; для Zed модель всегда
провайдер `custom`. Это отдельный коммит в конце этапа: пока он не сделан,
`LLAMA_ENABLED=0` держит внутреннюю лламу выключенной, и всё остальное
работает.

**Этапы внутри:** 5.1 `cfg` + чистые части `llama.rs` (`serve_args`,
расчёт чисел, разбор `/props`) с тестами; 5.2 хостовая форма (операции,
`nssm`/systemd, измерения, переменные контейнера, entrypoint); 5.3
контейнерная форма; 5.4 окно; 5.5 `pack.sh`; 5.6 образ без CUDA. Проверка:
на этой машине (3060 Ti, 8 ГБ, Qwen3.5-4B — тот же файл, что у `volt-llama`),
в CI — сборка и `check` без карты (факты про модель — `Blocked`, не провал
установки с `serve = "remote"`).

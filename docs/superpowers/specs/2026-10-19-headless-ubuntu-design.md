# Установка на сервер Ubuntu без графики

Дата: 2026-10-19. Новые вводные от клиента, где разворачивается пилот.
Дополняет `2026-10-16-setup-binaries-design.md` (комплекты и операции) и
`2026-10-19-dev1c-setup-gpui-design.md` (окно; на этом сервере его нет).

## Зачем

Сервер клиента — Ubuntu 24.04.4 LTS, ядро 6.8, x86-64, **без графики**.
Разворачивает **администратор клиента по нашей инструкции**, не мы: заходит
по SSH, кладёт комплект, запускает один файл. Окна на той машине не будет, и
гигабайты по нашему соединению мы не возим — их кладёт он сам тем, чем
привык.

Проверить что-либо на их стороне заранее возможности нет (решение заказчика
2026-10-19: «надо делать универсально, чтобы работало везде»). Значит всё,
что раньше звучало как «проверьте у себя», должна проверять сама программа
и говорить, что делать.

## Что известно о машине

| Что | Значение | Следствие для нас |
|---|---|---|
| ОС | Ubuntu 24.04.4 LTS, ядро 6.8, x86-64 | Linux-сборка собирается уже сейчас, `--no-default-features` |
| Docker | Engine 20.10.24 (апрель 2023), API 1.41, containerd 1.7.27, runc 1.2.6 | Флаги запуска он понимает; риск — формат архива образа, см. «Старый Docker» |
| Видеокарта | RTX 5090 (Blackwell, sm_120) | Наш образ сервера модели собран с `CMAKE_CUDA_ARCHITECTURES` c `120` — карта поддержана |
| Разделение карты | vGPU между виртуальными машинами, на пилот дают 100 % | Замер при установке верен; урезали долю — модель не загрузится, и проверка это скажет |
| Права | Неизвестно: root или пользователь в группе `docker` | Программа определяет сама и говорит, чего не хватает |
| `nvidia-container-toolkit` | Неизвестно | Определяем сами; поставить его из интернета нельзя, см. ниже |
| Сеть | **Закрытый контур, интернета нет** (заказчик, 2026-10-19) | Любая подсказка вида «`sudo apt install …`» — тупик: ставить нечего и неоткуда |

## Цели

- Администратор клиента ставит среду с терминала, по инструкции из комплекта,
  не задавая нам вопросов.
- Любая преграда называется словами и имеет готовую к вставке команду,
  работающую **без интернета**: нет прав на `docker`, нет
  `nvidia-container-toolkit`, нет архива образа, нет файла модели, не
  сходится сумма.
- Сервер модели на Linux по умолчанию поднимается **контейнером**
  (`serve = "docker"`): так предпочли их администраторы, расход тот же.
- Архив образа грузится и старым Docker 20.10, и свежим. Гарантия на нашей
  стороне, проверка — в нашей сборке.

## Не-цели

- Окна на сервере нет. Linux-сборка остаётся CLI.
- Окно со своей машины через SSH — вторая очередь, не эта работа. Механику
  под неё не закрываем: исполнитель команд остаётся единственной точкой, в
  которую она потом встанет.
- Перенос гигабайтов нашими руками. `scp`, `rsync`, WinSCP делают это лучше.
- Установка самого Docker и драйвера видеокарты. Это работа администратора;
  наше дело — сказать, чего не хватает.

## Анти-цели

- Инструкция, которая расходится с программой. Всё, что в ней написано,
  программа должна уметь проверить и сказать сама; инструкция — короткий
  путь, а не второй источник истины.
- «Шагов: 0» без объяснения. Любой отказ называет причину и следующий шаг.
- Своя проверка окружения вместо операций. Операции уже умеют отвечать
  `Blocked(почему)` — новые преграды живут там же, а не в отдельном
  «предполётном» коде.

## Решения

### Образ сервера модели нужно доделать

Сегодня `Dockerfile.llama` заканчивается `FROM scratch` и только переносит
собранные файлы наружу — основной `Dockerfile` копирует из него `/opt/llama`.
Ни libc, ни точки входа, ни переменных NVIDIA в нём нет, а форма `docker`
пытается запустить в этом образе `llama-server`. То есть форма, которую
предпочли администраторы клиента, **сегодня физически не работает**, и CI её
никогда не проверял: там гоняется только `serve = "remote"`.

Решение заказчика 2026-10-19: доделать образ. В `Dockerfile.llama` появляется
рабочий слой — база с libc, точка входа, `NVIDIA_VISIBLE_DEVICES` и
`NVIDIA_DRIVER_CAPABILITIES`; образ пересобирается своим рабочим потоком
(около 40 минут), тег закрепляется, и CI впервые проверяет форму `docker`
целиком: загрузить архив, поднять контейнер модели, дождаться ответа.

Без этого шага всё остальное в этой спеке бессмысленно: ставить будет нечего.

### Закрытый контур: ничего не ставится из сети

Сервер в интернет не выходит. Значит ни одна подсказка не может звучать как
«поставьте пакет» — ставить неоткуда. Отсюда:

- `nvidia-container-toolkit` едет **в комплекте** пакетами `.deb` (сам
  toolkit, `-base`, `libnvidia-container1`, `libnvidia-container-tools`;
  вместе единицы мегабайт, лицензия Apache 2.0, сборка от NVIDIA одна на
  все дистрибутивы). Подсказка программы — установка из комплекта:
  `sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker`.
  Суммы этих файлов попадают в общий `checksums.txt` комплекта.
- Драйвер видеокарты в комплект не едет: он привязан к ядру и к политике
  клиента. Нет драйвера — это требование к администратору, сказанное до
  начала, а не команда.
- Docker в комплект не едет: на этом сервере он есть.

### Форма модели на Linux — контейнер

`serve = "docker"` становится умолчанием в `dev1c.example.toml` для Linux.
Форма `host` на Linux (systemd) остаётся в коде, но в комплект для этого
сервера не едет: ряд `llama/bin` под Linux в комплект не кладём, модель
приходит в образе `dev1c-llama` из того же архива.

Умолчание зависит от того, под какую ОС собран комплект, а не от того, где
запущена программа: `pack.sh` кладёт в кит свой `dev1c.toml`.

### Старый Docker: архив образа

`docker load` на 20.10 не примет архив с OCI-манифестом и вложениями
(provenance, SBOM), которые современный BuildKit добавляет по умолчанию.
Поэтому образ собирается одной платформой `linux/amd64`, без вложений, и
выгружается классическим `docker save`.

Проверка — у нас, в сборке комплекта: в архиве обязан быть `manifest.json` в
корне, и ни один манифест в нём не должен быть вложением (`attestation`).
Правило «не должно быть `index.json`» было бы неверным: свежий `docker save`
кладёт его всегда, рядом с `manifest.json`, и старый Docker его просто не
смотрит. Не так — сборка падает у нас, а не у клиента.

### Преграды, которые программа называет сама

Каждая — состояние операции или факт проверки, с готовой командой:

| Преграда | Что говорит программа |
|---|---|
| `docker` отвечает «permission denied» | «Текущему пользователю нельзя говорить с Docker. `sudo usermod -aG docker $USER`, затем перезайти; или запускать установку через `sudo`» |
| `docker` не отвечает вовсе | «Docker не отвечает: `sudo systemctl status docker`» |
| Контейнер не видит карту | «Docker не отдаёт видеокарту контейнеру: нужен nvidia-container-toolkit. Он лежит в комплекте: `sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker`» |
| Нет `nvidia-smi` | «Драйвер видеокарты не установлен» |
| Нет архива образа | «Положите `dev1c-image.tar.gz` в каталог комплекта: `scp dev1c-image.tar.gz <user>@<сервер>:<каталог>/`» |
| Нет файла модели | То же про `.gguf`, с именем из `dev1c.toml` |
| Сумма не сошлась | Уже есть: сверка перед установкой называет файлы |

Проверка видеокарты **в контейнере**, а не только на хосте: `nvidia-smi` на
машине может отвечать, а `docker run --gpus all` падать — это и есть
отсутствующий toolkit, и именно он ломает форму `docker`.

### Права: установка от root или от пользователя в группе docker

Контейнерная форма тоже идёт через `ensure_token`, а он закрывает каталог
`/opt/dev1c/llama` на `root:root`. Пользователь из группы `docker` умрёт там
на `chown`, а установка через `sudo` оставит токен, который потом не прочитать
обычному пользователю при проверке.

Решение: **секрет сервера модели живёт в комплекте, а не в `/opt`** —
рядом с `dev1c.toml`, с правами `600` на владельца, который ставит. Каталог
`/opt/dev1c/llama` на Linux остаётся только у формы `host` (службы systemd),
которой в этом комплекте нет. Оба пути — от root и от пользователя в группе
`docker` — должны проходить установку целиком; это проверяется в CI.

### Модель кладут до установки

Сервер среды собирается по числам, которые даёт замер модели, поэтому без
файла модели установка останавливается на первом же шаге, а не ставит
половину. Это записано в инструкции первым пунктом: сначала оба файла в
каталог комплекта, потом команда.

### Инструкция в комплекте

Файл `УСТАНОВКА.md` рядом с программой, на русском, страница: что положить,
какую команду запустить, что будет видно, куда смотреть при отказе. Все
команды — готовые к вставке. Инструкция ссылается на программу («дальше
`./dev1c-setup install` скажет сам»), а не повторяет её логику.

### Без вопросов в терминале

Установка по SSH идёт без подтверждений: там, где CLI сегодня спрашивает,
при отсутствии TTY ответом считается значение по умолчанию (как делает
`--yes`). Опасное — удаление данных — наоборот: без TTY отказывается и
просит явный ключ.

## Что остаётся исполнителю

- Разбиение на задачи и порядок — планом (`writing-plans`).
- Linux-комплект собирается отдельным (`pack.sh --llama none`, без `.exe`),
  и `dev1c.toml` в нём получается командой `dev1c-setup example` с выбранной
  формой — так умолчание не ломает равенство `EXAMPLE == Cfg::default()` и
  круговые тесты в `cfg.rs`.
- Точные тексты сообщений: в таблице выше смысл, слова подбираются на месте
  по правилу «причина и следующий шаг».
- Как именно проверять карту в контейнере (пробный `docker run --rm --gpus
  all <образ> nvidia-smi` против разбора `docker info`) — выбрать подешевле
  и объяснить выбор в коде.
- Живая проверка всего пути на чистой Ubuntu 24.04 с Docker 20.10: это и
  есть приёмка этой работы.

# Пара B: разработчик принимает, машина с базой звонит

План. Проектирование, кода здесь нет. Основание — `docs/superpowers/specs/connection-combinations.md` (пять сочетаний, две законные пары) и `docs/superpowers/specs/2026-11-01-protocol-design.md` (раздел «MCP», раздел «Что переезжает с нынешнего моста дословно»).

## 1. Где граница

**Мост не разрезается вовсе.** `bridge::pipe_jsonrpc` берёт `stream: S where S: AsyncRead + AsyncWrite + Unpin + Send + 'static` и ничего о транспорте не знает; `session::Serve::dispatch` — тоже. Сегодня в этот параметр приходит `TcpStream` от `listen::run` или канал russh от `tunnel::run`; завтра — двунаправленный поток iroh. Это ровно то, что спека называет «смена трубы под готовым механизмом».

Отрезается и подменяется **одно место на каждой стороне**, и ни одной строки правил моста.

**Сторона с базой** (принимает поток канала, поднимает ребёнка):
- `channel::accept_all` отдаёт разговору `Control` — уже готовый двунаправленный поток плюс доказанный ключ той стороны. Первый кадр потока сегодня обязан быть `Msg::Hello`; добавляется второй законный первый кадр — `Msg::McpOpen { base_id, kind, client }`.
- `peer::answering` (единственный читатель первого кадра) расходится на два: `Hello` → `enroll::accept_side`, как сегодня; `McpOpen` → допуск, ответ `McpOk` и `Serve::serve(kind, stream)`.
- `Serve::dispatch(port: u16, stream)` **перестаёт ключеваться портом** и становится `Serve::serve(kind: ops_host::McpServer, stream)`. Порт — свойство локального слушателя, и жить ему положено в `listen::accept_for`, который один его и знает.

**Сторона с агентами** (тонкая, по спеке): `listen::accept_for` вместо `serve.dispatch(port, stream)` открывает поток в живом канале (`Channel::call`), пишет туда `McpOpen` кадром, ждёт `McpOk` и дальше — `tokio::io::copy_bidirectional`. Правил моста она не повторяет ни одним выражением.

**Почему заголовок едет в `wire::Msg`, а не в своём перечислении.** `Frame` без состояния и годен для любого сообщения, но отдельный `enum Open` дал бы два словаря сообщений, два `KNOWN` и два правила «незнакомое сообщение — это действие, и молча глотать его нельзя». Машинерия «кадр не в свою очередь» уже есть (`enroll::out_of_turn`, `code::UNKNOWN_MESSAGE`), и `channel::hold`/`enroll::heard` отказывают `McpOpen` на управляющем потоке тем же путём, которым сегодня отказывают `enroll` вместо `hello`. Один словарь, один `KNOWN` (становится 12), одно кадрирование.

Новые сообщения: `Msg::McpOpen { base_id, kind: McpServer, client: Option<SaysName> }`, `Msg::McpOk`. Номер `PROTO` не растёт: сборка наружу не выпускалась, ALPN взят без версии нарочно, а сторона без этих сообщений получает отказ словами — та же развилка, что при добавлении `why` 10.11.

## 2. Как это выражается типами

### 2.1. Сочетание — одно значение, и шестого нет

```rust
// cfg.rs, рядом с shown_fields
pub enum Combo { Alone, AcceptBaseHere, AcceptBaseThere, DialBaseHere, DialBaseThere }
impl Combo {
    pub fn of(c: &Connection) -> Combo;        // ЕДИНСТВЕННАЯ дорога от mode/role/base_here
    pub fn side(self) -> Option<wire::Side>;   // None у Alone: той стороны нет вовсе
}
```

Сегодня на вопрос «что это за карточка» отвечают порознь: `Connection::base_is_here`, `link::waits_for_incoming`, `link::accepts_connections`, тройная раскладка в `peer::Machine::of`, `cfg::shown_fields` и `session.rs:437` (`mode == "local"` выбирает весь транспорт). Шесть читателей одной оси — ровно тот разряд, который спека сочетаний называет дефектом, а не мнением. `Combo::of` — одно решение, остальные становятся его производными.

### 2.2. Где живёт база — тип УЖЕ ЕСТЬ

`wire::Side { WithBase, WithAgents }`. Поле `side` в `hello` отправляется (`Side::WithAgents` из `dial_side`) и **не читается нигде** — развилка под него обещана прямо в докстроке `enroll::accept_side` («Поле `side` из `hello` здесь не читается, и это ждёт случая второго»). Своего типа заводить не нужно: `Combo::side()` и `hello.side` — одно слово по обе стороны провода.

### 2.3. Куда идёт вызов — новый тип, и перепутать стороны нельзя

```rust
// listen.rs или новый узкий модуль
pub enum Toward {
    Child(ops_host::McpServer),                                  // база здесь: поднимаем ребёнка
    Channel { peer: EndpointId, base: TheirCard, kind: McpServer } // база там: уходим в поток
}
impl Toward { pub fn of(combo: Combo, partner: Option<&Partner>) -> Result<Toward, &'static str>; }
```

Вариант `Channel` **не конструируется снаружи**: поля приватны, единственный вход — `Toward::of`, и он отдаёт его только для `Combo::{AcceptBaseThere, DialBaseThere}`. «Уйти в канал, хотя база здесь» и «поднять ребёнка, хотя базы нет» невыразимы, а не запрещены условием.

### 2.4. Чей это ключ карточки — ГЛАВНОЕ изменение типов

`cfg::CardId` сегодня значит «ключ карточки на той машине, что его назвала», и в паре A этого достаточно: `base_id` всегда называет сторона с базой, она же принимающая, она же хозяйка книги допуска — то есть `Book::enrolled_to(c.id(), peer)` сравнивает местный ключ с местным.

В паре B база — у звонящего, а книга допуска — у принимающего. Два ключа из двух пространств имён становятся одного типа и выглядят сравнимыми. Хуже: `CardId::from_name` — это `sha256("card:" + имя)[..16]`, то есть две машины с карточкой «Ромашка» без закреплённого ключа дают **одинаковый** `CardId`. Сравнение «их» ключа с «нашим» по типу проходит, по смыслу — нет, и молча совпадает.

Поэтому:

```rust
// cfg.rs
pub struct TheirCard(String);   // ключ карточки ТОЙ машины; serde как у CardId
```

`wire::BaseFields::base_id`, `wire::BaseBrief::id`, `wire::Msg::Revoked::base_id`, `wire::Why::Return`, `wire::Msg::McpOpen::base_id`, `enrolled::Partners::base_id_of`/`remember_base_id` переходят на `TheirCard`. `enrolled::Book` (`Enrolled::card`, `IssuedTicket::card`) и `cfg::Connection::id()` остаются на `CardId`. Между ними **нет преобразования** — есть только отображение, которое уже существует (`Partners`: наш `CardId` → партнёр и его `TheirCard`). `enroll::Card::id()` отдаёт `CardId` для книги и `TheirCard` для провода, и это разные функции.

Плата: механическая правка по подписям, компилятор покажет каждое место. Выгода: подстановка чужого ключа в книгу допуска перестаёт компилироваться.

### 2.5. Чем ограждён входящий `McpOpen`

```rust
pub struct Admit(Arc<Mutex<HashSet<(EndpointId, CardId)>>>);  // живые управляющие потоки ЭТОЙ машины
```

Одно правило на обе пары: **поток MCP обслуживается тогда и только тогда, когда у этой машины есть живой управляющий поток этой карточки к этому ключу.** Второй книги допуска не заводится. Запись кладётся туда, где управляющий поток встаёт на присмотр — `peer::answering` (пара A) и `peer::one_round` на `Round::Held` (пара B), — и снимается вместе с присмотром, тем же `Drop`, что сегодня снимает вожжи (`channel::reins`, `Live`). Отзыв и прощание действуют на потоки MCP немедленно и сами собой, без второго читателя книги.

## 3. Что с зачислением

**Разрешение у карточки без базы означает:** «этому ключу разрешено прислать сюда СВОЮ базу и получить от моих агентов вызовы её инструментов». Пускают не к данным этой машины — их тут нет; пускают к агентам этой машины, то есть к её папке документов и её набору инструментов.

Разговор зачисления в паре B **инвертируется, и провод к этому уже готов**:
- `Msg::Enroll` несёт `base: Option<BaseFields>` — поле завели ровно под это («в `enroll_ok`, когда база на принимающей, и в самом `enroll`, когда база на зовущей», докстрока `BaseFields`);
- `Msg::EnrollOk` несёт `base: Option<BaseFields>` и в паре B уезжает с `None`;
- тикет по-прежнему выдаёт принимающая сторона (спека сочетаний, строка «Выдать код»: у сочетания 3 — «ничего», то есть код выдаётся и базы не требует).

Правки:
- `accept_side` читает `hello.side`. `WithAgents` — как сегодня. `WithBase` — ищет карточку в `Cards::base_elsewhere`, берёт поля базы из `enroll.base` (отсутствие — отказ `code::MALFORMED` словами), спрашивает человека тем же `decide`, отвечает `EnrollOk { base: None }`.
- `Cards::base_elsewhere` перестаёт быть кучей отказа и становится второй кучей зачисления. Куча `not_accepting` и вариант `Unreadable` не меняются. Слова `enroll::BASE_ELSEWHERE` и `gui::panel::BASE_ELSEWHERE_NOTE` удаляются вместе с их тестами — им больше нечего описывать.
- `Cards::aside` перестаёт возвращать `BASE_ELSEWHERE`.
- `dial_side` в паре B шлёт `Side::WithBase` и `enroll { base: Some(…) }`. Сегодня `Side::WithAgents` стоит в семи местах `enroll.rs` литералом — все семь берут его у `Combo::side()`.

**Пара A не ломается:** её ветка в `accept_side` — та же, что сегодня, и выбирается явным `Side::WithAgents`, а не `else`.

**Книга допуска (`enrolled.rs`) не меняет смысла ни одного поля.** `Party::key` — ключ зачисленной стороны, `Enrolled::card` — НАША карточка, `IssuedTicket` — наш выданный тикет. Всё это свойства принимающей стороны, а принимающая сторона в обеих парах одна и та же — та, что выдала код. Единственная правка — `Party::peer_write` (см. ниже).

## 4. Потолок записи

Потолок — свойство машины, едет в `hello`, запрет сильнее разрешения. Складывать три меры может только та сторона, где база: своих две она читает у настроек (`Cfg::may_write(card)` — потолок машины и слово карточки), третью берёт из `hello` той стороны.

В паре B база у ЗВОНЯЩЕГО, значит складывает звонящий. А потолок принимающей стороны **на провод сегодня не уезжает вовсе**: `hello_ok` его не несёт. Это единственная настоящая дыра протокола для пары B.

- `Msg::HelloOk` получает поле `ceiling: Ceiling`. Симметрично `hello`, одно слово, читателей по одному на сторону.
- Складывание выносится в одно выражение — `wire::folded_write(mine: bool, theirs: Ceiling) -> bool` — и зовётся из двух мест (`accept_side` в паре A, `dial_side` в паре B). Два места вызова, одно выражение; оставить `c.base.write && ceiling.allows()` по месту в обоих значило бы заводить вторую меру ровно там, где её уже один раз чинили как Critical.
- **Проверяется потолок там же, где и сегодня** — на стороне базы, в аргументах ребёнка (`bridge::mcp_command`, ключ `--access`: при `read_only` пишущие инструменты у ребёнка не регистрируются вовсе). Сторона с агентами `tools/list` не фильтрует ни в одной паре — спека говорит это прямо. Потолок стороны с агентами влияет на дело ТОЛЬКО доехав до стороны с базой; в этом весь смысл поля в `hello_ok`.
- `Party::peer_write` (чужой потолок, хранится затем, что карточка в окне о нём спрашивает) сегодня обновляется только в `accept_side`. В паре B принимающая сторона — та, у которой агенты, и чужой потолок, который ей надо хранить, приезжает в `hello` звонящего так же, как и в паре A. То есть обновление остаётся на месте; меняется только то, что `write` в `hello_ok` она теперь не считает, а свой `ceiling` объявляет.

## 5. Порядок работ

Каждый шаг оставляет дерево зелёным и проверяемым. Полный прогон `cargo` — за контроллером.

**Шаг 0. `Serve::dispatch` перестаёт ключеваться портом.** `Serve::serve(kind: McpServer, stream)`; разбор «порт → вид» остаётся в `listen::accept_for`. Поведение не меняется. Доказывается: существующие тесты `listen.rs` (`both_listeners_come_up_and_a_connection_reaches_the_bridge`, `a_broken_kit_answers_every_request_with_a_refusal_and_keeps_the_connection_open`) и `session.rs` зелены без правок смысла.

**Шаг 1. `Combo`.** `Combo::of` + `Combo::side`; через них переписываются `link::accepts_connections`, `link::waits_for_incoming`, `cfg::shown_fields`, раскладка `peer::Machine::of`, ветка транспорта `session.rs:437`, `need::missing`. Чистый перенос. Доказывается: табличный тест на пять сочетаний (состав полей, принимает/звонит, где база) в одном месте; существующие тесты `gui/panel.rs` и `need.rs` зелены.

**Шаг 2. `TheirCard`.** Раскол типа ключа карточки (§2.4). Поведения не меняет; компилятор показывает каждое место. Доказывается: тест, что `Book::enrolled_to` не принимает `TheirCard` (компиляция — отрицательный тест через `trybuild` не заводить, довод в комментарии), плюс зелёные тесты `enrolled.rs` и `enroll.rs`.

**Шаг 3. `McpOpen`/`McpOk` в протоколе.** Два варианта `Msg`, `KNOWN` становится 12, `Admit`. Поток MCP пока никем не открывается. Доказывается: round-trip в `wire.rs` рядом с существующими; тест, что `McpOpen` на управляющем потоке даёт `code::UNKNOWN_MESSAGE` словами, а не проглатывается.

**Шаг 4. MCP по каналу для пары A.** Сторона с агентами (звонящая): `Toward::Channel` в `listen::accept_for`, `copy_bidirectional`. Сторона с базой (принимающая): второй первый кадр в `peer::answering` → `Serve::serve`. Доказывается: **живой прогон двумя машинами** — база здесь, Zed на `home-gpu`, `tools/list` и один `tools/call` проходят по iroh без SSH-туннеля; плюс тест на поток в памяти (`tokio::io::duplex`), что заголовок + труба отдают ребёнку те же байты, что TCP.

**Шаг 5. Зачисление пары B.** `hello.side` читается, `Cards::base_elsewhere` зачисляет, `enroll.base` разбирается, `HelloOk.ceiling`, `folded_write`, слова диалога разрешения для «база у той стороны». Удаляются `BASE_ELSEWHERE` и `BASE_ELSEWHERE_NOTE`. Доказывается: тесты `accept_side` зеркально девяти существующим (разрешили / отказали / не ответили / не зачислен / отозвали в щель / `enroll` без `base`); тест `gui/panel.rs`, что карточка с базой на другом компьютере **выдаёт код**; живой прогон не требуется — поток MCP ещё не ходит.

**Шаг 6. Вызовы пары B.** Звонящая сторона с базой на `Round::Held` кладёт себя в `Admit` и обслуживает входящий `McpOpen` через `Serve::serve`; принимающая сторона с агентами routes `listen::accept_for` в `Toward::Channel`. Доказывается: **живой прогон двумя машинами наоборот** — база на `home-gpu` звонит, Zed здесь; отзыв разрешения в окне рвёт поток MCP в ту же секунду; `--access read_only` на машине с агентами доезжает и гасит пишущие инструменты у ребёнка на машине с базой.

**Шаг 7. Слова.** Строка состояния сочетания 3 вместо снятой прозы; «обе принимают» и «обе звонят» названы словами (долг спеки сочетаний, пункт 3). Доказывается: тесты текстов в `gui/panel.rs`.

Шаги 0–3 можно вести одним заходом (ни одной правки поведения). Шаги 4 и 6 — по одному живому прогону каждый.

## 6. Чего НЕ делать

- **Не трогать внутренности `bridge.rs`**: правила, белый список инструментов, подмешивание своих, отказ при выключенных MCP, пересоздание ребёнка, спячка, переигрывание рукопожатия, уборка дерева. Спека перечисляет это как «переезжает дословно»; любая правка там — признак, что граница выбрана не там.
- **Не удалять `tunnel.rs`, gitea, среду отдельной машиной.** Снос — отдельная работа. Здесь: не опираться и не чинить. `tunnel::Incoming` остаётся жить до неё.
- **Не заводить потоки обмена** (`sync_open`, `file_open`), манифесты, сверку, git по каналу.
- **Не заводить своего пинга, своего таймера на поток MCP и своего предела на их число.** Спека: пределы держит QUIC, потоки MCP не ограничиваем.
- **Не возвращать на провод `publication`, `BaseBrief::name`, `state`.** Снято с доводом; читателя у них по-прежнему нет.
- **Не добавлять `write` в `enroll::Decision`** — четвёртая мера права записи, снятая с доводом.
- **Не делать проходимыми «обе принимают» и «обе звонят».** Шаг 7 — только слова.
- **Не поднимать номер `PROTO`** и не трогать ALPN.
- **Не заводить второй книги допуска на стороне базы в паре B** — гарантия живая (`Admit`), не хранимая.

### Что сломается молча — шесть мест «две меры на один вопрос»

1. **«Какой это ребёнок»: порт против слова.** `Serve::dispatch` ключуется `u16`, заголовок потока назовёт `kind`. Два словаря одного понятия. Снимается шагом 0.
2. **«Что это за карточка»: `mode == "local"` против раскладки по `role`+`base_is_here`.** `session.rs:437` выбирает весь транспорт одной мерой, `Machine::of` раскладывает карточки другой. Пара B добавит третью. Снимается шагом 1.
3. **Состав полей: `cfg::shown_fields` против трёх условий замка.** Спека сочетаний это уже называет долгом (следствие 1). Карточка пары B, которой поля базы не нужны, разойдётся с замком заново, если `need::missing` не пойдёт от `Combo`. Снимается шагом 1.
4. **Чей `CardId`.** `Book` ключуется нашим, провод несёт чужой, типы одинаковы, а `from_name` = `sha256("card:"+имя)` даёт двум машинам с карточкой «Ромашка» **один и тот же ключ**. Сравнение пройдёт по типу и совпадёт по значению. Самое опасное место работы. Снимается шагом 2.
5. **Складывание права записи.** `Cfg::may_write` (две половины) + `ceiling.allows()` (третья) живёт выражением по месту в `accept_side`. Пара B заводит второе такое место в `dial_side`. Ровно тот дефект, который чинили как Critical при снятии замороженного итога из книги. Снимается `folded_write` на шаге 5.
6. **`Party::peer_write` обновляется только из `accept_side`.** Если пара B пойдёт мимо него, карточка в окне покажет чужой потолок, которого нет, — и молча. Проверяется тестом на шаге 5.

Седьмое, не «две меры», но тихое: `Partners::remember_base_id` пишет признак базы только на звонящей стороне (`peer::remember`). В паре B звонящая сторона — это и есть сторона с базой, и `base_id`, который она запомнит, — её собственный ключ. Выглядит безвредно, но `Why::Return(Some(id))` тогда называет той стороне ключ из нашего пространства имён. Шаг 2 делает это невыразимым; без шага 2 — молчаливый отказ возврата.

### Сколько работы

**Много** — но не из-за пары B, а из-за MCP в канале.

- Шаги 0–1: день. Перенос, компилятор ведёт.
- Шаг 2 (`TheirCard`): день-полтора. Механика по подписям, но мест много (`wire`, `enroll`, `enrolled`, `gui/peer`, `gui/panel`, тесты).
- Шаги 3–4 (MCP по каналу, пара A): два-три дня, из них один — живой прогон двумя машинами и его разбор. Это и есть рубеж продукта; остальное вокруг него мелко.
- Шаг 5 (зачисление пары B): день. Провод готов, работа в `accept_side`/`dial_side` и в словах.
- Шаг 6 (вызовы пары B): день, почти весь — живой прогон наоборот.
- Шаг 7: полдня.

Итого порядка **недели сосредоточенной работы**, и она делится по живым прогонам: после шага 4 пара A работает по каналу без SSH (это само по себе ценность и само по себе отгружаемо), после шага 6 работает пара B.

Сократить не выйдет: пара B без MCP в канале — это зачисление, после которого нечего делать.

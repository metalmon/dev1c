# Git и альтернативы как основа синхронизации (1c-connect)

Дата: 2026-11-01. Задача: перенос дерева выгрузки 1С (~125 000 файлов) и папки
документов (Excel, PDF, бинарные печатные формы) между двумя машинами поверх
своего транспорта (iroh), без сервера, без git-знаний у человека. Код не
правил — только исследование.

Параллельно другой агент исследует automerge + iroh; здесь — git и его
альтернативы.

---

## 1. Git поверх своего транспорта (без сервера и ssh)

**Факт.** `git bundle` — файл с объектами и ссылками, который можно передать
любым способом (почта, флешка, наш iroh-поток) и применить `git pull
file.bundle`. Инкрементальные бандлы строятся диапазоном ревизий
(`git bundle create file.bundle last..master`), так что повторная передача
несёт только новые коммиты.
[git-bundle docs](https://git-scm.com/docs/git-bundle) ·
[Incremental object transfer](https://ratatoskr.run/git/2016/06/7490575/t)

**Следствие.** Бандл — это файл, не поток: подходит для «скопировал файл
через iroh, применил», но не даёт живого двустороннего протокола
(upload-pack/receive-pack) по месту. Для нашего случая (периодическая
синхронизация папки, не интерактивная сессия) это нормально: бандл можно
погнать как один blob поверх iroh, как мы гоняем любой другой файл.

**Факт.** `git-remote-ext` — встроенный remote helper, который прогоняет git
smart-protocol через произвольную внешнюю команду:
`git remote add x "ext::socat - ABSTRACT-CONNECT:/git-server %G/repo"`.
Протокол между git и helper-ом — текстовый, через stdin/stdout.
[git-remote-ext docs](https://git-scm.com/docs/git-remote-ext) ·
[Git Remote Helpers (разбор)](https://nesbitt.io/2026/03/18/git-remote-helpers.html)

**Следствие.** Это и есть «подсунуть свой транспорт» без написания полного
remote helper — но `ext::` в основе зовёт внешний процесс (ssh, socat), а
не произвольную Rust-функцию в нашем же процессе. Чтобы гонять git через
iroh, пришлось бы либо писать мост-процесс (iroh-клиент как `ext::`
команда, стримящий себя же в стдин/стдаут git), либо писать полноценный
`git-remote-<scheme>` helper на Rust, который сам понимает git-протокол и
говорит с iroh. Известная дыра безопасности: `ext::` выполняет произвольную
команду — при приёме чужих URL это RCE
([разбор](https://codeant.ai/blogs/exploiting-git%E2%80%99s-ext-protocol-for-command-execution)),
нам это не грозит, т.к. URL не внешний.

**Факт.** На уровне библиотеки — не процесса — `libgit2` имеет официальный
API регистрации кастомного «smart transport»: `git_transport_register` +
`SmartSubtransport`/`SmartSubtransportStream`, где именно ты решаешь, как
байты уходят и приходят. Пример на C# в LibGit2Sharp показывает полную
реализацию. Из Rust это видно в `git2::transport` (`unsafe fn register`).
[libgit2 transport API](https://libgit2.org/docs/reference/v1.9.0/sys/transport/index.html) ·
[git2 (Rust) transport](https://docs.rs/git2/latest/git2/transport/index.html) ·
[пример LibGit2Sharp](https://gist.github.com/pwkelley/4057030)

**Следствие.** Это — рабочий путь подсунуть iroh как транспорт git **без
отдельного процесса**, если взять `git2`/libgit2: регистрируешь свой
`SmartSubtransport`, он читает/пишет в iroh-поток, а дальше весь
upload-pack/receive-pack говорит сам git. Подводных камней на Windows в
найденном не описано отдельно — общий риск Windows у git обсуждается в п.3.

**Проверено не всё.** Готового примера «git smart-protocol поверх iroh» или
поверх произвольного QUIC/duplex-потока в Rust не нашёл — нашёл только общие
крейты транспорта (`quic-rpc`, `channel-rs`) и факасад `git-internal`
(проект Mega/Libra, см. п.2), который переизобретает протокол, а не
подключает его к существующему git. GIT_SSH_COMMAND-трюк (подменить ssh на
свою программу) не проверял отдельно — по структуре он эквивалентен
`ext::`, тех же ограничений.

## 2. Gitoxide (`gix`) и альтернативы

**Факт.** `gix`/`gitoxide` — чистый Rust, лицензия `MIT OR Apache-2.0`,
активно обновляется (`gix` 0.88.0, `gitoxide` 0.61.0 — релизы около недели
назад на момент проверки). Статус по `crate-status.md`: `gix` помечен
«usable» (грубая, но полная документация, функциональность местами не
полна), `gix-transport` — тоже «usable»/initial development. Поддержаны
clone/fetch/ls-refs (и shallow-варианты), push, самодостаточные clone/fetch
по `file://` и `ssh://`.
[crates.io: gix](https://crates.io/crates/gix) ·
[crate-status.md](https://github.com/GitoxideLabs/gitoxide/blob/main/crate-status.md) ·
[GitoxideLabs/gitoxide](https://github.com/gitoxidelabs/gitoxide)

**Следствие — важная дыра.** Независимый обзор прямо пишет: «You cannot use
gitoxide to send commits to a remote» — т.е. push ещё не на уровне
production-grade для произвольных транспортов, и своего транспортного слоя
(аналога `SmartSubtransport` из libgit2) под кастомный iroh-поток в
gitoxide, судя по найденному, никто не подключал готовым примером.
[gitoxide review](https://hysenlabs.com/projects/gitoxidelabs-gitoxide)

**Факт.** `git2` (Rust-биндинги к `libgit2`, C) — зрелая, многофункциональная
библиотека, но «сама» является WIP по покрытию API; обзор формулирует это
как «git2 подходит сервису, который читает/пишет репозитории в своём же
процессе», в то время как gitoxide целят в безопасность (нет C) и скорость
без запуска подпроцесса. Замер из обзора: `gitoxide`-python быстрее на
обходе 10 000 коммитов (129 мс против 323/389 мс), листинге 531 ссылки
(3.45 мс против 74.4/1.31 мс), чтении blob (48.8 µs против 179/188 µs).
[git2 vs gitoxide](https://hysenlabs.com/projects/rust-lang-git2-rs)

**Следствие для нас.** Транспорт, который нам реально нужен (свой iroh-канал
вместо http/ssh), сегодня **доступнее через `git2`/libgit2** (есть
официальный `SmartSubtransport` API, п.1), чем через `gix` (транспортный
слой «usable», но без документированного примера подмены на произвольный
поток, и push не гарантирован). gitoxide — кандидат на будущее
(чистый Rust, лицензия подходит), но не для первого прототипа.

**Что не проверено.** Не нашёл прямого сравнения именно по 125k-файловым
деревьям между `git2` и `gix` (checkout/commit/diff на таком размере) —
нашёл только общие замеры на количестве коммитов/ссылок, не на ширине
дерева.

## 3. Git на дереве в 125 000 мелких файлов

**Факт (Windows, наш случай).** NTFS сам по себе медленнее Linux на операциях
с множеством мелких файлов; это подтверждается замерами стороннего
Rust-реимплементатора git (`grit`, gitbutler) на Windows: на дереве 49-50k
файлов после касания 100 файлов `add` у `grit` медленнее штатного git в
3.1–4x, `diff` в 3.1–8x, `commit` в 2.4–3x; «холодный» (no-op) `add` у `git`
сам занимает 63 мс, у `grit` — свыше секунды. Корень — метаданные файловой
системы NTFS на уровень записи, не алгоритм.
[grit #1041](https://github.com/gitbutlerapp/grit/issues/1041) ·
[grit #1518](https://github.com/gitbutlerapp/grit/issues/1518) ·
[grit #2106](https://github.com/gitbutlerapp/grit/issues/2106)

**Следствие.** Это не про штатный `git.exe` (он у них — база сравнения, т.е.
быстрый), а показывает, что **самописная Rust-реализация git-подобных
операций на Windows рискует быть кратно медленнее C git** на нашем же
масштабе дерева. Аргумент в пользу «гонять MinGit как процесс», а не писать
свою индексацию.

**Факт.** Официальные рекомендации Git for Windows под большие деревья:
`core.preloadindex`, `core.fscache` (кэш файловой системы, только Windows,
требует «прогрева»), `gc.auto`. В недавних версиях (с 2.55) есть
регрессия: checkout на очень большом индексе (~2.4M записей) стал заметно
медленнее — `cache_tree_fully_valid()` вызывается двукратно, ~20с+~19с из
~44с общего времени. Параллельный checkout (`checkout.workers`) не помог
(~38–44с в обоих режимах).
[Diagnosing performance issues](https://gitforwindows.org/diagnosing-performance-issues.html) ·
[microsoft/git #974](https://github.com/microsoft/git/issues/974)

**Следствие.** На 125k файлов (не 2.4M) эта конкретная регрессия вряд ли
бьёт больно, но показывает: нужно замерять на нашем MinGit 2.56.0.2, не
верить общим цифрам — версии git дают разный результат на одном дереве.

**Факт.** `core.fsmonitor` реально ускоряет `git status`: на macOS — с ~4с до
0.6с; на грязном Linux-монорепо с 858 001 путём — с ~19с до 0.91–1.25с.
Важное ограничение: **`core.fsmonitor` работает на Windows и macOS, но не на
штатном Linux-демоне** (там нужен сторонний watchman или builtin fsmonitor с
ограничениями). На малых/средних репозиториях включение fsmonitor — это
деградация, не ускорение.
[git-tower: Git performance](https://www.git-tower.com/blog/git-performance) ·
[PSA: Turn on fsmonitor](https://groups.google.com/a/chromium.org/g/chromium-dev/c/MbTkba8g_MU)

**Факт.** `index.version=4` сжимает пути (prefix compression), даёт
30–50% уменьшения размера индекса на больших репозиториях → быстрее
загрузка/запись индекса. `sparse-index` (поверх `sparse-checkout` cone mode)
идёт дальше: размер индекса зависит от выбранных директорий, а не от всего
дерева.
[gitformat-index](https://www.kernel.org/pub/scm/git/git-htmldocs.git/tree/gitformat-index.txt) ·
[Sparse index (github blog)](https://github.blog/2021-11-10-make-your-monorepo-feel-small-with-gits-sparse-index)

**Факт.** Замер практика на монорепо из 407 проектов: `sparse-checkout`
ускорил клон вдвое, сократил `.git` вдвое, `git status` упал с 76 мс до
13 мс, рабочее дерево — на 97%.
[GitHub blog: sparse-checkout](https://github.blog/open-source/git/bring-your-monorepo-down-to-size-with-sparse-checkout/)

**Факт.** Для действительно огромных деревьев Microsoft сделал `Scalar`
(обёртка над партиальным клоном + fsmonitor + multi-pack-index) — опыт с
Windows-репозиторием: индекс — 3+ млн записей, дерево ~3.5 млн файлов,
~300ГБ. Это масштаб x25 от нашего — если 125k не тянет штатный git с
правильными настройками, это сигнал о проблеме конфигурации, не о пределе
git.
[Introducing Scalar](https://devblogs.microsoft.com/devops/introducing-scalar/) ·
[Scalar tech doc](https://www.kernel.org/pub/software/scm/git/docs/technical/scalar.adoc)

**Следствие для нас.** 125 000 файлов — это **ниже** порога, где git
официально «ломается» (миллионы файлов). При включённых
`core.fscache`/`core.fsmonitor`/`index.version=4`/`core.preloadindex` на
Windows штатный `git.exe`(MinGit) должен справляться с секундами, не
минутами — но это **нужно замерить именно на нашем MinGit и нашем дереве**,
т.к. готового стороннего замера на 100–130k файлов конкретно на MinGit
2.56.0.2 я не нашёл (есть только 50k у `grit`, где база — не MinGit, и
~400-858k-файловые монорепо на Linux).

**Что не проверено.** Нет прямого замера `git add`/`commit`/`status` именно
на дереве 125 000 файлов именно на Windows именно на штатном `git.exe` —
ближайшие цифры (50k у grit-issues, 400-858k у sparse-checkout/fsmonitor
постов) дают коридор, не точку.

## 4. Бинарные файлы (документы) в git

**Факт.** Git хранит полную копию файла при каждом изменении бинарника —
дельта-сжатие внутри pack-файлов плохо работает на несжимаемых/непохожих
бинарных форматах (Excel, PDF меняются «насквозь» при пересохранении). Каждый
клон тащит всю историю всех версий файла — размер репозитория растёт
монотонно и не садится без переписывания истории.
[git-tower: handling large files](https://www.git-tower.com/learn/git/faq/handling-large-files-with-lfs) ·
[Fekir: git and binary files](https://fekir.info/post/git-and-binary-files/)

**Факт.** Смягчения — `git-lfs` (указатель в репо, сам файл — вовне, нужен
сервер/хранилище LFS), `git-annex` (похож, сложнее в освоении), DVC
(похожая модель с `.dvc`-указателями), либо вообще не класть большие файлы
в git («самый прямой путь — хранить вовне»). Очистка истории после факта —
`git filter-repo`.
[Git LFS alternatives](https://files.link/blog/git-lfs-alternatives)

**Следствие — ключевое для нас.** Все смягчения проектированы под
**редко меняющиеся** большие бинарники в репозитории с сервером (GitHub и
т.п.). У нас документы синхронизируются **постоянно** (рабочий поток
редактирования Excel/PDF) — это ровно худший случай для git: история будет
пухнуть при каждом сохранении, а LFS/annex требуют инфраструктуры
(хранилище, сервер), которую мы прямо решили не поднимать («человек не
настраивает git»). **Git — плохая основа именно для папки документов**, даже
если взять его для кода 1С.

## 5. Syncthing / BEP как встраиваемая вещь

**Факт.** Нашёл `syncthing-rust` (github.com/juice094/syncthing-rust) —
заявлен как провод-совместимая (wire-compatible) с официальным Go Syncthing
реализация протокола BEP на чистом Rust: TLS, блочная P2P-синхронизация,
LAN/глобальный discovery (UDP/HTTPS/STUN/UPnP/Relay v1), REST API, TUI,
трей для Windows, «production-ready», версия 3.0.3 (есть релиз 3.0.5 —
«Data-Loss Hardening + E2E Race Elimination» — само название релиза говорит,
что гонка данных и потеря данных были найдены и чинились).
[syncthing-rust](https://github.com/juice094/syncthing-rust) ·
[релиз 3.0.5](https://github.com/juice094/syncthing-rust/releases/tag/v3.0.5)

**Следствие.** Это не официальный проект Syncthing (сам Syncthing — Go), а
независимая реимплементация силами одного автора/небольшой команды — риск
зрелости и поддержки выше, чем у вендора. Название релиза про «устранение
гонок» на минорной версии 3.0.x — сигнал, что продукт ещё находит свои
баги на основной функции (целостность данных), а не признак зрелости.
Лицензию конкретно этого форка я не проверил по файлу LICENSE — не нашёл её
текста в выдаче поиска.

**Факт.** Есть и `bep`/`bep-core` на docs.rs — библиотека протокола
отдельно от демона; есть `st-rust` — явно обозначен автором как «toy
implementation... purely for educational purposes», то есть не для
встраивания.
[bep-core docs.rs](https://docs.rs/bep-core/latest/bep/) ·
[st-rust](https://github.com/abusch/st-rust)

**Что не проверено.** Лицензия `syncthing-rust` и `bep-core`; живой
бенчмарк блочной передачи на дереве 125k файлов; совместимость с нашей
моделью «не демон, а библиотека внутри нашего процесса, говорящая по iroh,
а не по своему TCP/TLS» — BEP в этих реализациях рассчитан на свой
транспорт (TLS-сокет), не на подстановку произвольного потока; степень
переносимости на iroh не проверял за неимением примеров.

## 6. rsync-дельты из Rust

**Факт.** `fast_rsync` (Dropbox) — чистый Rust, оптимизированная (SIMD)
переработка `librsync`: API `calculate_signature`/`diff`/`apply`, лицензия
**Apache-2.0**. Явное предупреждение авторов: подписи используют MD4
(небезопасный алгоритм), поэтому `diff` **не гарантирует корректность**
дельты — нужна дополнительная проверка (например, итоговый sha256, который
у нас и так есть в `integrity.rs`).
[fast_rsync README](https://github.com/dropbox/fast_rsync/blob/master/README.md)

**Факт.** `librsync` (крейт) — биндинги к C librsync 1, для построения и
применения сетевых дельт, поддерживается (последний релиз на момент
проверки — около 2 месяцев назад).
[librsync docs.rs](https://docs.rs/librsync/latest/librsync/)

**Факт.** `zsync-rs` — чистый Rust, реализация алгоритма zsync (скачивание
только недостающих частей файла), 5 релизов, последний 0.1.3/0.1.4 на
момент проверки — живой, но маленький проект.
[zsync-rs на lib.rs](https://lib.rs/crates/zsync-rs)

**Следствие для нас.** Это именно тот слой, который считает «что
изменилось внутри файла» — хорошо дополняет файловую синхронизацию (списки
+ sha256) для **больших бинарников, которые меняются целиком** (Excel,
PDF): передавать не весь файл, а дельту. `fast_rsync` — лучший кандидат
(Apache-2.0, SIMD, живой, от крупной компании), но контрольную сумму
проверять поверх (MD4-предупреждение) — у нас уже есть sha256 в
`integrity.rs`, это бесплатно закрывается.

## 7. Своя синхронизация на списке файлов + sha256

У нас уже есть обход дерева с sha256 (`setup/common/src/integrity.rs`) — это
не нужно искать в сети, это проектный факт. Честный список того, что
придётся решать самим, если идти этим путём (без ссылок — это инженерный
список, не факт из сети):

- **Переименования.** Список+хеш не видит переименование — файл пропадёт из
  одного места и появится в другом; без эвристики «тот же хеш, другое имя»
  это передаётся как удаление+вставка (двойной трафик на большой файл, но
  безопасно).
- **Удаления.** Нужен явный маркер tombstone — иначе удалённый на одной
  стороне файл при следующем скане посчитается «отсутствующим локально» и
  может быть не удалён, а переслан заново с другой стороны.
- **Частичная/прерванная передача.** Нужны свои временные файлы +
  атомарное переименование по завершении; sha256 после записи — проверка,
  что докачалось верно (уже есть механизм для этого в проекте).
- **Одновременная правка с двух сторон.** Список+хеш не знает про
  «одновременно» — нужен свой маркер версии/времени или просто
  «последний применённый побеждает» + сохранение проигравшей копии
  (`.conflict`), иначе тихая потеря правки.
- **Масштаб 125k файлов.** Полный обход + sha256 всего дерева на каждый
  цикл синхронизации — это сам по себе стоит столько же, во что встаёт
  `git status` без fsmonitor (обход всех файлов); нужен дифференциальный
  скан (mtime+size до хеширования) — это тоже не бесплатно спроектировать,
  но это 1 файл логики, не новая зависимость.

**Во что это обходится против git.** git присылает «бесплатно» вместе с собой:
протокол передачи только расхождений (pack negotiation), атомарность
коммита, историю/откат, разрешение переименований (эвристика git diff),
защиту от гонки записи (через собственный процесс индексации). Самодельный
путь на списке+sha256 экономит на зависимостях и сложности транспорта
(подходит ЛЮБОЙ канал, включая iroh, без протокольной мимикрии под
upload-pack), но платит тем, что перечислено выше нужно написать и
протестировать руками — переименования, tombstone, atomic rename, conflict-
маркер. Для одной синхронизируемой папки документов (не истории, не
дерева 125k) это разумный объём работы. Для дерева 125k файлов 1С этот же
объём работы нужно делать быстро (дифф-скан, не полный обход) — не находка
из сети, инженерная оценка.

## Что не проверено (сводка)

- Нет готового опубликованного примера «git smart-protocol поверх
  произвольного duplex-потока (iroh/QUIC) в Rust» — ни на `git2`, ни на
  `gix`. Путь через `git2::transport::register` выглядит рабочим по API,
  но без чужого прецедента.
- Нет прямого замера `git add`/`commit`/`status` на дереве именно 125 000
  файлов именно на MinGit 2.56.0.2 на Windows — только соседние точки (50k у
  grit, 400–858k у монорепо-постов).
- Лицензия и устойчивость `syncthing-rust` (juice094) не подтверждена
  текстом LICENSE; переносимость BEP на произвольный транспорт (не TLS-сокет)
  не нашёл примеров.
- `gix` push на кастомный транспорт — по независимому обзору не поддержан
  («cannot use gitoxide to send commits to a remote»); не проверял, изменилось
  ли это в версии 0.88 отдельным поиском по changelog.
- Рост размера истории git конкретно на профиле «Excel/PDF, пересохраняется
  N раз в день» не замерян численно ни в одном найденном источнике — только
  общий принцип «растёт монотонно».

## Вывод

**Для дерева 1С (125 000 файлов, код/конфигурация, текстовый по природе)**
git — разумная основа: это ровно его расчётный случай (структурированные
текстовые деревья, инкрементальный обмен), 125k заметно ниже порога, где
git официально требует Scalar/VFS (миллионы файлов), и путь «подсунуть
iroh как транспорт» существует на уровне API (`git2`/libgit2
`SmartSubtransport`), хоть без чужого прецедента. Условие — спрятать git
полностью: наш процесс гоняет MinGit как библиотеку/подпроцесс,
настраивает `core.fscache`+`core.fsmonitor`+`index.version=4`+
`core.preloadindex` сам, человек ничего не видит.

**Для папки документов (бинарники, правятся постоянно)** git — плохая
основа: его модель «полная копия на каждое изменение, история растёт
монотонно» — ровно худший случай для рабочего потока правки Excel/PDF, а
единственные официальные смягчения (LFS/annex) требуют внешнего хранилища,
которого мы решили не поднимать. Здесь дешевле и честнее собственная
синхронизация на уже существующем `integrity.rs` (список + sha256 +
дифф-скан по mtime/size) с дельта-передачей через `fast_rsync` для крупных
файлов — не git-механизм вообще.

**Единого механизма на оба случая, подтверждённого фактами, не нашлось.**
Если нужен ровно один инструмент — ближе к общему знаменателю git
(он тянет оба типа файлов технически), но для документов он будет платить
постоянным ростом репозитория без выигрыша (бинарники дельта-сжимаются
плохо). Если можно разделить — git для кода 1С, своя синхронизация
(список+sha256+fast_rsync) для документов — это не противоречит
результатам исследования.

**Что стоит прототипировать первым:** узкий тест на реальном дереве проекта
(125k файлов, тот самый ERP-выгруз) — `git init` + `git add -A` + `git
commit` на MinGit 2.56.0.2 с включёнными `core.fscache`/`core.fsmonitor`/
`index.version=4`, с замером по секундомеру. Это закрывает самую большую
дыру из раздела «что не проверено» одним прогоном и либо подтверждает, либо
опрокидывает весь вывод по git для кода.

## Замер, которого в сети нет: git из нашего комплекта на 125 тысячах файлов

Исследование честно сказало, что прямого замера на таком дереве не нашло. Сделал сам 1.11.2026 — MinGit из комплекта (`C:\dev1c-connect-kit\git\cmd\git.exe`), Windows, NTFS, дерево 125 000 файлов по 1,2 КБ в 3 125 каталогах, флаги из исследования (`core.fscache`, `core.preloadindex`, `index.version=4`).

| Действие | Время |
| --- | --- |
| создание дерева средствами ФС (не git) | 68,2 с |
| `git init` | 0,1 с |
| `git add .` — первый, всё дерево | **41,7 с** |
| `git commit` — первый | 4,5 с |
| `git status` на чистом дереве | **0,2 с** |
| `git status` после правки 100 файлов | **0,2 с** |
| `git add -A` тех же 100 | 0,3 с |
| `git commit` второй | 0,6 с |
| размер `.git` после двух коммитов | 8 МБ |

**Что из этого следует.** Дорогой только первый ввод дерева — около 45 секунд, один раз. Всё, что происходит дальше каждый день, укладывается в доли секунды: `status` на чистом дереве 0,2 с, цикл «правка сотни файлов → коммит» меньше секунды. Опасение «git задохнётся на выгрузке ERP» не подтвердилось с большим запасом.

**Оговорка про размер.** Файлы замера однообразны и сжимаются лучше настоящей выгрузки, поэтому 8 МБ — нижняя граница, а не ожидание. Порядок (десятки мегабайт на дерево в 190 МБ текста) при этом сохраняется: XML жмётся хорошо.

**Находка, которой не искал.** Git на каждом файле ругался «LF будет заменён на CRLF». Для нашей задачи это не косметика: автоматическая замена переводов строки **меняет содержимое файлов**, то есть выгрузка, проехавшая через такой репозиторий, вернётся в 1С не байт-в-байт. Для внутреннего репозитория синхронизации перевод строк обязан быть выключен (`core.autocrlf=false`, а надёжнее — `.gitattributes` с `-text` на всё дерево). Это та же болезнь, что уже записана в бэклоге про расхождение комплекта и образа переводом строки.

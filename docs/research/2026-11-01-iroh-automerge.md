# iroh и automerge как транспорт/основа синхронизации (2026-11-01)

Контекст: синхронизация каталога выгрузки 1С (порядка 125 000 файлов для ERP) и бинарных документов (Excel, PDF) между машиной с 1С и машиной с агентами. Транспорт — iroh (решено). Основа синхронизации — кандидат automerge (альтернатива, git, исследует другой агент). Задача этого документа — факты по automerge и iroh со ссылками, без догадок.

Все даты и номера версий — по состоянию на 2026-11-01.

## 1. iroh-blobs / iroh-docs / iroh-willow: что живо, что нет

Факты:

- `iroh-blobs` README буквально: *«NOTE: this version of iroh-blobs is not yet considered production quality. For now, if you need production quality, use iroh-blobs 0.35»* — то есть сейчас одновременно существуют старая стабильная линия (0.35) и новая переработанная линия (0.9x–0.10x), которая ещё не признана продакшен-готовой самими авторами. 206 899 загрузок/месяц, 81 крейт-потребитель. [lib.rs/crates/iroh-blobs](https://lib.rs/crates/iroh-blobs)

Важно: **содержимое записи не хранится в самом документе** — значение entry это 32-байтный BLAKE3-хеш содержимого + размер + timestamp; реальные байты раздаёт `iroh-blobs`. 46 287 загрузок/месяц, 26 крейтов-потребителей (на порядок меньше, чем у `iroh-blobs`). [lib.rs/crates/iroh-docs](https://lib.rs/crates/iroh-docs)
- `iroh-willow` — реализация протокола Willow (willowprotocol.org) поверх iroh. Один релиз 0.0.1, 886 скачиваний за всё время. Репозиторий не архивирован, коммиты идут, но собственный README статус — «work is not released yet». Фактически пригоден только для наблюдения за проектом, не для использования. [github.com/n0-computer/iroh-willow](https://github.com/n0-computer/iroh-willow), [docs.rs/crate/iroh-willow/latest](https://docs.rs/crate/iroh-willow/latest)
- Исторический факт: `iroh-blobs`, `iroh-docs` (и `iroh-gossip`) были выделены из основного репозитория `iroh` и после версии 0.29 перестали ре-экспортироваться из ядра — то есть это сознательно отдельные, самостоятельно версионируемые крейты, а не «встроенные» модули. [newreleases.io/.../iroh/release/v0.28.1](https://newreleases.io/project/github/n0-computer/iroh/release/v0.28.1), [iroh.computer/blog/iroh-0-28-let-them-have-crates](https://www.iroh.computer/blog/iroh-0-28-let-them-have-crates)

**Следствие для нас:** для передачи самих байт файлов (`iroh-blobs`) нужно явно выбирать: либо старая линия 0.35 (продакшен-пригодная, но без новых улучшений), либо следить за выходом 1.0 новой линии. `iroh-docs` как «индекс файл→хеш» пригоден по форме для манифеста каталога, но это не CRDT и не слой мержа содержимого — конкурентные правки одного ключа разрешаются, видимо, по последней метке (не проверял механизм разрешения конфликтов внутри iroh-docs отдельно — см. раздел «не проверено»). `iroh-willow` непригоден сейчас.

## 2. Пробивание закрытых сетей без своего релея

Источник — официальный FAQ iroh. [docs.iroh.computer/about/faq](https://docs.iroh.computer/about/faq)

- iroh всегда пытается прямое P2P-соединение через QUIC + hole punching; если не получилось — падает на релей. Это поведение по умолчанию, отключаемое явно.
- Цитата из FAQ про цену отказа от релея: *«Roughly one connection in ten stops working. Stricter firewalls and certain router types do not allow two devices to connect directly. Those connections use a relay today. Without one they simply fail, with no fallback and no error you can fix from the network side.»* — то есть примерно 1 из 10 соединений **не пробивается** и без релея просто не работает.
- Релей нужен не только как fallback передачи данных, но и как точка знакомства (rendezvous): *«You lose the introduction, not just the fallback... a device behind a firewall cannot be reached at all unless you provide another way for peers to find each other.»*
- Полностью без релея (`RelayMode::Disabled`) соединение всё же возможно, если: (а) стороны уже обменялись `EndpointAddr` с прямыми адресами заранее, или (б) машины в одной локальной сети и включён local network address lookup (аналог mDNS). Для двух машин в разных сетях с NAT, не обменявшихся адресами заранее, — релей (свой или чужой) обязателен для первого «знакомства».
- Требуемые порты минимальны: исходящий TCP 443 к релею — «the only connection iroh strictly requires»; входящие порты не нужны, port forwarding не требуется.
- Самостоятельный релей — официально поддерживаемый, задокументированный путь (open-source `iroh-relay`, автоматический TLS через ACME), не требующий покупки у n0. [docs.iroh.computer/deployment/dedicated-infrastructure](https://docs.iroh.computer/deployment/dedicated-infrastructure)

**Следствие для нас:** «закрытая сеть заказчика» не ломает iroh-пробивание само по себе (90% соединений пробиваются и без релея как посредника для данных), но для **первого знакомства** сторон всё равно нужна точка координации, достижимая обеими машинами. Без неё системы просто не найдут друг друга через NAT. «Не хотим поднимать свой релей» и «сеть закрытая» — требования в потенциальном противоречии: если обе машины не могут достичь ни одного релея (ни n0, ни своего), hole punching тоже не начнётся, т.к. релей — это и механизм обмена рефлексивными адресами, а не только труба для данных.

## 3. Чей релей по умолчанию, видит ли он содержимое

Источник — FAQ и Overview. [docs.iroh.computer/about/faq](https://docs.iroh.computer/about/faq), [docs.iroh.computer/deployment/dedicated-infrastructure](https://docs.iroh.computer/deployment/dedicated-infrastructure)

- По умолчанию iroh использует публичную общую инфраструктуру, которой управляет **n0.computer**. Официально: *«We recommend using the public relays for development and testing... For most production systems, use Shared Relays... Use dedicated relays when you need single-tenant capacity, custom regions... Use an Enterprise plan when you need an SLA.»* — то есть сам n0 не рекомендует публичный релей для продакшена.
- Шифрование: все соединения iroh — это QUIC = TLS 1.3, сквозное шифрование включено всегда, без доп. настройки. Прямая цитата FAQ: *«The traffic you relay is fully end-to-end encrypted and cannot be decrypted by the relay. The only information a relay has is... the endpoint IDs and IP addresses of the endpoints currently connected to it, plus which endpoints are paired.»* Релей не имеет выхода в открытый интернет (сравнение с Tor: «like running a guard/middle relay, not an exit node»).
- Про трансграничность и юрисдикцию FAQ разделяет два разных страха прямой цитатой: *«If the concern is that someone could read the data, it is already addressed... If the concern is control, jurisdiction, or data residency, the answer is to run the relay yourself... Your server, your network, your logs, and nothing leaves your perimeter.»*

**Следствие для нас:** содержимое файлов релей (даже чужой, n0) не видит — это закрыто математически (TLS 1.3), а не только политикой n0. Но **метаданные соединения** (endpoint ID, IP-адреса сторон, факт и время связи) при использовании публичного релея n0 всё равно проходят через инфраструктуру, физически расположенную вне РФ (US/EU/Singapore — по данным одного из вторичных источников, не подтверждено первоисточником, см. «не проверено»). Если требование «никакой трансграничной передачи» трактуется шире, чем «содержимое», и охватывает сам факт маршрутизации трафика/метаданных через чужую инфраструктуру — единственный документированный способ это закрыть — свой релей на своей стороне. Это прямо противоречит желанию «отдельный релей не поднимать» и требует явного решения владельца: либо поднимаем минимальный свой релей (это open source, не платная услуга), либо принимаем, что метаданные соединения (не содержимое) идут через n0.

[lib.rs/crates/iroh](https://lib.rs/crates/iroh), copyright-строка «Copyright 2024 N0, INC.» в `iroh-willow`. [lib.rs/crates/iroh-willow](https://lib.rs/crates/iroh-willow)

- iroh 1.0 вышел 15 июня 2026, после ~4 лет разработки и 65 пред-релизных версий. [iroh.computer/blog/the-road-to-iroh-1-0](https://www.iroh.computer/blog/the-road-to-iroh-1-0)

Also заявлен кейс Nous Research — распределённое обучение ИИ на iroh, с заявленными 10x экономии полосы и 50% экономии стоимости — это материал со страницы кейсов самого n0, независимого подтверждения не нашёл.

- Важная оговорка про зрелость конкретно нужных нам частей: `iroh` (ядро, транспорт) — зрелый и широко используемый. `iroh-blobs` (передача файлов) — новая линия прямо помечена как не продакшен-готовая. `iroh-docs` — на порядок меньше внедрений, чем `iroh-blobs`. `iroh-willow` — пререлиз. То есть «iroh зрелый» верно для транспорта, но не автоматически верно для конкретных кусков, нужных для синхронизации файлов.

## 5. Automerge: CRDT на документ, а не на папку

- Протокол синхронизации Automerge работает **на уровне одного документа**: *«The sync protocol works on a per-document basis»* (automerge.org/docs/concepts). `automerge-repo` — обёртка, которая управляет сетью/хранением для **многих** документов одновременно, но не даёт «синхронизацию папки» из коробки — разбиение файлов на документы остаётся на разработчике. [automerge.org/blog/automerge-repo](https://automerge.org/blog/automerge-repo/)
- Собственная рекомендация авторов по модели данных: *«An Automerge document is best suited to being a unit of collaboration between two people or a small group.»* — то есть сама документация не советует «один документ на файл» при десятках/сотнях тысяч файлов. [automerge.org/docs/cookbook/modeling-data](https://automerge.org/docs/cookbook/modeling-data/)
- `autosurgeon` / `autosurgeon-derive` — Rust-крейты с serde-подобными трейтами `Reconcile`/`Hydrate` и derive-макросами для маппинга Rust-структур в/из одного Automerge-документа. Это решает только преобразование «структура ↔ документ», не синхронизацию дерева файлов. [crates.io/crates/autosurgeon](https://crates.io/crates/autosurgeon)
- Готового, поддерживаемого решения «синхронизировать папку файлов через automerge» на сегодня **не нашёл**. Единственная известная попытка — ниже (п.7/даrn).

**Следствие:** то, что нужно нам (синхронизация дерева в 125 000 файлов), не является тем, для чего Automerge спроектирован и не тем, для чего у него есть готовый инструмент — это придётся писать самим поверх `automerge-repo`, с неочевидным масштабированием (см. п.6).

## 6. Накладные расходы Automerge: память, большие деревья, бинарники

- История изменений хранится полностью (ради offline-режима и version control). До Automerge 3.0 это могло означать **гигабайты памяти** на документах с длинной историей. [automerge.org/blog/automerge-3](https://automerge.org/blog/automerge-3)
- Automerge 3.0 (релиз в 2026) снизил потребление памяти «более чем в 10 раз, местами сильно больше», перейдя на сжатый формат и во время работы, не только «на диске». Конкретный пример от самой команды: вставка полного текста «Моби Дика» в документ Automerge 2 — 700 МБ памяти; в Automerge 3 — 1.3 МБ. Формат файла (на диске) не менялся, обновление почти полностью совместимо по API. [automerge.org/blog/automerge-3](https://automerge.org/blog/automerge-3)
- Это измерение — для **одного** документа с историей текстовых правок. Для сценария «много документов» другая, отдельно документированная проблема: проект **PushPin** (сделан самим Ink & Switch, создателями Automerge) был построен на очень гранулярных документах (документ на карточку) и столкнулся с высокими накладными расходами именно на синхронизации **многих тысяч** документов. [inkandswitch.com/pushpin](https://www.inkandswitch.com/pushpin/), упоминание в [automerge.org/docs/cookbook/modeling-data](https://automerge.org/docs/cookbook/modeling-data/)
- 125 000 файлов — это ещё на 1-2 порядка больше, чем «тысячи», на которых уже зафиксирована проблема у авторов библиотеки на их собственном продукте.
- Бинарные файлы: тип `Bytes` в Automerge — непрозрачный скаляр (BLAKE3/байтовый блок), для него **нет diff/merge** — это подтверждается конкретной реализацией схемы Patchwork в проекте darn (см. п.7): бинарный файл хранится как `Bytes`-скаляр с семантикой «весь файл целиком, последняя запись побеждает» (whole-file last-writer-wins). Это означает, что для Excel/PDF вся «добавленная стоимость» CRDT (история изменений с метаданными на каждую операцию) просто не используется — выгоды мержа нет, а цена хранения истории остаётся.
- Прямого измерения «сколько места/памяти занимает история automerge-документа с множеством перезаписанных бинарных блобов» **не нашёл** — это вывод из архитектуры (Bytes — непрозрачный скаляр, каждая правка такого скаляра добавляет новую версию в историю операций), а не измеренный факт.

## 7. Пример iroh + automerge

Официальный пример живёт в `github.com/n0-computer/iroh-examples`, задокументирован на странице [docs.iroh.computer/protocols/automerge](https://docs.iroh.computer/protocols/automerge). Внутри репозитория — две разные папки:

1. **`iroh-automerge/`** — минимальный пример: самодельный обработчик iroh-протокола, который прогоняет «сырые» сообщения automerge sync protocol (length-prefixed бинарные фреймы) через двунаправленный QUIC-поток между двумя iroh endpoint'ами до тех пор, пока обе стороны не сообщат «done». Никакого `automerge-repo`, никакого хранения на диске, никакой работы с множеством документов — только «можно прогнать sync-сообщения одного in-memory документа через iroh-соединение». Год/актуальность: пример активно задокументирован в текущей (2026) документации iroh, то есть жив и поддерживается как часть официальных примеров.
2. **`iroh-automerge-repo/`** — использует крейт `samod` (сторонняя Rust-реализация протокола `automerge-repo`) как backing repo. Демонстрирует одно действие за раз через CLI (`create`, `upsert`, `print`) для **одного документа, идентифицируемого вручную по id**. [github.com/n0-computer/iroh-examples/tree/main/iroh-automerge-repo](https://github.com/n0-computer/iroh-examples/tree/main/iroh-automerge-repo)

Оба — учебные примеры внутри репозитория-коллекции примеров (`iroh-examples`), не отдельные версионируемые библиотечные крейты и не демонстрация синхронизации дерева файлов. Они показывают «транспорт совместим», а не «есть готовое решение для нашей задачи».

## Что из этого не проверено

- Конкретный список регионов публичных релеев n0 (US West/East, EU Central, Singapore) — встретился только в сводке поиска, не подтверждён прямой выдержкой из первоисточника в этом заходе.
- Термин «QUIC-NAT-Traversal (QNT), emerging IETF standard» — из стороннего блога (pinggy.io), не из собственной документации iroh; числовая оценка «~90% пробивается» согласуется с официальным FAQ («1 из 10 не работает»), но терминология QNT не проверена по первоисточнику iroh.
- Причина архивации проекта `darn` (архивирован владельцем 30 апреля 2026) — не нашёл явного объяснения ни в README, ни в обсуждениях.
- Поведение `iroh-docs` при конкурентной записи одного ключа двумя авторами (разрешение конфликта) — не проверял отдельно механизм в этом заходе.
- Заявленные n0 метрики масштаба (миллионы устройств, 200+ млн endpoint'ов, кейс Nous Research с 10x/50%) — это собственные публикации/анонсы n0, независимого подтверждения третьей стороной не нашёл.
- Прямое измерение роста размера automerge-документа/истории при множестве перезаписанных бинарных блобов — не нашёл, вывод сделан из архитектуры типа `Bytes`, а не из бенчмарка.
- Активность `iroh-willow` по коммитам (видел в сводке «push 27 дней назад», 60 звёзд, 7 форков) — не проверял напрямую список коммитов, полагаюсь на сводку поиска.

## Вывод

**Automerge не годится как основа синхронизации каталога в 125 000 файлов с бинарниками.** Три независимые причины, каждая сама по себе достаточна:

1. **Нет готового инструмента.** Automerge синхронизирует документы, не папки. Единственная известная попытка построить «папку как набор Automerge-документов» — проект `darn`, сделанный самими авторами Automerge (Ink & Switch), — архивирован (30.04.2026), а транспорт синхронизации, на котором он стоял (Subduction), сам называет себя «early release preview... not recommended for production use cases».
2. **Масштаб на 1-2 порядка выше, чем уже зафиксированная проблема.** Собственный рекомендательный документ Automerge советует не делать «документ на мелкую единицу»; собственный проект авторов (PushPin) на тысячах документов уже столкнулся с высокими накладными расходами синхронизации. 125 000 — заметно больше «тысяч».
3. **Для бинарников CRDT не даёт ничего, кроме цены.** `Bytes`-скаляр не мержится по содержимому — это подтверждено конкретной реализацией (`darn`'s Patchwork-схема: whole-file last-writer-wins). То есть для Excel/PDF Automerge платит стоимость хранения истории операций, не получая взамен единственной причины использовать CRDT — слияния.

Место Automerge — не здесь. Если он всё же нужен в системе, его естественная роль — небольшой фрагмент действительно конкурентно редактируемых структурированных данных (например, манифест состояния синхронизации или общая небольшая конфигурация), а не транспорт для дерева выгрузки 1С и не механизм для документов Excel/PDF.

Для самого дерева файлов и бинарных документов на стороне iroh ближе к делу `iroh-blobs` (контентно-адресуемая передача по BLAKE3, подходит и для кода, и для бинарников как есть) в связке с `iroh-docs` как индексом «путь → хеш» (с учётом, что `iroh-docs` не хранит содержимое и не является CRDT, а сам `iroh-blobs` в новой линии пока не признан продакшен-готовым — для старта разумнее закрепиться на линии 0.35). Вопрос релея (п.2–3) требует отдельного решения владельца: условие «никакой трансграничной передачи» и условие «свой релей не поднимаем» в текущем виде логически противоречат друг другу, если трактовать «передачу» шире, чем «содержимое».

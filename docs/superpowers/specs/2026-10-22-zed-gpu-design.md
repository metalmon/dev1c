# Zed жжёт процессор: причина, GPU и что с этим делать

**Дата:** 2026-10-22 (редакция 2 — после проверки GPU на живом железе).
**Повод:** заказчик — «проблема с высокой нагрузкой на CPU от Zed и Zed на GPU».

## Коротко

1. **Главный расход процессора — не «кадры», а панель проекта.** Воркспейс
   проекта на 184 556 файлов — это 128 475 записей, и Zed рисует их
   непрерывно: 358–391 % ядра в простое. Пустой проект — 0 %, скрытое окно —
   0 %, закрытая панель проекта — 1–2 %. Рендер программный (llvmpipe),
   потому что устройства Vulkan в контейнере нет.
2. **GPU в контейнере на WSL2 не включается** — две проверенные, независимые
   причины (графический адаптер dxg недоступен для сессии `docker-desktop`;
   Xvfb в контейнере без DRI2/DRI3). Это ограничение WSL, а не настройки.
3. **В самом WSL-дистрибутиве (без контейнера) GPU работает** — но через
   **GL**, а не через Vulkan (см. ниже). Это важно для диагноза: «WSL не умеет
   GPU» — неверно, «WSL не умеет GPU в контейнере» — верно.
4. **На Linux-сервере с NVIDIA GPU включается в текущей конфигурации**
   (драйвер ≥ 525 + Vulkan ICD на хосте + `NVIDIA_DRIVER_CAPABILITIES` с
   `graphics`, который уже прописан). Не проверено на живом сервере — на пилоте.
5. **GPU не отменяет фоновую работу git.** Даже на GPU Zed продолжает поллить
   git каждые 2–5 с (баг апстрима), и 30 с на `status` никуда не денутся —
   это отдельная работа, см. спеку про ограничение git двумя ядрами.

## Как мерилась нагрузка

`ps -eo pcpu` показывает среднее за всю жизнь процесса, а не текущую
нагрузку, — по нему легко ошибиться. Текущая нагрузка — разница счётчиков
`/proc/<pid>/stat` (поля 14+15) за интервал:

```
p=$(pgrep -f zed-editor | head -1)
a=$(awk '{print $14+$15}' /proc/$p/stat); sleep 5
b=$(awk '{print $14+$15}' /proc/$p/stat); echo $(( (b-a)*100/5/100 ))% ядра
```

Все числа ниже — на живом контейнере `dev1c`, рабочее место dev1, проект
`/home/dev1/project`, 2026-10-22.

## Диагноз: панель проекта, а не кадры

| Сценарий | Нагрузка |
|---|---|
| Проект открыт, в редактор никто не смотрит | **358–391 % ядра** |
| Тот же проект, панель проекта закрыта | 1–2 % |
| Тот же проект, окно скрыто | **0 %** |
| Пустой проект | 0 % |
| Всплеск при открытии | 533 % (8 потоков llvmpipe) |
| Xorg за тот же интервал | ≈ 0,6 % |
| `bsl-analyzer` (LSP и MCP) | 0,5 % |

Состав проекта: 184 556 файлов, из них `src/` — 66 958 (44 727 `.xml`, 15 172
`.bsl`, 2 090 `.zip`), `.git` — 117 591; индекс git — 14,4 МБ.

Отсюда вывод: пока панель проекта открыта, Zed рисует 128 475 записей
непрерывно, программным рендером, в несколько потоков. Закрыть панель
(`ctrl+shift+e`) — мгновенный выигрыш в сотни процентов процессора; это
работает везде и не зависит от наличия видеокарты.

Цена вопроса на пилоте: рабочих мест три. Три простаивающих Zed — это
примерно десять ядер, занятых рисованием того, на что никто не смотрит,
рядом с 1С, Конфигуратором и анализаторами.

## GPU: что получилось и что нет

| Среда | GPU в Zed | Чем ограничено |
|---|---|---|
| WSL-дистрибутив `Ubuntu-24.04`, Zed напрямую | **работает** | через GL, не через Vulkan |
| WSL2 + наш контейнер (стенда разработчика) | **не работает** | dxg без графического адаптера + Xvfb без DRI2/DRI3 |
| Linux-сервер + NVIDIA (пилот) | **должно работать** | не проверено: нужен сервер с картой |

### WSL2: почему Vulkan не работает, а GL работает

WSL2 отдаёт GPU через `/dev/dxg`, поверх него доступны два пути.

**Vulkan (Mesa Dozen, `dzn`).** Адаптер виден и работает:

```
vulkaninfo --summary  →  deviceName = Microsoft Direct3D12 (NVIDIA GeForce RTX 3060 Ti)
                          driverName = Dozen
```

Но Zed через wgpu требует четыре расширения: `VK_KHR_push_descriptor`,
`VK_KHR_descriptor_update_template`, `VK_EXT_inline_uniform_block`,
`VK_KHR_dynamic_rendering`. **Dozen отдаёт только два средних** — двух
недостающих у него нет (проверено `vulkaninfo` по списку расширений
устройства). wgpu отбрасывает адаптер, и живой Zed пишет:

```
gpui_wgpu::wgpu_context  Found 1 GPU adapter(s):
                            - llvmpipe (LLVM 20.1.8, 256 bits) (backend=Gl, type=Cpu)
zed::zed                 Using GPU: ... is_software_emulated: true
```

В Mesa 26.1 (release notes, май 2026) dzn этих расширений всё ещё не
получил: починится только в Mesa. Обойти на стороне Zed нельзя — набор
расширений задан его графическим слоем.

**GL (Mesa gallium поверх Direct3D12).** Работает, и это полноценный GPU:

```
GALLIUM_DRIVER=d3d12 zed
gpui_wgpu::wgpu_context  Selected GPU adapter: "D3D12 (NVIDIA GeForce RTX 3060 Ti)" (Gl)
zed::zed                 Using GPU: is_software_emulated: false,
                                      device_name: "D3D12 (NVIDIA GeForce RTX 3060 Ti)"
```

Требует WSLg-X-сервера (`:0`) и Mesa с `d3d12_dri.so`; в контейнер путь не
переносится (см. ниже). Для стенда это не решение: проект лежит в Docker-volume
`dev1c-home`, а не в файловой системе дистрибутива.

### Контейнер на WSL2: две независимые преграды

1. **Графического адаптера dxg нет.** В ядре WSL:

   ```
   misc dxg: dxgk: dxgkio_is_feature_enabled: Ioctl failed: -22
   misc dxg: dxgk: dxgkio_query_adapter_info: Ioctl failed: -22
   ```

   WSLg есть только у `Ubuntu-24.04` (`/mnt/wslg`), у дистрибутива
   `docker-desktop`, где живёт наш Docker, — его нет. D3D12 в контейнере
   падает на `ID3D12DeviceFactory::CreateDevice failed`.
2. **Xvfb без DRI2/DRI3.** Контейнер рисует в Xvfb `:99`; GL-путь через
   `d3d12_dri.so` (в образе он есть) не поднимается:
   `libEGL warning: egl: failed to create dri2 screen`.

Вывод: на машине разработчика GPU в контейнере получить нельзя. Лечение
процессора здесь — закрытая панель проекта и ограниченный git (отдельная
спека), а не видеокарта.

### Linux-сервер с NVIDIA: что уже готово

| Что | Где | Состояние |
|---|---|---|
| `NVIDIA_VISIBLE_DEVICES=all` | `Dockerfile:602` | есть |
| `NVIDIA_DRIVER_CAPABILITIES=compute,utility,graphics` | `Dockerfile:603` | есть — `graphics` и есть то, что даёт Vulkan ICD |
| `libvulkan1`, `mesa-vulkan-drivers` | `Dockerfile:84` | есть (загрузчик Vulkan) |
| `gpu = true` → `--gpus all` (docker) / `--device nvidia.com/gpu=all` (podman) | `setup/dev1c-setup/src/ops.rs:84-90` | есть |
| `ZED_ALLOW_EMULATED_GPU=1` | `Dockerfile:606` | есть; наличие настоящего GPU не блокирует |
| `vulkan-tools` (`vulkaninfo`) в образе | — | **нет**, добавить: без него проверка не штатная |

В контейнер драйвер не ставится: NVIDIA Container Toolkit подтягивает с
хоста `nvidia_icd.json`, `libGLX_nvidia.so`, `libnvidia-glvkspirv.so`,
`libcuda.so`. Capability `graphics` — самая частая причина «карта проброшена,
а толку нет»: по умолчанию `compute,utility`, и тогда ни Vulkan, ни GL.

Xvfb в контейнере остаётся: для Vulkan/XCB DRI3 не нужен, программным будет
только вывод готового кадра в буфер Xvfb — сама отрисовка Zed уходит на GPU.

## Требования к хосту

1. **Драйвер NVIDIA не ниже 525.** Нужен `VK_KHR_dynamic_rendering`
   (с 525); остальные нужные расширения отдаются давно. Практически — любой
   современный драйвер (535+).
2. **На хосте должен быть Vulkan ICD драйвера:**

   ```
   ls -l /usr/share/vulkan/icd.d/nvidia_icd.json
   ```

   На Ubuntu он входит в обычный `nvidia-driver`; на RHEL/Fedora — в отдельный
   пакет `nvidia-vulkan-icd`. Compute-only вариант драйвера (без графической
   части) ICD может не содержать — тогда GPU в контейнере не заведётся.
3. **NVIDIA Container Toolkit** (уже едет в комплекте) и запуск контейнера с
   `--gpus all` (или `gpu = true` в `dev1c.toml`).
4. **CUDA 12.8 или новее** — это отдельное требование сервера модели
   (`УСТАНОВКА.md`), к GPU в Zed отношения не имеет.

## Что менять

1. **Добавить `vulkan-tools` в образ** — чтобы «есть ли GPU в контейнере» was
   штатной проверкой, а не разовой ручной командой.
2. **Проверка в комплекте:** `vulkaninfo --summary` внутри контейнера должен
   называть устройство NVIDIA, а не `llvmpipe`; в `Zed.log` — строка
   `Using GPU: ... is_software_emulated: false`.
3. **Закрыть панель проекта по умолчанию** — работает везде, включая WSL, и
   снимает сотни процентов процессора. Настройка образа, доезжает до всех
   рабочих мест одной сборкой.
4. **Ограничить git двумя ядрами** — см. спеку
   `docs/superpowers/specs/2026-10-22-zed-git-cpu-cores-design.md`.

## Проверки приёмки

1. На пилоте: `vulkaninfo --summary` в контейнере называет NVIDIA.
2. В `Zed.log`: `Using GPU: GpuSpecs { is_software_emulated: false, ... }`.
3. Замер простоя Zed (скрипт из начала спеки) — не больше 10 % одного ядра на
   рабочем месте, не больше половины ядра на три места вместе.
4. На машине разработчика под WSL2: GPU в контейнере отсутствует — это
   ожидаемо и проверяемо (шаг 1 «Коротко»); в контейнере остаётся программный
   рендер, и CPU лечится закрытой панелью проекта и ограниченным git.
5. В WSL-дистрибутиве (без контейнера) — GPU есть: `GALLIUM_DRIVER=d3d12`
   даёт `is_software_emulated: false`.

## Что остаётся за рамками

- **Патчи Zed.** Исходников в репозитории нет, собирать Zed из исходников —
  отдельный проект. Диагноз «панель проекта» и GPU-путь снимают нагрузку без
  этого.
- **Покупка карт под стенд разработчика.** Проброс WSL-графики в контейнер
  упирается в dxg и DRI3, а не в отсутствие карты.
- **Фоновая работа git.** GPU её не отменяет — см. отдельную спеку.

# Среда разработки 1С на сервере

Комплект поднимает на одном сервере два контейнера:

- **среда** — рабочие места 1С по RDP (`dev1`, `dev2`, `dev3`), Gitea с репозиториями, SSH для туннеля к инструментам 1С;
- **сервер модели** — локальная модель для агентов в редакторе, на видеокарте этого же сервера.

Сервер закрыт от интернета: всё, что нужно, едет в комплекте, кроме файла
модели и того, что ставит администратор сервера (см. ниже). Дальше —
Ubuntu 24.04, x86-64, права `sudo`.

Весь разговор с комплектом идёт одной программой `dev1c-setup`. Она же, если
двоичный файл в контуре не разрешён, напечатала раздел «Ручной путь» в конце
этой страницы: те же действия командами `docker`.

## Что нужно до начала

**1. Docker Engine уже установлен и отвечает.** Движка в комплекте нет — он
ставится до нас, и на сервере без интернета пакеты приносят с собой. Подойдёт
любой из двух наборов:

- пакеты Ubuntu 24.04: `docker.io`, `containerd`, `runc`;
- пакеты Docker (`download.docker.com`): `docker-ce`, `docker-ce-cli`,
  `containerd.io` — вместе с их зависимостями.

Проверка на месте:

    docker version                 # должен ответить раздел Server
    dpkg -l | grep -E 'docker|containerd'

Если видно «permission denied» — пользователь не в группе `docker`:

    sudo usermod -aG docker $USER      # и войти заново (или newgrp docker)

**2. Драйвер NVIDIA уже установлен на самом сервере.** Драйвера в комплекте
нет: он подбирается под карту, этим занимается администратор сервера. В
Ubuntu пакет называется `nvidia-driver-<номер>-server` (серверный вариант, без
графической части) — номер берётся тот, что поддерживает вашу карту **и не
ниже 525**.

    nvidia-smi                     # модель карты, память, версия драйвера
    dpkg -l | grep nvidia-driver

**525 — это нижняя граница, а не пожелание:** редактору (Zed) нужен Vulkan с
расширением `VK_KHR_dynamic_rendering`, более старые драйверы его не отдают, и
редактор уходит на программную отрисовку (процессор вместо видеокарты).

Нужна и **графическая часть драйвера** — в ней лежит Vulkan ICD драйвера
(`nvidia_icd.json`), именно его ищет редактор и именно его контейнер видит
через NVIDIA Container Toolkit. Проверьте, что файл на месте:

    ls -l /usr/share/vulkan/icd.d/nvidia_icd.json

Файла нет — драйвер поставлен без графической части (compute-only), и
видеокарта в контейнере не заведётся. Доустановите графическую часть: на
Ubuntu — пакет `nvidia-driver-libs-<номер>` (или полный `nvidia-driver-<номер>`),
на RHEL/Fedora — `nvidia-vulkan-icd`.

В заголовке `nvidia-smi` есть «CUDA Version» — нужно **12.8 или новее**: образ
сервера модели собран с CUDA 12.8. Ядра в образе собраны под Ampere (30xx) и
Blackwell (50xx), для остальных карт новее Turing драйвер собирает их сам при
первом запуске — это добавляет минуту к первому старту сервера модели.

**3. NVIDIA Container Toolkit — он в комплекте.** Без него карту видит
операционная система, но не контейнер:

    sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker

**4. Файл модели.** Сперва загляните в каталог `model/` комплекта — модель
может уже лежать там, и тогда в `dev1c.toml` она уже названа:

    [model]
    file = "model/GLM-4.7-Flash-UD-Q4_K_XL.gguf"

Если каталог пуст, `.gguf` приносит заказчик: файл весит гигабайты и
выбирается под карту. Положите его в комплект и назовите так же — путь
относительно каталога комплекта.

Пока имя пусто, установка останавливается словами «модель не выбрана:
`[model] file` — файл в комплекте». Файл копируется в том `dev1c-models` на
установке, из каталога комплекта его потом можно убрать.

**5. Четыре порта подряд свободны.** Первый задан в `dev1c.toml`
(`[server] port`, по умолчанию 3390), дальше по порядку: RDP, Gitea, сервер
модели, SSH для туннеля — 3390, 3391, 3392, 3393. Заняты — поставьте другой
блок (см. «Правка dev1c.toml»).

**6. Оперативная память — не меньше 32 ГБ.** Делит её установка сама, на три
части. Контейнеру среды — предел из `[server] memory`; в комплекте это `8g`.
Хосту и движку контейнеров — 2 ГБ. Остаток целиком получает контейнер сервера
модели, и половина его предела (но не больше 8 ГБ) уходит под кэш подсказок.
Для 32 ГБ выходит так:

    контейнер среды    8192 МиБ   — [server] memory
    хост и docker      2048 МиБ
    сервер модели     22528 МиБ   — из них 8192 МиБ кэш подсказок,
                                    с подкачкой до 45056 МиБ

Те же два числа программа печатает строкой «память: контейнеру среды … МиБ,
серверу модели … МиБ» в плане установки — то есть при `./dev1c-setup install`
(в том числе `--dry-run`). `status` перечисляет операции и их состояние, но
плана не строит, и этой строки там нет. Памяти меньше 32 ГБ — считается то же самое от меньшего
остатка; `[server] memory` и сервер модели делят одну машину, и каждый
гигабайт среде — гигабайт не серверу модели. Предел серверу модели можно
задать и прямо, тогда от памяти машины он не считается:
`[model] memory = "16g"` (не меньше 4096 МиБ).

**7. Файл подкачки на хосте — 64 ГиБ.** Кэш подсказок при переполнении
уезжает в подкачку хоста, а не убивает сервер модели вместе со всеми
сеансами: контейнер запускается с `--memory-swap` вдвое больше предела. 64 ГиБ
— это расчёт стенда: три пользователя по три сеанса на 250 000 токенов, и
контрольные точки спящих сеансов живут в оперативной памяти и подкачке.
В Ubuntu 24.04 по умолчанию подкачки около 2 ГБ, этого мало.

    swapon --show                               # сколько есть сейчас
    sudo fallocate -l 64G /swapfile && sudo chmod 600 /swapfile
    sudo mkswap /swapfile && sudo swapon /swapfile
    echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # после перезагрузки

`./dev1c-setup check` печатает факт «файл подкачки», но ругается только ниже
предела контейнера модели (на стенде это 22 ГБ) и ругается предупреждением, а
не отказом: установка пройдёт и с маленькой подкачкой — умрёт потом сервер
модели со всеми сеансами разом.

**8. Видеопамять.** Модель живёт целиком на карте, и окно контекста — тоже. В
видеопамяти должны поместиться: файл `.gguf` целиком, KV-кэш всех слотов и
запас 1–2 ГБ, который сервер оставляет на чужую нагрузку (2 ГБ, если на карте
уже что-то есть). Кэш — не одно окно: слотов три, у каждого свой, поэтому
нижняя граница просится у карты умноженной на слоты — `[model] fit_ctx × 3`:
при умолчании 81920 это 245 760 токенов KV, а не 81 920. Сколько окна дать на
самом деле, решает сам сервер (`--fit`), и наше число — только минимум. Сколько это гигабайт — зависит от модели (размер KV
на токен у разных моделей отличается в разы), и установка считает это сама,
по числам, которые сообщил сервер.

Не помещается — установка останавливается и называет все числа сразу (см.
«Когда не получилось»). Снизить запрос: `./dev1c-setup change
model.fit_ctx=...`. Карта, занятая чем-то ещё (рабочий стол, другая модель),
отдаёт настолько меньше: `./dev1c-setup check` печатает занятую и полную
память карты.

**9. Место на диске.** Образ едет архивом (`dev1c-image.tar.gz`) и после
`docker load` занимает в `/var/lib/docker` примерно столько же ещё раз.
Модель — отдельно, в томе. Тома лежат там же, в `/var/lib/docker`.

## Что скопировать и куда

Комплект копируется целиком, одним каталогом — программа ищет свои файлы
рядом с собой:

    scp -r dev1c-kit-linux <логин>@<сервер>:/srv/dev1c-kit

Или флешкой — тогда скопируйте каталог в `/srv/dev1c-kit`. Все команды
дальше выполняются из этого каталога:

    cd /srv/dev1c-kit
    chmod +x dev1c-setup            # если бит исполнения потерялся по дороге

## Проверить, что довезли целиком

    sha256sum -c checksums.txt

Каждая строка должна кончаться на `: OK`. В списке нет `dev1c.toml` — его
правят на месте, и его сумма менялась бы от каждой правки. То же самое
проверкой из комплекта: `./dev1c-setup verify`.

Битый или недовезённый файл — копируйте комплект заново; архив образа на
гигабайты обрывается чаще всего.

## Правка dev1c.toml

Обязательное — одно: `[model] file`. Остальное имеет значения по умолчанию,
и каждое поле в файле объяснено комментарием рядом. Правки удобнее делать
программой: она проверяет значение и применяет только то, что разошлось.

    ./dev1c-setup change port=4000           # другой блок портов
    ./dev1c-setup change memory=12g          # предел памяти контейнера среды

## Три команды

    ./dev1c-setup status     # что уже есть и что мешает; на машине ничего не меняет
    ./dev1c-setup install    # грузит образ, создаёт тома, копирует модель,
                             # поднимает и замеряет сервер модели, собирает
                             # контейнер среды, ждёт его службы и проверяет
    ./dev1c-setup check      # проверки по фактам; отчёт — last-check.txt

`install` на чистом сервере идёт долго: архив образа — минуты, копирование
модели в том — минуты, замер сервера модели — до пяти минут (модель читается
с диска на карту). Повторный запуск делает только то, чего не хватает.

Все три идут и одной строкой по SSH, без входа на сервер:

    ssh сервер '/srv/dev1c-kit/dev1c-setup install'

Вывод вы увидите полностью — он идёт в вашу же консоль, шаг за шагом, как при
запуске на самом сервере. Отличие одно: в таком запуске программа не задаёт
вопросов. Спрашивать там некого — ответ некому ввести, и вопрос висел бы до
утра, поэтому подтверждения берутся по умолчанию. Исключение — удаление
данных: оно без терминала не делается молча и просит ключ `--yes`.

## Что нормально увидеть

До установки `status` показывает не «всё плохо», а список того, что ещё не
сделано, и того, что пока нельзя. «Нельзя» означает одно: шаг ждёт результата
другого шага, который `install` выполнит раньше него. На чистом сервере это
норма.

Вот как это выглядит на комплекте, собранном как обычно — модель лежит в
`model/` и названа в `dev1c.toml`:

    Комплект: /srv/dev1c-kit

      image      Образ среды          не сделано
      volumes    Тома данных          не сделано
      payload    Платформа 1С и демо-база  не сделано
      model      Файл модели          не сделано
      llama.container Контейнер модели  нельзя: образ oktaplus/dev1c-llama:latest не загружен: он едет в dev1c-llama-image.tar.gz — выполните шаг «Образ среды»
      container  Контейнер среды      нельзя: сервер модели ещё не замерен (шаг llama.answers); без его чисел контейнер собирать нельзя

    Применить то, чего не хватает: dev1c-setup install

Если модели в комплекте нет и `[model] file` в `dev1c.toml` пуст, добавляются
ещё два «нельзя» — про невыбранную модель, у шагов `model` и
`llama.container`. Это единственный случай, когда «нельзя» требует вашего
действия: назовите файл модели, и обе строки уйдут.

Оставшиеся два «нельзя» ждут того, что `install` делает раньше них: загружает
образ из архива и замеряет сервер модели. После установки в этих строках стоит
«сделано».

В конце `install` — адреса, которые диктуют разработчикам (адрес сервера
программа подставляет свой):

    Среда запущена:
      Рабочие места   mstsc /v:192.168.1.10:3390  —  dev1/dev1, dev2/dev2, dev3/dev3
      Репозитории     http://192.168.1.10:3391
      Сервер модели   http://host.docker.internal:3392/v1 (GLM-4.7-Flash-UD-Q4_K_XL)
      Для 1c-connect  192.168.1.10:3393

`check` — нумерованный список фактов; `[info]` — не провал, а сведение. Ниже
несколько строк из середины списка, чтобы было видно форму:

      1. [ ok ] движок контейнеров: docker 29.8.2
      2. [ ok ] контейнер: работает
      3. [ ok ] рабочие места (RDP): порт 3390 принимает соединение
      4. [ ok ] Gitea: http://127.0.0.1:3391/ отвечает 200
      ...
     [ ok ] видеокарта: NVIDIA RTX ..., занято ... МиБ, драйвер ...
     [ ok ] модель в настройках Zed: провайдер llama.cpp, модель ...

    Проверок пройдено 17, провалено 0. Отчёт: /srv/dev1c-kit/last-check.txt

Номера строк не ищите: порядок фактов меняется вместе с программой. В файле
отчёта итог записан короче — «Пройдено 17, провалено 0.».

## Как подключаться к рабочему месту

Подключение по RDP на адрес сервера и порт рабочих мест (в комплекте 3390).
Пользователи — `dev1`, `dev2`, `dev3`, у каждого свой рабочий стол и своя
ветка в Gitea. Пароль совпадает с именем.

Логин и пароль спрашивает **окно самого стенда**, а не Windows, и так будет
всегда: сохранённый пароль Windows отдаёт только серверу, который сам себя
удостоверил (NLA), а у RDP-сервера стенда такой поддержки нет. Галочка
«Разрешить мне сохранять учётные данные» в клиенте работать не будет — это не
поломка установки.

В окне стенда **всегда латиница**, какая бы раскладка ни стояла в Windows.
Так сделано нарочно: переключателя в том окне нет вовсе (его рисует сервер
RDP, а не рабочий стол Linux), а логины и пароли у рабочих мест латиницей.

Внутри сеанса раскладок две, `us` и `ru`, переключение — Alt+Shift, текущая
видна в правом нижнем углу.

## Чат с моделью, без агента

У сервера модели есть собственный веб-интерфейс — обычный чат. Он для случаев,
где агент не нужен вовсе: проверить формулировку, перевести кусок текста,
разобрать письмо, попробовать модель «как она есть».

На рабочем столе для этого ярлык **«Чат с моделью»**. Он открывает браузер по
адресу сервера модели — адрес ярлык берёт из переменных сеанса, а не зашит,
поэтому порт у каждой установки свой и править ничего не надо.

Ключа сервер не спрашивает: порт опубликован на адресе моста `docker0`, то
есть снаружи сервера недоступен, а встроенный интерфейс llama.cpp посылать
ключ не умеет — с ключом чат был бы невозможен.

Чат и агенты делят одну модель и одни и те же места (слоты): три. Долгий
разговор в чате занимает место так же, как работа агента.

## Как работать с агентом

Агент на рабочем месте доступен двумя способами, и это один и тот же агент с
одними знаниями: панель в редакторе Zed и команда `pi` в терминале. `pi`
запускают **вместо** панели, а не рядом; у него терминальный вид и сессия,
которая сама сжимается, когда окно заполняется.

## Когда не получилось

Программа называет преграду и команду, которая её снимает — на сервере без
интернета спросить нас по ходу не выйдет. Что встречается:

- «Docker отвечает «в доступе отказано»: пользователь не в группе docker» —
  `sudo usermod -aG docker $USER`, затем войти заново.
- «Служба Docker не отвечает: демон не запущен или сокет недоступен» —
  `sudo systemctl restart docker`.
- «Драйвер NVIDIA на сервере не отвечает (nvidia-smi молчит)» — карту не видит
  сама операционная система. Из комплекта это не лечится: нужен администратор
  сервера с драйвером под эту карту.
- «Драйвер на сервере работает, но видеокарта не видна внутри контейнера» —
  `sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker`.
- «Не найден архив платформы: …» — в комплекте нет
  `dev1c-1c-payload.tar.gz`, а без него не будет ни платформы 1С, ни
  демо-базы. Комплект довезли не целиком — берите заново.
- «Не найден архив образа: …» или «Не найден файл модели: …» — в сообщении
  назван путь, куда программа смотрела. Архив — значит комплект довезли не
  целиком; файл модели — значит `.gguf` не лежит в каталоге комплекта под тем
  именем, что в `dev1c.toml`.
- «модель не выбрана: `[model] file` — файл в комплекте» — пункт 4 выше.
- «образ oktaplus/dev1c-llama:latest не загружен: он едет в
  dev1c-llama-image.tar.gz — выполните шаг «Образ среды»» — сервер модели
  приезжает **своим** архивом, и загружает его тот же `./dev1c-setup install`.
- «сервер модели ещё не замерен (шаг llama.answers); без его чисел контейнер
  собирать нельзя» — сначала должен подняться сервер модели: контейнер среды
  получает его числа переменными.
- «сервер дал 54000 токенов на слот при нижней границе fit_ctx = 81920 (3
  слота): на этой карте модель с такими параметрами не помещается» — карты не хватает
  на такую модель с таким окном. Либо модель меньше или с более плотным
  квантованием, либо ниже граница:
  `./dev1c-setup change model.fit_ctx=...`.
- «порт N занят другой программой — задайте другой блок:
  `dev1c-setup change port=4000`».

Куда смотреть:

- `setup.log` в каталоге комплекта — все команды движка и их вывод, по порядку;
- `last-check.txt` — отчёт последней проверки;
- `docker logs dev1c-llama` — сервер модели (почему не поднялся, какое окно взял);
- `docker logs dev1c` — среда (gitea, xrdp, sshd).

Снять среду: `./dev1c-setup clean --stack` — контейнеры, данные на месте.

`./dev1c-setup clean --data --yes` — это НЕ только контейнеры. Уходят все пять
томов: рабочие места (`home` — проекты, настройки, скиллы, сессии агента),
репозитории (`gitea`), файл модели (`models`), платформа 1С (`platform`) и
демо-база (`demo`), а вместе с ними и образ стенда. Платформу и демо-базу
потом возвращает только `dev1c-1c-payload.tar.gz` из комплекта — если
комплект уже убрали с сервера, возвращать будет нечем.

## Ручной путь

Этот раздел печатает сама программа при сборке комплекта: ниже — те же
команды, которые выполнил бы `./dev1c-setup install`, в том же порядке. Они
для случая, когда наш двоичный файл в контуре запускать не станут.

Перед тем как вставлять:

- выполняйте из каталога комплекта: пути в командах относительные;
- `.gguf` лежит в каталоге комплекта под тем именем, что в `dev1c.toml`; ниже
  он назван `модель.gguf`, подставьте своё;
- значения портов, имён и предела памяти в командах взяты из `dev1c.toml` того
  комплекта, с которым приехала эта страница; поправили `dev1c.toml` — правьте
  и команды;
- **ключа у сервера модели нет** — ни в комплекте, ни в командах. Порт он
  публикует на адресе моста `docker0`, то есть снаружи сервера недоступен, а
  ключ закрывал бы только тех, кто уже на нём. Взамен он отнимал веб-чат
  (см. «Чат с моделью» ниже): послать ключ встроенный интерфейс llama.cpp не
  умеет;
- `docker rm -f …` на первой установке отвечает «No such container» — так и
  должно быть, дальше по списку;
- `-p <адрес>:3392:8080` — адрес моста `docker0` этой машины; в командах стоит
  тот, что был на машине сборки комплекта. Свой: `docker network inspect
  bridge -f '{{(index .IPAM.Config 0).Gateway}}'`. Этот же адрес — тот, по
  которому сервер модели потом отвечает: подставьте его и в команды;
- **последняя команда неполна.** `docker run` контейнера среды напечатан без
  четырёх переменных модели (`MODEL_PROVIDER`, `LLAMA_API_URL`,
  `LLAMACPP_API_KEY`, `MODEL_NAME`): до замера сервера модели их никто не
  знает. Имена `CUSTOM_*` остались в прошлом — они у формы `remote`, то есть
  у чужого сервера, а комплект поднимает свой.
  Вставите список как есть — среда поднимется, рабочие места и репозитории
  заработают, а агент в редакторе промолчит. Что дописать — в разделе «Шаг,
  который нельзя вставить» сразу после команд;
- `--cache-ram` и `--fit-target` — числа, посчитанные на машине сборки
  (половина предела контейнера модели под кэш подсказок; запас на карте под
  чужую нагрузку). Работать будет и так; под сервер их считает
  `./dev1c-setup install`;
- **`--memory`, `--memory-swap` и `--memory-reservation` вместо чисел несут
  заглушки** `<ПРЕДЕЛ>m`, `<ПРЕДЕЛ×2>m`, `<ПРЕДЕЛ÷2>m` — и это единственные
  числа, которые нельзя оставить как есть. Предел считается от памяти
  сервера, а комплект собран на другой машине; вставленная заглушка
  остановит `docker` с ошибкой — так и задумано. Посчитайте свой:
  `<ПРЕДЕЛ>` = вся память сервера − предел контейнера среды (`memory` в
  `[server]`) − 2 ГБ хосту. Для 32 ГБ и `memory = "8g"` это 22528 МиБ,
  `--memory-swap 45056m`, `--memory-reservation 11264m`. Без предела кэш
  подсказок сервера модели выдавит в подкачку всю машину, включая 1С. Если в
  `[model] memory` комплекта предел уже вписан (в комплекте там пусто), то
  заглушек в команде нет: стоит ваше число, и считать нечего.

@MANUAL-PATH@

### Шаг, который нельзя вставить: числа модели

Сколько модель получит контекста, решает не комплект, а карта: сервер модели
подбирает окно сам, под то, что на карте свободно. Поэтому последний шаг —
единственный, который нельзя приготовить заранее.

Поднимите сервер модели (команда выше) и спросите его. Ключ не нужен — сервер
его не спрашивает. Адрес и порт — те самые, что стоят в `-p <адрес>:3392:8080`
в команде сервера модели выше: на петле (`127.0.0.1`) он не отвечает, порт
опубликован на адресе моста `docker0`.

    curl -s http://<адрес из -p>:3392/props

В ответе `default_generation_settings.n_ctx` — контекст ОДНОГО слота в токенах,
который карта дала на самом деле (сервер сообщает именно долю слота, не весь
пул). Делить его на слоты не надо.

Числа для редактора считать больше не нужно: с версии 2026-10-21 среда
работает через штатный провайдер Zed `llama.cpp`, а он забирает окно с того же
`/props` сам. Раньше здесь стояли три формулы (`окно агента`, `ответ`,
`max_tokens`) и предупреждение, что Zed просит ответ сверх входа; всё это
ушло вместе с объявлением чисел.

Проверить осталось одно: хватает ли окна агенту.

    окно агента = n_ctx ÷ agents     (`agents` из `dev1c.toml`, в комплекте 1)

Оно обязано быть не меньше 81920 токенов: 49152 на вход и 32768 на ответ.
Ответ такой большой потому, что модель размышляет, а размышления расходуют
выходные токены: при скупом пределе ответ приходит пустым.
Вход такой большой потому, что 32 000 токенов агент занимает ещё до первого
вопроса — правила, описания скиллов и схемы инструментов (Zed показывает это
число в диалоге); остальное уходит на сам код, модуль в 100 КБ это около
40 000 токенов. Слот — у
человека, и несколько агентов одного человека делят его слот, поэтому делить
надо именно так. При `agents = 1` (комплект уезжает так, и на стенде так и
остаётся) окно агента равно контексту слота.

Если окно слота вышло меньше `fit_ctx` из `dev1c.toml` — модель на этой карте
с таким окном не помещается, и дальше идти незачем: это ровно тот отказ,
которым останавливается и `install`.

Программа печатает вышедшее строкой:

    [ ok ] сервер отвечает: <имя>, 3 слота по 250000 токенов; на агента 250000

Адрес сервера модели и имя модели дописываются к `docker run` контейнера среды
четырьмя переменными — их нет в командах выше, потому что до замера их никто
не знает. Без них среда поднимется и редактор будет работать, а агент
промолчит:

    -e MODEL_PROVIDER=llama.cpp     -e LLAMA_API_URL=http://host.docker.internal:3392     -e LLAMACPP_API_KEY=<ключ из llama.env>     -e MODEL_NAME=<имя модели: --alias из команды сервера модели>

Адрес здесь — КОРЕНЬ сервера, без `/v1`: провайдер сам ходит в `/props` и
`/v1/models`. Имя переменной ключа диктует Zed — он ищет
`<ПРОВАЙДЕР>_API_KEY`, поэтому `LLAMACPP_API_KEY`, а не наше название.

Чужой OpenAI-совместимый сервер (не llama.cpp) штатный провайдер не понимает.
Для него остаётся прежняя ветвь, и там числа окна объявляются по-прежнему,
потому что взять их с такого сервера нельзя:

    -e MODEL_PROVIDER=custom     -e CUSTOM_API_URL=https://<адрес>/v1     -e CUSTOM_API_KEY=<ключ>     -e MODEL_NAME=<имя модели>     -e CUSTOM_MAX_TOKENS=<вход>     -e CUSTOM_MAX_OUTPUT_TOKENS=<ответ>

Внутри контейнера эти переменные подставляются в настройки редактора. Если
среда уже собрана без них — пересоберите контейнер среды той же командой с
добавленными `-e`: тома, а с ними репозитории и проекты, остаются на месте.

Проверить вышедшее можно и чужими руками: `./dev1c-setup check` смотрит на те
же факты — отвечает ли сервер модели, подставлены ли провайдер и модель в
настройки редактора, хватает ли окна агенту.

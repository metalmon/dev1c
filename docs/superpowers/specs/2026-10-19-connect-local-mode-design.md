# `1c-connect`: переключатель MCP и локальный режим

Дата: 2026-10-19. Ветка `main`. Поверх спек окна
(`2026-10-16-gpui-connect-design.md`, раздел «Режим работы»), демо-стенда
(`2026-10-19-demo-stand-design.md`) и user flow (`2026-10-18-user-flow.md`,
пп. 1 и 2 «куда гребём не туда»).

## Зачем

У разработчика один агент в Zed и несколько проектов, у каждого своя база.
Сегодня, чтобы агент смотрел на другую базу, надо править настройки Zed или
держать поднятыми отдельные MCP под каждый проект. `1c-connect` становится
органом управления этой обвязкой: **один переключатель включает MCP для
текущего проекта**, база и каталог исходников задаются в его же «Параметрах»,
смена проекта — смена полей и «Сохранить». Настройки Zed не трогаются
никогда: там навсегда `nc localhost 777N` и `778N`.

То же окно, тот же переключатель и та же логика работают в двух местах:

- **туннельный режим** (Windows рядом с реальной базой): MCP включены =
  туннель в среду поднят и мосты принимают подключения;
- **локальный режим** (внутри образа, стенд с учебной платформой или любая
  платформа на той же машине): MCP включены = `1c-connect` сам слушает
  `777N`/`778N` на loopback и на каждое подключение Zed запускает
  `mcp-1c`/`vrunner-mcp` на текущую базу. Туннеля и SSH нет.

Ограничение учебной платформы «один сеанс Предприятия на базу» — частный
случай, не повод для особой механики: если вызов агента упёрся в лимит
(человек держит 1С открытой), ошибка платформы идёт строкой в журнал и
ответом агенту как есть. С обычной платформой всё работает так же, просто
без этой ошибки.

## Цели

- Переключатель «MCP» в карточке состояния с одним смыслом в обоих режимах.
  Выключено — порты закрыты, Zed показывает серверы упавшими и сам
  переподключается, когда включат (решение заказчика 2026-10-19).
- Смена проекта/базы через «Параметры» + «Сохранить»: следующее подключение
  Zed получает MCP уже на новую базу.
- Локальный режим как полноценный: мосты, установка расширения, проверка,
  журнал — без SSH, с линуксовыми путями и учебным конфигуратором.
- Стенд перестаёт держать свои socat-мосты: `777N`/`778N` принадлежат
  `1c-connect`.

## Не-цели

- Списки баз, профили проектов, «последние базы» — нет. Одна активная база,
  одно поле.
- Пауза агента, автоматическое закрытие 1С, арбитраж «агент или человек» —
  нет. Переключатель включает и выключает MCP, остальное — ошибки платформы
  в журнале.
- Кнопка «Открыть Zed» — не здесь (user flow п. 2 решается отдельно; внутри
  образа Zed и так главное окно).
- Серверные базы (`сервер\база`) — поле принимает, проверка подключения —
  как сейчас; отдельной работы здесь нет.
- Ничего из перечисленного не зависит от ОС: локальный режим
  проектируется **сразу под Linux и под Windows** (решение заказчика
  2026-10-19). На Windows он тоже сценарий: человек поставил образ рядом с
  собственной базой на той же машине — туннель ему не нужен, MCP слушают
  loopback, `1cv8.exe` и база местные. Разница ОС живёт в трёх местах:
  поиск платформы, уборка дочерних процессов и публикация (на Windows её
  по-прежнему делает человек, см. ниже).

## Анти-цели

- Правка `settings.json` Zed из `1c-connect`.
- Второй набор команд и экранов для локального режима. Разница режимов —
  в одном модуле «как доставить stdio MCP на порт», остальное общее.
- Опрос по таймеру там, где есть событие.

## Что есть сейчас (проверено по коду и стенду)

| Часть | Как работает | Что мешает |
|---|---|---|
| `session::start` (туннель) | поток с tokio: SSH, remote forward `777N`/`778N`/`779N`, на каждый канал — `bridge::pipe_jsonrpc` с `mcp_command`/`vrunner_command`; состояния `Off/Connecting/Up/Retrying/Failed` | весь путь «порт → процесс» живёт внутри SSH-сеанса |
| `bridge::mcp_command(cfg, kit)` | `mcp-1c --base <base_url> --user --password`; `vrunner_command(cfg, tools)` — `oscript … mcp.os` с `cwd = project`; `connection_args(cfg)` подставляет `ibconnection`/`db-user`/`db-pwd` | база берётся из `cfg` в момент запуска процесса — смена базы = перезапуск мостов |
| `cfg::Host.mode` | читается, проверяется (`tunnel`/`local`), сохраняется; поведения нет | — |
| Стенд (`config/1c/stand.sh`) | пишет `1c-connect.toml` с `mode = "local"`, `base_path`, `base_url = http://127.0.0.1:808N/base/hs/mcp-1c`, `project`, `db_user`; публикует базу (`publish`: `default.vrd` + свой Apache на `808N`); слушает `777N`/`778N` через `socat`, запуская `1c-stand mcp N` / `vrunner N`; запускает `1c-connect --tray` при входе | два хозяина у портов; база зашита в скрипт |
| `ops_host::Extension`, `verify::run` | `mcp_exe` различает ОС; `find_1cv8` ищет Windows-платформу; факты проверки — про SSH, `1cv8.exe`, Windows-инструменты | в образе половина фактов не имеет смысла |
| Карточка состояния | одна строка: кружок, заголовок по `session::State`, «Прервать», переключатель туннеля | заголовки говорят о туннеле |

## Решения

### Переключатель = «MCP включены»

Состояние окна — `session::State`, как сейчас, но смысл: `Up` — MCP
принимают подключения, `Off` — порты закрыты. Заголовки карточки:
«MCP выключены» / «Включаю…» / «MCP включены» / «Переподключаю» /
«MCP выключены» (после сбоя — причина строкой в журнал, как сейчас).
Подсказка трея и пункт «Подключить/Отключить» меняют слова на
«Включить MCP / Выключить MCP». Автоподключение при запуске остаётся —
«включать MCP при запуске».

### Два транспорта под одним сеансом

`session::start(cfg, kit, sink, on_state)` выбирает по `cfg.host.mode`:

- `tunnel` — как сейчас (SSH, remote forward, переподключение);
- `local` — `tokio::net::TcpListener` на `127.0.0.1:777N` и `127.0.0.1:778N`;
  на каждое принятое соединение — тот же `bridge::pipe_jsonrpc` с теми же
  `mcp_command`/`vrunner_command`. Состояния: `Connecting` на миг,
  `Up` когда оба слушателя подняты, `Failed(why)` если порт занят («порт
  7771 занят: остановите socat стенда или другой 1c-connect»). `Retrying`
  в локальном режиме не бывает. `779N` (веб) в локальном режиме не нужен:
  веб-клиент базы открывается по `base_url` напрямую (`open_web` берёт
  адрес из `base_url`, а не из `779N`).

**Остановка сеанса обязана убить всё, что родила.** Сегодня это умеет
только Windows (`job::Job` — Job Object), на Linux тот же тип — пустышка,
и в туннельном режиме это сходило с рук: процессы жили на той стороне SSH,
а обрыв сеанса закрывал каналы. В локальном режиме так нельзя:
`oscript`/`vrunner` и платформа держат файловую базу, и забытый процесс
займёт единственный сеанс — ровно то, ради чего всё затевалось. Поэтому:

- закрытие `TcpListener` **не** рвёт уже принятые соединения (в отличие от
  SSH-канала) — сеанс ведёт свой список живых мостов и закрывает их сам;
- каждый мост в локальном режиме запускается в своей группе процессов
  (`setsid`/`CommandExt::process_group(0)` на Linux, Job Object на
  Windows) и при закрытии гасится целиком (`killpg(SIGTERM)`, через 5 с
  `SIGKILL`);
- `job.rs` получает рабочую реализацию для Linux вместо заглушки.

Это не отдельная работа «потом»: без неё локальный режим не считается
сделанным (вывод проверки строителем 2026-10-19).

### Смена проекта = перезапуск сеанса

`save_host` уже перезапускает сеанс после сохранения, если он был поднят
(`stop_session` → `start_session`). Это и есть смена базы: новые мосты
стартуют с новым `cfg`. Zed держит старые stdio-соединения, пока они не
закроются; закрытие слушателя рвёт их, Zed переподключается и получает
MCP на новую базу. В журнал — «MCP перезапущены: база <путь>».

### Публикация в локальном режиме

`mcp-1c` ходит в базу через HTTP-сервис, у активной базы должна быть
публикация. В локальном режиме её ведёт `1c-connect`: операция
`host.publication` (новая строка на вкладке «Проект», рядом с расширением):
пишет `default.vrd` и конфиг Apache рабочего места по образцу стенда
(`1c-stand publish`) и перезапускает этот Apache. Вызывается при
«Сохранить» с изменённым `base_path` (до перезапуска сеанса) и из
«Установить». Решение автора: механика копируется из стенда в Rust
(`ops_host`), а не зовётся скриптом — стенд после этого свою публикацию не
трогает.

**В туннельном режиме операции нет** (решение заказчика 2026-10-19:
«Windows позже»). Сегодня коннектор на Windows публикацию только проверяет
(`ops_host` ищет `base_url/version`, `verify` — порт веб-сервера и ответ
публикации) и отправляет человека в Конфигуратор. Симметрия с локальным
режимом — это `httpport` из спеки установщика и user flow п. 4: на Windows
публикацию делает `webinst` из состава платформы, веб-сервер чужой (Apache
или IIS), нужны права администратора. Отдельная работа после локального
режима.

### Расширение и проверка в локальном режиме

- **`find_1cv8` сегодня безусловно ищет платформу в `Program Files`** — на
  Linux факт «платформа» не «теряет смысл», а падает. Функция становится
  кроссплатформенной: на Windows — как сейчас (каталог версии и bin/1cv8.exe в обоих Program Files),
  на Linux — `/opt/1cv8/x86_64/<версия>/1cv8` (обычная платформа) и
  `/opt/1cv8t/x86_64/<версия>/1cv8t` (учебная, стенд), версии сортируются
  как числа, берётся старшая; путь можно задать руками переменной
  `ONEC_PLATFORM`. Установка расширения — тот же `mcp-1c --install`, бинарь
  по ОС, на Linux под `xvfb-run -a`, если нет `DISPLAY` (конфигуратору
  нужен дисплей).
- Факты `verify::run` по режиму: общие — параметры, платформа, комплект
  инструментов, каталог проекта, Gitea; туннельные — SSH-адрес, `1cv8.exe`;
  локальные — публикация отвечает (`GET base_url/version`), расширение
  установлено, порты `777N`/`778N` слушает именно этот процесс (или
  свободны, если MCP выключены), «1С с этой базой открыта» как `info`
  (не провал: это и есть ситуация лимита, человек должен знать).

### Ошибки платформы — в журнал и агенту

`bridge` уже отдаёт агенту ответ инструмента как есть. Текст лимита
сеансов («превышено предельное количество подключений») проходит без
перевода; окно добавляет строку `Warn` в журнал: «агент не вошёл в базу:
<текст платформы>; если 1С открыта у вас — закройте её». Это единственное
место, где учебная платформа упоминается в поведении, и оно же сработает на
обычной платформе при любом отказе входа.

### Стенд после этого

`1c-stand` перестаёт слушать `777N`/`778N` и запускать `mcp`/`vrunner` сам:
эти ветки скрипта уходят, остаются `seed` (toml, копия бинаря), платформа,
первая публикация при изготовлении образа и `connect` (запуск
`1c-connect --tray`). Toml стенда дополняется `autoconnect` в состоянии
комплекта («включать MCP при запуске» — да), чтобы агент работал сразу
после входа.

### Окно

Меняются слова (переключатель, карточка, трей) и набор строк «Проекта» в
локальном режиме (публикация — только на Linux). Подменю «Режим работы» в
трее — по спеке окна, делается здесь же: выбор пишет `mode` в toml и
перезапускает сеанс.

**Поля «Параметров» зависят от режима** (как и планировала спека окна;
проверка строителем нашла, что эта спека говорила обратное — исправлено):
туннельный — все семь, как сейчас; локальный — только про базу и проект
(каталог базы, пользователь и пароль базы, каталог исходников). Адрес
среды, пароль и имя рабочего места в локальном режиме не показываются:
они ничего не делают. Рабочее место при этом остаётся в toml — от него
считаются номера портов `777N`/`778N`.

## Что остаётся строителю

- Как разделить `session.rs`: `transport::tunnel` / `transport::local` с
  общим `pipe_jsonrpc`, или две ветви в `start` — по размеру кода.
- Детали завершения дочерних процессов мостов на Linux при остановке
  сеанса.
- Формат строки «Проекта» для публикации и тексты фактов проверки по
  режиму.
- Где взять версию платформы для путей `/opt/1cv8t/x86_64/<версия>`:
  каталог единственный — брать первый.

## Проверки

- `session`: локальный транспорт на свободных портах принимает соединение,
  гонит `initialize` в фиктивный mcp-скрипт и закрывается по `stop`; занятый
  порт → `Failed` с текстом; смена `cfg` между сеансами меняет `--base` у
  `mcp_command` (проверяется по аргументам команды).
- `verify`: набор фактов по режиму (тест на два `mode`).
- `ops_host::Publication`: `default.vrd`/конфиг Apache по образцу стенда —
  текстовое сравнение с эталоном.
- Живой прогон на стенде: вход → трей → MCP включены → агент в Zed видит
  базу → человек открывает 1С → вызов агента падает с текстом лимита в
  журнале → закрыл 1С → агент снова работает → сменил базу в «Параметрах»
  → агент на новой базе.

## Решения заказчика (2026-10-19)

- Переключатель включает MCP для текущего проекта; лимит сеансов учебной
  платформы — обычная ошибка в журнале, не особая механика.
- Выключено = порты закрыты, Zed переподключается сам.
- Базу и проект выбирают в «Параметрах», списков баз нет.
- Публикацию активной базы в локальном режиме ведёт `1c-connect`; стенд её
  больше не трогает.
- Автоматическая публикация на Windows (`httpport`, `webinst`) — отдельная
  работа после локального режима.
- Локальный режим проектируется сразу под обе ОС.

Открытых вопросов к заказчику нет.

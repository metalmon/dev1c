# Стенд разработки 1С — установка на сервер

Эта страница — порядок действий. Делайте шаги подряд; у каждого написано,
что вы увидите и что делать, если увидели другое.

Комплект поднимает на одном сервере два контейнера:

- **среда** — три рабочих места 1С по RDP (`dev1`, `dev2`, `dev3`), Gitea с
  репозиториями, SSH для туннеля к инструментам 1С на машине разработчика;
- **сервер модели** — локальная модель для агентов в редакторе, на видеокарте
  этого же сервера.

Сервер закрыт от интернета: всё нужное едет в комплекте. Снаружи ставятся
только две вещи, и обе — до нас: движок контейнеров и драйвер видеокарты.

Требуется: Ubuntu 24.04, x86-64, права `sudo`, видеокарта NVIDIA.

Весь разговор с комплектом идёт одной программой — `dev1c-setup`. Если
запускать чужой двоичный файл в вашем контуре не станут, в конце страницы
лежит «Ручной путь»: те же действия командами `docker`.

## Весь путь на одном экране

    1. Проверить сервер            docker version; nvidia-smi; free -g; swapon --show
    2. Довезти комплект            scp -r … /srv/dev1c-kit; sha256sum -c checksums.txt
    3. Поставить NVIDIA Toolkit    sudo dpkg -i nvidia-container-toolkit/*.deb
    4. Назвать модель              [model] file в dev1c.toml — если ещё не названа
    5. Посмотреть план             ./dev1c-setup status
    6. Поставить                   ./dev1c-setup install
    7. Проверить                   ./dev1c-setup check
    8. Раздать доступы             RDP на порт 3390, логины dev1/dev1 …

Шаги 1–4 делает администратор сервера, 5–7 — кто угодно из каталога
комплекта, 8 — вы, разработчикам.

---

# Шаг 1. Проверить сервер

Шесть требований. Каждое проверяется одной командой; не сошлось — чините
здесь, а не в середине установки.

## 1.1 Движок контейнеров

Движка в комплекте нет: он ставится до нас, и на сервере без интернета
пакеты приносят с собой. Подойдёт любой набор:

- пакеты Ubuntu 24.04: `docker.io`, `containerd`, `runc`;
- пакеты Docker (`download.docker.com`): `docker-ce`, `docker-ce-cli`,
  `containerd.io` — с зависимостями.

    docker version                 # должен ответить раздел Server
    dpkg -l | grep -E 'docker|containerd'

**«permission denied»** — вы не в группе `docker`:

    sudo usermod -aG docker $USER      # и войти заново (или newgrp docker)

## 1.2 Драйвер видеокарты

Драйвера в комплекте нет: он подбирается под карту, этим занимается
администратор сервера.

    nvidia-smi                     # модель карты, память, версия драйвера
    dpkg -l | grep nvidia-driver
    ls -l /usr/share/vulkan/icd.d/nvidia_icd.json

Что должно сойтись:

- **версия драйвера не ниже 525.** Это граница, а не пожелание: редактору Zed
  нужен Vulkan с расширением `VK_KHR_dynamic_rendering`, старые драйверы его
  не отдают, и редактор уходит рисовать процессором;
- **«CUDA Version» в заголовке `nvidia-smi` — 12.8 или новее.** Образ сервера
  модели собран с CUDA 12.8;
- **файл `nvidia_icd.json` на месте.** Это Vulkan ICD драйвера; его ищет
  редактор и его же видит контейнер. Файла нет — драйвер поставлен без
  графической части (compute-only), и видеокарта в контейнере не заведётся.
  Доустановите: Ubuntu — `nvidia-driver-libs-<номер>` или полный
  `nvidia-driver-<номер>`; RHEL/Fedora — `nvidia-vulkan-icd`.

Ядра в образе собраны под Ampere (30xx) и Blackwell (50xx). Для других карт
новее Turing драйвер соберёт их сам при первом запуске — это добавит минуту к
первому старту сервера модели, один раз.

## 1.3 Оперативная память: не меньше 32 ГБ

    free -g

Делит её установка сама, на три части:

    контейнер среды    8192 МиБ   — [server] memory из dev1c.toml
    хост и docker      2048 МиБ
    сервер модели     22528 МиБ   — остаток; из него 8192 МиБ кэш подсказок,
                                    с подкачкой до 45056 МиБ

Эти два числа программа печатает строкой «память: контейнеру среды … МиБ,
серверу модели … МиБ» — в плане установки, то есть при `install`, в том числе
`--dry-run`. У `status` плана нет, и строки там нет тоже.

Памяти меньше 32 ГБ — считается то же самое от меньшего остатка. Среда и
сервер модели делят одну машину: каждый гигабайт среде — гигабайт не серверу
модели. Предел серверу модели можно задать и прямо, тогда от памяти машины он
не считается: `[model] memory = "16g"` (не меньше 4096 МиБ).

## 1.4 Файл подкачки: 64 ГиБ

    swapon --show                               # сколько есть сейчас

В Ubuntu 24.04 по умолчанию около 2 ГБ — мало. Сделать:

    sudo fallocate -l 64G /swapfile && sudo chmod 600 /swapfile
    sudo mkswap /swapfile && sudo swapon /swapfile
    echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # после перезагрузки

Зачем: кэш подсказок при переполнении уезжает в подкачку хоста, а не убивает
сервер модели вместе со всеми сеансами — контейнер запускается с
`--memory-swap` вдвое больше предела. 64 ГиБ — расчёт стенда: три человека по
три сеанса на 250 000 токенов, и контрольные точки спящих сеансов живут в
памяти и подкачке.

`check` печатает факт «файл подкачки», но ругается **предупреждением** и
только ниже предела контейнера модели (на стенде это 22 ГБ): установка
пройдёт и с маленькой подкачкой — потом умрёт сервер модели со всеми
сеансами разом.

## 1.5 Видеопамять

Модель живёт целиком на карте, и окно контекста тоже. В видеопамять должны
поместиться:

- файл `.gguf` целиком;
- KV-кэш **всех трёх слотов** — не одного: нижняя граница просится у карты как
  `[model] fit_ctx × 3`, при умолчании 81920 это 245 760 токенов, а не 81 920;
- запас 1–2 ГБ, который сервер оставляет на чужую нагрузку (2 ГБ, если на
  карте уже что-то есть).

Сколько это гигабайт — зависит от модели: размер KV на токен у разных моделей
отличается в разы. Установка считает это сама, по числам, которые сообщил
сервер; сколько окна дать на самом деле, решает сам сервер (`--fit`), наше
число — только минимум.

Не помещается — установка останавливается и называет все числа сразу (см.
«Если не получилось»). Снизить запрос: `./dev1c-setup change
model.fit_ctx=...`. Карта, занятая чем-то ещё (рабочий стол, другая модель),
отдаёт настолько меньше: `check` печатает занятую и полную память карты.

## 1.6 Четыре порта подряд и место на диске

Порты идут блоком от `[server] port` (в комплекте 3390): RDP 3390, Gitea 3391,
сервер модели 3392, SSH для туннеля 3393. Заняты — возьмите другой блок:
`./dev1c-setup change port=4000`.

Место: образ едет архивом и после `docker load` занимает в `/var/lib/docker`
примерно столько же ещё раз. Модель — отдельно, в томе. Тома лежат там же.

# Шаг 2. Довезти комплект

Копируется **целиком, одним каталогом** — программа ищет свои файлы рядом с
собой:

    scp -r dev1c-kit-linux <логин>@<сервер>:/srv/dev1c-kit

Флешкой — так же, в `/srv/dev1c-kit`. Дальше все команды выполняются оттуда:

    cd /srv/dev1c-kit
    chmod +x dev1c-setup            # если бит исполнения потерялся по дороге

Проверить, что довезли целиком:

    sha256sum -c checksums.txt

Каждая строка обязана кончаться на `: OK`. `dev1c.toml` в списке нет нарочно:
его правят на месте, и сумма менялась бы от каждой правки. То же самое
проверкой из комплекта: `./dev1c-setup verify`.

Хоть одна строка не `OK` — копируйте комплект заново. Обрывается чаще всего
архив образа: он на гигабайты.

# Шаг 3. Поставить NVIDIA Container Toolkit

Он **в комплекте**. Без него карту видит операционная система, но не
контейнер:

    sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker

---

# Шаг 4. Назвать модель

Загляните в каталог `model/`. Если модель там лежит — она уже названа в
`dev1c.toml`, и делать нечего:

    [model]
    file = "model/GLM-4.7-Flash-UD-Q4_K_XL.gguf"

Каталог пуст — `.gguf` приносит заказчик: файл весит гигабайты и выбирается
под карту. Положите его в комплект и впишите путь **относительно каталога
комплекта**, как выше.

Пока имя пусто, установка останавливается словами «модель не выбрана:
`[model] file` — файл в комплекте».

На установке файл копируется в том `dev1c-models`; из каталога комплекта его
потом можно убрать.

**Остальное в `dev1c.toml` менять не обязательно** — у всего есть умолчания, и
каждое поле объяснено комментарием рядом. Правки удобнее делать программой:
она проверит значение и применит только то, что разошлось:

    ./dev1c-setup change port=4000           # другой блок портов
    ./dev1c-setup change memory=12g          # предел памяти контейнера среды

# Шаг 5. Посмотреть, что будет сделано

    ./dev1c-setup status     # на машине ничего не меняет

До установки `status` показывает не «всё плохо», а список того, что ещё не
сделано, и того, что пока нельзя. **«Нельзя» означает: шаг ждёт результата
другого шага**, который `install` выполнит раньше него. На чистом сервере это
норма:

    Комплект: /srv/dev1c-kit

      image      Образ среды          не сделано
      volumes    Тома данных          не сделано
      payload    Платформа 1С и демо-база  не сделано
      model      Файл модели          не сделано
      llama.container Контейнер модели  нельзя: образ oktaplus/dev1c-llama:latest не загружен: он едет в dev1c-llama-image.tar.gz — выполните шаг «Образ среды»
      container  Контейнер среды      нельзя: сервер модели ещё не замерен (шаг llama.answers); без его чисел контейнер собирать нельзя

    Применить то, чего не хватает: dev1c-setup install

Единственное «нельзя», которое требует **вашего** действия, — про невыбранную
модель (шаг 4). Остальные снимает сам `install`.

Хотите увидеть не состояние, а план с командами и числами памяти:

    ./dev1c-setup install --dry-run

# Шаг 6. Поставить

    ./dev1c-setup install

Что он делает по порядку: грузит образы из архивов, создаёт тома, вносит
платформу 1С и демо-базу, копирует модель в том, поднимает сервер модели и
**замеряет** его, собирает контейнер среды с его числами, ждёт службы внутри и
проверяет результат.

Сколько ждать на чистом сервере: архив образа — минуты, копирование модели —
минуты, замер сервера модели — до пяти минут (модель читается с диска на
карту). Повторный запуск делает только то, чего не хватает.

Команду можно дать и одной строкой по SSH, не входя на сервер:

    ssh сервер '/srv/dev1c-kit/dev1c-setup install'

Вывод вы увидите полностью — он идёт в вашу консоль, шаг за шагом. Отличие
одно: в таком запуске программа не задаёт вопросов (ответ некому ввести, и
вопрос висел бы до утра), поэтому подтверждения берутся по умолчанию.
Исключение — удаление данных: без терминала оно не делается молча и просит
ключ `--yes`.

В конце `install` печатает адреса, которые вы раздадите разработчикам (адрес
сервера он подставляет свой):

    Среда запущена:
      Рабочие места   mstsc /v:192.168.1.10:3390  —  dev1/dev1, dev2/dev2, dev3/dev3
      Репозитории     http://192.168.1.10:3391
      Сервер модели   http://host.docker.internal:3392/v1 (GLM-4.7-Flash-UD-Q4_K_XL)
      Для 1c-connect  192.168.1.10:3393

---

# Шаг 7. Проверить

    ./dev1c-setup check

Нумерованный список фактов. `[info]` — сведение, а не провал. Форма такая:

      1. [ ok ] движок контейнеров: docker 29.8.2
      2. [ ok ] контейнер: работает
      3. [ ok ] рабочие места (RDP): порт 3390 принимает соединение
      4. [ ok ] Gitea: http://127.0.0.1:3391/ отвечает 200
      ...
     [ ok ] видеокарта: NVIDIA RTX ..., занято ... МиБ, драйвер ...
     [ ok ] модель в настройках Zed: провайдер llama.cpp, модель ...

    Проверок пройдено 17, провалено 0. Отчёт: /srv/dev1c-kit/last-check.txt

Номера строк не запоминайте: порядок фактов меняется вместе с программой. В
файле отчёта итог записан короче — «Пройдено 17, провалено 0.».

# Шаг 8. Раздать доступы

Подключение по RDP на адрес сервера и порт рабочих мест (в комплекте 3390).
Пользователи — `dev1`, `dev2`, `dev3`; **пароль совпадает с именем**. У
каждого свой рабочий стол и своя ветка в Gitea.

Что сказать людям заранее, иначе спросят вас:

- **логин и пароль спрашивает окно самого стенда, а не Windows.** Так будет
  всегда: сохранённый пароль Windows отдаёт только серверу, который сам себя
  удостоверил (NLA), а у RDP-сервера стенда такой поддержки нет. Галочка
  «Разрешить мне сохранять учётные данные» работать не будет — это не
  поломка;
- **в том окне всегда латиница**, какая бы раскладка ни стояла в Windows.
  Переключателя там нет вовсе: окно рисует сервер RDP, а не рабочий стол
  Linux. Логины и пароли — латиницей;
- **внутри сеанса раскладок две**, `us` и `ru`, переключение Alt+Shift,
  текущая видна в правом нижнем углу.

## Что человек найдёт на рабочем столе

- **1С:Предприятие (учебная)** — список баз рабочего места;
- **Репозитории (Gitea)** — браузер с репозиториями стенда;
- **Zed** — редактор с агентом в панели;
- **Чат с моделью** — веб-интерфейс сервера модели, без агента и без кода:
  проверить формулировку, перевести кусок текста, разобрать письмо. Адрес
  ярлык берёт из переменных сеанса, поэтому править в нём нечего. Ключа
  сервер не спрашивает: порт опубликован на адресе моста `docker0`, снаружи
  сервера недоступен, а встроенный интерфейс llama.cpp посылать ключ не
  умеет — с ключом чат был бы невозможен;
- **Коннектор 1С** — значок в трее: проект в git, проверки, журнал. Поднимается
  при входе сам; ярлык нужен, если из значка вышли.

Агент доступен двумя способами, и это **один и тот же агент** с одними
знаниями: панель в редакторе Zed и команда `pi` в терминале. `pi` запускают
вместо панели, а не рядом: у него терминальный вид и сессия, которая сама
сжимается, когда окно заполняется.

Чат, панель и `pi` делят одну модель и одни и те же места (слоты): их три.
Долгий разговор в чате занимает место так же, как работа агента.

# Если не получилось

Программа называет преграду и команду, которая её снимает: на сервере без
интернета спросить нас по ходу не выйдет. Что встречается:

| Сообщение | Что это значит и что сделать |
| --- | --- |
| «Docker отвечает „в доступе отказано“: пользователь не в группе docker» | `sudo usermod -aG docker $USER`, затем войти заново |
| «Служба Docker не отвечает: демон не запущен или сокет недоступен» | `sudo systemctl restart docker` |
| «Драйвер NVIDIA на сервере не отвечает (nvidia-smi молчит)» | Карту не видит сама операционная система. Из комплекта не лечится: нужен администратор сервера с драйвером под эту карту |
| «Драйвер на сервере работает, но видеокарта не видна внутри контейнера» | `sudo dpkg -i nvidia-container-toolkit/*.deb && sudo systemctl restart docker` |
| «Не найден архив платформы: …» | В комплекте нет `dev1c-1c-payload.tar.gz` — без него не будет ни платформы 1С, ни демо-базы. Комплект довезли не целиком: берите заново |
| «Не найден архив образа: …», «Не найден файл модели: …» | В сообщении назван путь, куда программа смотрела. Архив — комплект довезли не целиком; модель — `.gguf` не лежит под тем именем, что в `dev1c.toml` |
| «модель не выбрана: `[model] file` — файл в комплекте» | Шаг 4 |
| «образ oktaplus/dev1c-llama:latest не загружен…» | Сервер модели едет своим архивом, и загружает его тот же `install` — просто не дошёл до него |
| «сервер модели ещё не замерен (шаг llama.answers)…» | Сначала должен подняться сервер модели: контейнер среды получает его числа переменными |
| «сервер дал 54000 токенов на слот при нижней границе fit_ctx = 81920 (3 слота)» | Карты не хватает на такую модель с таким окном. Либо модель меньше или плотнее квантована, либо ниже граница: `./dev1c-setup change model.fit_ctx=...` |
| «порт N занят другой программой» | `./dev1c-setup change port=4000` — весь блок из четырёх портов сдвинется |

Куда смотреть:

- `setup.log` в каталоге комплекта — все команды движка и их вывод, по порядку;
- `last-check.txt` — отчёт последней проверки;
- `docker logs dev1c-llama` — сервер модели: почему не поднялся, какое окно взял;
- `docker logs dev1c` — среда: gitea, xrdp, sshd.

## Снять и удалить

    ./dev1c-setup clean --stack        # контейнеры; данные на месте

    ./dev1c-setup clean --data --yes   # НЕ только контейнеры

Второе уносит **все пять томов**: рабочие места (`home` — проекты, настройки,
скиллы, сессии агента), репозитории (`gitea`), файл модели (`models`),
платформу 1С (`platform`), демо-базу (`demo`), — и образ стенда вместе с
ними. Платформу и демо-базу потом возвращает только
`dev1c-1c-payload.tar.gz` из комплекта: убрали комплект с сервера — возвращать
будет нечем.

# Ручной путь

Этот раздел печатает сама программа при сборке комплекта: ниже — те же
команды, которые выполнил бы `./dev1c-setup install`, в том же порядке. Они
для случая, когда наш двоичный файл в контуре запускать не станут.

Перед тем как вставлять:

- выполняйте из каталога комплекта: пути в командах относительные;
- `.gguf` лежит в каталоге комплекта под тем именем, что в `dev1c.toml`; ниже
  он назван `модель.gguf`, подставьте своё;
- значения портов, имён и предела памяти взяты из `dev1c.toml` того комплекта,
  с которым приехала эта страница; поправили `dev1c.toml` — правьте и команды;
- **ключа у сервера модели нет** — ни в комплекте, ни в командах. Порт он
  публикует на адресе моста `docker0`, то есть снаружи сервера недоступен, а
  ключ закрывал бы только тех, кто уже на нём. Взамен он отнимал бы веб-чат:
  послать ключ встроенный интерфейс llama.cpp не умеет;
- `docker rm -f …` на первой установке отвечает «No such container» — так и
  должно быть, идите дальше по списку;
- `-p <адрес>:3392:8080` — адрес моста `docker0` этой машины; в командах стоит
  тот, что был на машине сборки комплекта. Свой: `docker network inspect
  bridge -f '{{(index .IPAM.Config 0).Gateway}}'`. По этому же адресу сервер
  модели потом отвечает;
- **`--memory`, `--memory-swap` и `--memory-reservation` несут заглушки**
  `<ПРЕДЕЛ>m`, `<ПРЕДЕЛ×2>m`, `<ПРЕДЕЛ÷2>m` — единственные числа, которые
  нельзя оставить как есть. Предел считается от памяти сервера, а комплект
  собран на другой машине; вставленная заглушка остановит `docker` с ошибкой —
  так и задумано. Свой считается так: `<ПРЕДЕЛ>` = вся память сервера − предел
  контейнера среды (`[server] memory`) − 2 ГБ хосту. Для 32 ГБ и `memory =
  "8g"` это 22528 МиБ, `--memory-swap 45056m`, `--memory-reservation 11264m`.
  Без предела кэш подсказок выдавит в подкачку всю машину, включая 1С. Если в
  `[model] memory` предел уже вписан (в комплекте там пусто), заглушек нет:
  стоит ваше число;
- `--cache-ram` и `--fit-target` — числа, посчитанные на машине сборки
  (половина предела контейнера модели под кэш подсказок; запас на карте под
  чужую нагрузку). Работать будет и так; под ваш сервер их считает `install`;
- **последняя команда неполна** — см. раздел сразу после списка.

## Шаг, который нельзя вставить: числа модели

Сколько модель получит контекста, решает не комплект, а карта: сервер модели
подбирает окно сам, под то, что на карте свободно. Поэтому последний шаг
нельзя приготовить заранее.

Поднимите сервер модели (команда выше) и спросите его. Ключ не нужен — сервер
его не спрашивает. Адрес и порт — те самые, что стоят в `-p <адрес>:3392:8080`:
на петле (`127.0.0.1`) он не отвечает, порт опубликован на адресе моста
`docker0`.

    curl -s http://<адрес из -p>:3392/props

В ответе `default_generation_settings.n_ctx` — контекст **одного слота** в
токенах, который карта дала на самом деле. Делить его на слоты не надо.

Проверьте, хватает ли окна агенту:

    окно агента = n_ctx ÷ agents     (`agents` из dev1c.toml, в комплекте 1)

Оно обязано быть не меньше **81920** токенов: 49152 на вход и 32768 на ответ.

- ответ такой большой потому, что модель размышляет, а размышления расходуют
  выходные токены: при скупом пределе ответ приходит пустым;
- вход такой большой потому, что 32 000 токенов агент занимает ещё до первого
  вопроса — правила, описания скиллов и схемы инструментов (Zed показывает это
  число в диалоге); остальное уходит на сам код: модуль в 100 КБ — это около
  40 000 токенов.

Слот принадлежит человеку, и несколько агентов одного человека делят его слот
— поэтому делится именно так. При `agents = 1` (комплект уезжает так) окно
агента равно контексту слота.

Вышло меньше `fit_ctx` из `dev1c.toml` — модель на этой карте с таким окном не
помещается, и дальше идти незачем: этим же отказом останавливается `install`.

Программа печатает вышедшее строкой:

    [ ok ] сервер отвечает: <имя>, 3 слота по 250000 токенов; на агента 250000

## Чем дописать последнюю команду

К `docker run` контейнера среды добавляются **три** переменные — адрес сервера
модели и имя модели. В командах выше их нет потому, что до замера их никто не
знает. Без них среда поднимется и редактор будет работать, а агент промолчит:

    -e MODEL_PROVIDER=llama.cpp \
    -e LLAMA_API_URL=http://host.docker.internal:3392 \
    -e MODEL_NAME=<имя модели: --alias из команды сервера модели>

Адрес здесь — **корень** сервера, без `/v1`: провайдер сам ходит в `/props` и
`/v1/models`. Ключа нет — его нет и у сервера.

Если модель берётся с **чужого** OpenAI-совместимого сервера (не llama.cpp),
штатный провайдер Zed его не понимает, и переменные другие — там же
объявляются числа окна, потому что взять их с такого сервера нельзя:

    -e MODEL_PROVIDER=custom \
    -e CUSTOM_API_URL=https://<адрес>/v1 \
    -e CUSTOM_API_KEY=<ключ> \
    -e MODEL_NAME=<имя модели> \
    -e CUSTOM_MAX_TOKENS=<вход> \
    -e CUSTOM_MAX_OUTPUT_TOKENS=<ответ>

Внутри контейнера эти переменные подставляются в настройки редактора. Среда
уже собрана без них — пересоберите контейнер той же командой с добавленными
`-e`: тома, а с ними репозитории и проекты, остаются на месте.

Проверить вышедшее можно и чужими руками: `./dev1c-setup check` смотрит на те
же факты — отвечает ли сервер модели, подставлены ли провайдер и модель в
настройки редактора, хватает ли окна агенту.

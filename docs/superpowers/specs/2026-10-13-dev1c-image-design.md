# Образ среды разработки 1С: Zed + агент + MCP

Дата: 2026-10-13
Статус: черновик на ревью

## Цель

Docker-образ с графическим окружением, куда 1С-разработчик заходит по RDP и
получает готовую среду: Zed с настроенным агентом, скиллами и MCP-серверами для
работы с кодом 1С.

Платформа 1С **в образ не входит**. Исходники приезжают выгрузкой, а операции с
живой платформой агент выполняет по SSH.

## Что уже доказано спайком

Проверено работой, переделывать не нужно:

- Zed работает в xrdp-сессии на софтовом Vulkan (lavapipe), GPU не требуется.
  Отзывчивость по RDP признана приемлемой.
- Русская локаль, раскладка `us,ru` (Alt+Shift), ярлыки в меню и на рабочем столе.
- Debian 13, glibc 2.41 — все зависимости Zed удовлетворены.

Обойденные грабли (ломали результат молча):

1. `ENV` из Dockerfile не доходит до RDP-сессии — PAM сбрасывает окружение.
   Переменные пишем в `/etc/environment`.
2. `debian:*-slim` вырезает `/usr/share/locale` при установке каждого пакета.
   `path-include` нужен **до** `apt install`.
3. `xorgxrdp` берёт раскладку от RDP-клиента и перетирает системную — настройка
   должна быть в `.xsession`.
4. Zed кладёт `.desktop` и иконки в `/opt`, вне XDG-путей.

## Граница системы

Решающий фактор — нужна ли компоненту живая платформа 1С.

### Внутри образа

| Компонент | Чем обоснован |
|---|---|
| Zed + агент | редактор и рабочее место |
| BSL Language Server (Java) | статический анализ, платформа не нужна |
| Скиллы: superpowers + отобранные 1С | инструкции агенту, обычные файлы |
| SSH-клиент и ключ | транспорт до `vrunner-mcp` и платформы |

### Снаружи

| Компонент | Почему не внутри |
|---|---|
| Платформа 1С (Конфигуратор, сервер) | лицензия у заказчика, вес, GUI-установка |
| vanessa-runner + `vrunner-mcp` | вызывают бинарники платформы локально |
| `1c-dev` MCP (`/InfoBase/hs/mcp-1c`) | HTTP-сервис **опубликованной базы** |
| `v8std` | внешний сервис |
| llama.cpp | занимает GPU, отдельный жизненный цикл |

**Критично:** конфиги на хосте ссылаются на `localhost` и `C:/...`. Внутри
контейнера `localhost` — это сам контейнер. Все такие адреса переписываются на
`host.docker.internal`, пути — на точки монтирования. Иначе MCP отваливаются без
внятной ошибки.

## Доступ к платформе по SSH

Выбранная схема: агент не держит платформу внутри, а выполняет пакетные операции
(`ДесигнерКомандаПакетногоРежима`: выгрузка/загрузка конфигурации, обновление БД,
синтаксический контроль) на машине с платформой через SSH.

Следствие: **скиллы 1С-кита написаны под локальный Windows-вызов `1cv8.exe` с
путями `C:\`.** При работе по SSH каждый такой скилл требует переписывания. Это
главный аргумент за ревизию скиллов вместо переноса всех подряд.

### Файлы — через проброшенные диски, команды — через SSH

Проброс дисков с Windows по RDP (канал `rdpdr`, монтирование через FUSE в
`~/thinclient_drives`) меняет распределение ролей и заметно упрощает схему.

| Что | Как | Почему |
|---|---|---|
| Выгрузка, `.cf`, `.cfe`, логи | смонтированный диск | файлы видны напрямую, без копирования |
| Запуск `vrunner`, Конфигуратора | SSH-команда | `1cv8.exe` — Windows-бинарь, из Linux его не выполнить |

Изначально предполагалось гонять выгрузку по SSH — на ЕРП это сотни тысяч
файлов. Теперь по SSH передаётся только строка команды.

**Ограничение, которое надо помнить:** проброшенные диски существуют **только
внутри RDP-сессии**. Закрыл подключение — монтирование исчезло. Для работы
человека это нормально, для фоновой работы агента и для CI — нет, там нужен
постоянный канал.

Что требуется для работы FUSE в контейнере (всё три пункта обязательны):
`/dev/fuse` в `devices` (Docker не отдаёт его по умолчанию),
`apparmor:unconfined` и `user_allow_other` в `/etc/fuse.conf`.

### Транспорт: vrunner-mcp через SSH

`vanessa-runner` собственного SSH-транспорта не имеет — он вызывает бинарники
платформы локально. Поэтому vrunner живёт **на машине с платформой**, не в
образе.

Но у vrunner 3.0 есть MCP-сервер `vrunner-mcp`, и работает он **по stdio**. Stdio
прозрачно прокидывается через SSH, что даёт готовое решение без самописных
обёрток:

```json
"context_servers": {
  "vrunner": { "command": "ssh", "args": ["1c-host", "vrunner-mcp"] }
}
```

Модель получает штатные инструменты vrunner — сборка и разборка конфигураций и
расширений, загрузка в базу, запуск тестов (Vanessa-ADD, YAxUnit), синтаксический
контроль — как обычные MCP-инструменты, без платформы в образе.

Требования со стороны платформы: установленные OneScript 2.0+, vanessa-runner и
сама платформа; `vrunner-mcp` в `PATH`. Рабочий каталог сервера — корень проекта,
оттуда читается `autumn-properties.json`.

### OneScript сам по себе

Важно не путать: **OneScript — самостоятельный интерпретатор и платформа 1С ему
не нужна.** Без платформы бесполезен именно vanessa-runner, потому что все его
команды (`Cf`, `Cfe`, `Infobase`, `Cluster`, `Repo`, `Epf`, `Validate`) — обёртки
над `1cv8`, `ibcmd`, `rac` или EDT.

Поэтому OneScript в образе имеет смысл ровно настолько, насколько в работе есть
`.os`-код, не трогающий платформу: утилиты, обработка выгруженных XML,
вспомогательные скрипты проекта, библиотеки `opm`.

Решение: **пока не ставим** — конкретной задачи нет. Добавление стоит одной
строки в Dockerfile, если такая задача появится.

Это снимает необходимость переписывать под SSH скиллы, которые дублируют команды
vrunner: вместо скилла с ручным вызовом `1cv8.exe` агент зовёт инструмент.

## Скиллы

Формат `SKILL.md` у Zed и Claude Code совместим — технически перенос есть
копирование. Но переносим не всё.

- Глобально: `~/.agents/skills/` (действует на все проекты)
- Вложенность **не поддерживается** — всё плоско, прямыми потомками

**Ревизия обязательна.** 15 superpowers + 55 из 1С-кита = 70 скиллов плоским
списком. Это не только риск коллизий имён (`code-review`, `testing-patterns`
есть в обоих наборах), но и перегрузка каталога, из которого агент выбирает:
чем длиннее список, тем хуже выбор, особенно у модели среднего размера.

Порядок работы:

1. superpowers обновить до актуальной версии, взять как основу процесса
2. 1С-кит отсмотреть поштучно: что реально нужно под SSH-схему и ЕРП, что
   дублирует superpowers, что мертво без локальной платформы
3. При конфликте имён приоритет у superpowers, 1С-скилл получает префикс `1c-`

## LSP для человека: расширение `bsl`

В реестре Zed есть расширение `bsl` («Bsl (1C) support», ~35k загрузок). Оно даёт
грамматику tree-sitter и подключает language server штатно, без ручного конфига.

Его language server — **`bsl-analyzer`** (Rust), тянется из релизов
`itrous/bsl-analyzer`. Linux-сборка в релизах есть (`bsl-analyzer-linux-amd64`),
собирать из исходников не нужно; версия с `D:\1c` под Windows значения не имеет.

Это закрывает вопрос «мост или анализатор»: они не конкуренты. Анализатор —
LSP для разработчика в редакторе, мост — доступ модели к возможностям LSP.

## MCP

**`mcp-bsl-lsp-bridge` не нужен, Java тоже.** Проверено работой: `bsl-analyzer`
0.3.2 — один бинарь на Rust, который умеет и `lsp`, и `mcp serve`. Мост как
отдельный компонент, его сборка, BSL LS на Java и её `-Xmx6g` уходят из проекта
целиком. Для ЕРП это самая крупная экономия памяти из возможных.

Реализовано и проверено (этап 1):

```jsonc
"context_servers": {
  "bsl-reference": {
    "source": "custom",
    "command": "/opt/bsl-analyzer/bsl-analyzer",
    "args": ["mcp", "serve", "--profile", "reference"]
  }
}
```

Грабли, каждая из которых давала молчаливый отказ:

1. **`--profile` обязателен.** Без него сервер не стартует, а Zed отваливается по
   таймауту `initialize` через 60 секунд: `context server failed to start`.
   Значения — `reference` (справочник платформы, проект не нужен) и `workspace`
   (требует `--source-dir`, поэтому его прописывает конфигуратор).
2. **Asset `bsl-analyzer-linux-amd64` — это загрузчик**, а не LSP: при запуске он
   идёт на сервер обновлений. В закрытом контуре бесполезен. Нужен
   `bsl-analyzer-app-linux-amd64` — само приложение (76 МБ).

3. **`BSL_CACHE_DIR` задавать не нужно, а вредно.** Порядок у анализатора такой:
   ключ CLI, затем переменная, затем штатный кеш системы — а штатный это
   `~/.cache/bsl-analyzer`, то есть уже свой у каждого рабочего места. Прописанный
   абсолютный путь оказывается общим на всех, создать его некому (`/home`
   принадлежит root), и анализатор молча откатывается на штатный кеш: настройка
   выглядит работающей, не делая ничего. Каталог переживает перезапуск вместе с
   томом `/home`.

Полезное на будущее: `--mode broker` держит один тёплый backend на несколько
клиентов вместо тяжёлого процесса на каждого — это способ не плодить по
экземпляру анализатора на каждое рабочее место.

Критерий включения любого MCP — **пользуется ли им модель**. Сервер, к которому
агент не обращается, это мёртвый вес и лишние строки в каталоге инструментов.
Проверяется замером на целевой модели, а не наличием в конфиге.

## Офлайн-сборка (закрытый контур)

Расширение `bsl` при установке скачивает грамматику с GitHub, а при первом
запуске — бинарь `bsl-analyzer` оттуда же. В закрытом контуре заказчика оба
запроса не пройдут, и LSP молча не поднимется.

Поэтому всё сетевое вмораживается **на этапе сборки образа**, пока интернет есть:
расширение, грамматика, бинарь анализатора. Путь к бинарю задаётся явно через
`lsp.bsl-analyzer.binary.path` в настройках — расширение читает `LspSettings` и
при заданном пути не ходит в сеть.

Проверка: образ должен поднимать LSP с отключённой сетью.

## Преднастроенный конфиг Zed

Образ поставляется с готовым `settings.json` (`config/zed-settings.json`).
Принцип: из коробки Zed не делает ни одного сетевого запроса, кроме обращения к
выбранной модели.

По умолчанию Zed смотрит наружу сразу в нескольких местах — проверено по
`assets/settings/default.json` апстрима:

| Ключ | Дефолт | Ставим | Что делает |
|---|---|---|---|
| `telemetry.diagnostics` | `true` | `false` | отчёты о падениях |
| `telemetry.metrics` | `true` | `false` | метрики использования |
| `auto_update` | `true` | `false` | проверка обновлений Zed |
| `suggest_extensions` | `true` | `false` | обращение к реестру расширений |
| `edit_predictions.provider` | Zeta | `none` | запрос в облако на нажатия клавиш |
| `auto_install_extensions` | — | `{}` | расширения вморожены при сборке |

`disable_ai` **не** ставим: агент — смысл образа.

Расхождения, найденные при разборе расширения:

- Язык называется `Bsl`, а не `BSL` — конфиг с `D:\1c` использовал другой LSP и
  сюда не переносится как есть.
- `path_suffixes` расширения = `["bsl"]`. Файлы OneScript (`.os`) под LSP не
  попадают. Если работа с `.os` нужна, требуется отдельное решение.

## Масштаб: ЕРП

В проде — конфигурация ЕРП, на хосте сейчас Бухгалтерия. Это разные весовые
категории, и проверка на Бухгалтерии не докажет работоспособность на ЕРП.

Последствия:

- Выгрузка ЕРП в XML — сотни тысяч файлов. Первичная индексация BSL LS займёт
  существенное время и память: `-Xmx6g` из докер-отчёта моста — нижняя граница.
- Индекс держать на именованном томе, иначе он пересобирается при каждом старте
  контейнера.
- Нагрузочную проверку делать на ЕРП, а не на Бухгалтерии.

## Модель

Zed имеет штатный провайдер `llama.cpp`, обходные пути не нужны.

- **Прод:** llama.cpp рядом с образом, Qwen3.8-27B (4-бит), карта 5090.
  `"language_models": {"llama.cpp": {"api_url": "http://host.docker.internal:8080"}}`
- **Тесты сейчас:** внутренний сервер модели (`Qwen3.6-35B-A3B-AWQ`) через
  `openai_compatible`. Путь у него нестандартный — `/api/v1/threads` плюс
  `/chat/completions`, который Zed достраивает сам. Адрес задаётся переменной
  `OKTAPLUS_API_URL` при запуске и в репозитории не хранится.
- **Локально:** 3060 8 ГБ — хватит на проверку связности, не на рабочую модель.

**Ключ в образ не попадает.** Сначала он зашивался сборочным аргументом — так
было удобнее, но ключ оставался в слоях образа и в `docker history`, а поставку
приходилось собирать отдельной командой и помнить об этом. Теперь и ключ, и
адрес сервера передаются переменными окружения при запуске, а `entrypoint`
переносит их в `/etc/environment`, откуда их видит RDP-сессия. Любая сборка
чиста по определению. В проде работает llama.cpp, где ключа нет вовсе.

Два следствия, которые из этого обязаны соблюдаться:

- Ключ передаётся через `ARG`, по умолчанию пустой. Прод-сборка собирается тем
  же Dockerfile без аргумента и ключа не содержит.
- Отладочный образ с ключом — секрет. Не выкладывать в реестр, не передавать
  заказчику. Заказчику уходит сборка без ключа.

## Доверие воркспейса

Zed Restricted Mode блокирует language servers, проектные MCP-серверы и
проектные скиллы. Недоверенный воркспейс = внешне рабочий Zed без единой
функции, ради которой строится образ.

Проверено на практике, чем это выглядит: язык определяется, подсветка работает
(она от грамматики), а в логе `Worktree ... is not trusted` и **LSP не
запускается вовсе**. Со стороны — «подсказки почему-то не работают».

Решение — одна настройка, **внутри секции `session`**:

```jsonc
"session": { "trust_all_worktrees": true }
```

На верхнем уровне ключ игнорируется молча — на это легко потратить час.

Это осознанное ослабление: механизм защищает от враждебного
`.zed/settings.json` в чужом репозитории. В нашем случае среда контролируемая,
проекты — собственные выгрузки заказчика, а модальное окно про доверие для
1С-ника — гарантированный способ получить нерабочую среду.

Глобальные `context_servers` стартуют независимо от доверия — проверено, MCP
поднимался и до включения настройки.

## Конфигураторы

Это **не установщики**. Установщик отрабатывает один раз при развёртывании;
здесь же нужен инструмент, который живёт с системой и запускается каждый раз,
когда что-то поменялось: переехала машина с 1С, сменился порт, обновилась версия
платформы, поднялась другая модель.

Ключевое свойство — **идемпотентность**: повторный запуск с теми же значениями
ничего не ломает, с новыми — переписывает всё, что затронуто.

Вторая задача, помимо первичной настройки: собрать в одном месте параметры,
которые сейчас разбросаны по шести файлам в трёх форматах. Сегодня смена адреса
хоста означает ручную правку `~/.ssh/config`, `known_hosts`, `settings.json`
Zed и `autumn-properties.json` на той стороне — и любой пропущенный файл даёт
отказ без внятной диагностики.

### Единый источник правды

Из этого следует архитектура: конфигуратор не редактирует целевые файлы как
таковые. Он владеет **одним файлом параметров** и раскладывает значения по
местам назначения.

```
dev1c.toml  ──(применение)──>  ~/.ssh/config
(источник правды)              ~/.ssh/known_hosts
                               ~/.config/zed/settings.json
                               <проект>/.zed/settings.json
                               autumn-properties.json (на стороне платформы)
```

Целевые файлы становятся производными. Правится только источник, остальное
генерируется — это и есть «поменял в одном месте, исправилось везде».

Следствие, которое надо принять осознанно: конфигуратор перезаписывает участки
целевых файлов. Ручные правки в них будут затёрты, поэтому генерируемые секции
помечаются явным маркером, а всё за его пределами сохраняется.

### Инвентарь параметров

| Параметр | Куда приземляется | Что ломается при рассинхроне |
|---|---|---|
| Адрес и порт машины с 1С | `~/.ssh/config`, `context_servers.vrunner.args` | MCP не стартует, агент без инструментов платформы |
| Отпечаток хоста | `~/.ssh/known_hosts` | SSH виснет на запросе подтверждения, MCP молча не поднимается |
| Пользователь и ключ SSH | `~/.ssh/config`, `~/.ssh/id_*`, `authorized_keys` на хосте | отказ в доступе |
| Версия платформы 1С | `autumn-properties.json` (`v8version`) | vrunner падает с невнятной ошибкой |
| Строка подключения ИБ | `autumn-properties.json` (`ibconnection`) | команды работают не с той базой |
| Учётные данные ИБ | `autumn-properties.json` | отказ аутентификации |
| Адрес LLM | `language_models.llama.cpp.api_url` либо `openai_compatible.*.api_url` | агент не отвечает |
| Модель и провайдер | `agent.default_model` | агент работает не на той модели |
| API-ключ | тот же раздел `settings.json` | отказ авторизации |
| Путь к `bsl-analyzer` | `lsp.bsl-analyzer.binary.path` | нет подсветки, навигации и диагностики |
| Корень проекта | точка монтирования, рабочий каталог `vrunner-mcp`, доверие воркспейса | инструменты смотрят не туда |
| Доверенные воркспейсы | состояние доверия Zed | Restricted Mode глушит LSP, MCP и скиллы разом |

Отдельно: **корень проекта упоминается в четырёх местах**, а версия платформы и
адрес хоста — в двух каждый, причём по разные стороны SSH. Это главные
кандидаты на рассинхрон, и ровно ради них инструмент и затевается.

### Проверка после применения

Конфигуратор не ограничивается записью файлов — он проверяет результат и говорит
человеческим языком, что именно не так:

- SSH до хоста и наличие `vrunner-mcp` в `PATH`
- Ответ LLM на пробный запрос
- Запуск `bsl-analyzer` по указанному пути
- Доверие воркспейса выдано

Без этого пользователь получает «не работает» вместо «не отвечает модель по
адресу X».

### Интерфейс вместо инструкции

Требование: **конфигуратор сам себе документация**. Никакого отдельного
руководства, которое всё равно никто не откроет, а если откроет — оно будет
устаревшим. Всё, что нужно знать, человек видит там, где принимает решение.

Что это значит практически.

**Каждое поле объясняет себя:** что это, откуда взять значение, пример, что
будет, если оставить пустым. Не подпись в три слова, а короткий связный текст.

> ❌ `Хост: [____]`
>
> ✅ **Адрес машины с 1С**
> Имя компьютера в сети или IP-адрес машины, где установлена платформа
> 1С:Предприятие. Например, `192.168.1.50` или `1c-server.company.local`.
> Если 1С установлена на этом же компьютере — оставьте поле пустым.

**Ошибка говорит, что делать,** а не что случилось:

> ❌ `Connection refused (os error 111)`
>
> ✅ **Не удалось подключиться к `192.168.1.50:22`**
> Похоже, на машине с 1С не запущен SSH-сервер. Запустите этот же конфигуратор
> там и выберите режим «Машина с 1С» — он всё настроит.

**Язык предметной области, а не инфраструктуры.** Пользователь — 1С-разработчик.
Он знает, что такое конфигуратор, выгрузка и информационная база; он не обязан
знать, что такое MCP, LSP и воркспейс. Где термина не избежать — одна поясняющая
фраза рядом.

**Видимое состояние.** Главный экран показывает, что настроено и что нет, с
результатом последней проверки по каждому пункту. Это снимает вопрос «а оно
вообще работает» без обращения к кому-либо.

**Подсказки откуда брать значения.** Там, где параметр нужно где-то посмотреть,
конфигуратор говорит где: версию платформы — в списке установленных программ или
в каталоге `C:\Program Files\1cv8`, строку подключения — в свойствах базы в
списке баз 1С.

**Два режима отображения** под два сценария:

- первый запуск — мастер по шагам, каждый с объяснением, что произойдёт дальше;
- последующие — один экран со всеми параметрами, чтобы поправить адрес и нажать
  «Применить», не проходя мастер заново.

Критерий приёмки: 1С-разработчик, впервые увидевший эту среду, настраивает её от
начала до конца, ни разу ничего не спросив и не открыв никакой документации.

### Два сценария развёртывания

| Сценарий | Где платформа | Транспорт |
|---|---|---|
| Раздельный (основной) | на хосте, Windows или Linux | SSH до `vrunner-mcp` |
| Объединённый | внутри образа, если решат ставить | локально, SSH не нужен |

Установщик обязан поддерживать оба, иначе объединённый сценарий потребует
отдельной ветки кода и разойдётся с основной.

### Технология: Rust + Tauri

Стек команды — Rust и Tauri, на нём пишется всё последние полгода. Это решающий
аргумент: наработки, привычный стиль и скорость разработки перевешивают
теоретическую экономию на более лёгком стеке, которого никто не знает.

Интерфейс на HTML/CSS даёт нужную «красивую графику» без возни с тулкитами,
кроссплатформенность — пересборкой под Windows и Linux.

#### Риск WebKitGTK — ЗАКРЫТ, с оговоркой

**Проверено в реальной xrdp-сессии: страница рендерится.** WebKitGTK в образе
живой, Tauri применим, запасной путь не нужен.

Оговорка: в логе всё равно присутствует `Сбой веб-процесса`, хотя содержимое
отрисовано. Стабильность под длительной работой не проверялась — это стоит
погонять на реальном мастере до релиза.

Прочий шум в логе — отсутствующие в контейнере сервисы: шина доступности
(лечится `GTK_A11Y=none`, уже в образе), хранилище секретов
(`org.freedesktop.secrets`) и `xdg-desktop-portal`. Последние два всплывут и у
Tauri, если он будет хранить секреты или открывать системные диалоги файлов —
тогда понадобится `gnome-keyring` и `xdg-desktop-portal-gtk`.

#### История вопроса (почему проверка в Xvfb обманула)

Tauri на Linux рендерит через WebKitGTK. Проверка в контейнере (Xvfb, софтовый
рендер) дала **циклический сбой веб-процесса**:

```
epiphany-WARNING: Сбой веб-процесса
MESA: error: Failed to attach to x11 shm
```

Окно создаётся, содержимое не рисуется. `WEBKIT_DISABLE_COMPOSITING_MODE=1`,
`WEBKIT_DISABLE_DMABUF_RENDERER=1` и `LIBGL_ALWAYS_SOFTWARE=1` не помогли.

Этот результат оказался ложным: тест шёл в **Xvfb**, а не в xrdp-сессии, а
`xorgxrdp` обрабатывает MIT-SHM иначе. Для Zed разница несущественна, для
WebKitGTK — решающая. Вывод на будущее: **проверять GUI в настоящей
RDP-сессии, Xvfb годится не для всего.**

В образе нужен браузер и так — Firefox ESR для веб-клиента 1С и публикаций,
независимо от выбора стека установщика.

### Режимы

Модель параметров общая для обеих сторон, различается только то, куда значения
приземляются. Поэтому один бинарь с тремя режимами, а не две программы:

- `host` — на машине с 1С: ставит OneScript и `vanessa-runner`, проверяет
  платформу и её версию, поднимает SSH-сервер, авторизует ключ, пишет
  `autumn-properties.json`.
- `workstation` — внутри образа: принимает код подключения, пишет `~/.ssh/config`
  и `known_hosts`, настройки Zed, выдаёт доверие воркспейсу.
- `all-in-one` — объединённый сценарий (1С в образе): обе роли сразу, без SSH.

Разделение на две кодовые базы означало бы два описания одних и тех же
параметров, которые разойдутся при первом же изменении.

### Код подключения

Чтобы не заставлять пользователя переносить ключи руками: хостовой мастер
генерирует пару ключей и показывает одну строку — адрес, порт, отпечаток и
приватный ключ в base64. Пользователь копирует её в мастер рабочего места.
Один шаг вместо инструкции на страницу.

Строка содержит приватный ключ, то есть является секретом: передаётся тем же
каналом, что и образ, и не живёт в переписке.

### Требования к хостовому режиму

- Windows: нужны права администратора (установка OpenSSH Server как службы).
  Проверять заранее и говорить об этом прямо, а не падать на середине.
- Linux: та же логика через системный пакетный менеджер.
- Проверка, что платформа 1С найдена и её версия совпадает с ожидаемой в
  `autumn-properties.json` — иначе vrunner отработает с невнятной ошибкой.

## Внешний вид

Среду должны захотеть открыть — это требование маркетинга, а не украшательство.
Но у RDP есть жёсткое ограничение, которое определяет, каким именно способом
делать «вау».

**Принцип: эффект статический, не анимированный.** Всё, что перерисовывается,
гонится по сети кадрами. Композитинг, тени, прозрачность и анимации дают
отличный скриншот и ощущение «подвисает всё» в работе. Поэтому
`use_compositing=false`, анимации выключены, а впечатление создают вещи, которые
передаются один раз: тема, иконки, обои, шрифты.

| Элемент | Выбор | Почему |
|---|---|---|
| Тема GTK и окон | Materia-light | плоская и спокойная, визуально согласована с темой Zed |
| Иконки | Numix-Circle | круглые, выбраны после примерки нескольких наборов |
| Тема Zed | macOS Classic Light / Dark | те же, что на рабочей машине |
| Шрифт интерфейса | Inter 10 | полная кириллица, читаемость мелким кеглем |
| Моноширинный | JetBrains Mono | кириллица обязательна: в коде 1С русские идентификаторы |
| Обои | генерируются при сборке | `config/make-wallpaper.sh`, ~100 КБ |
| Тема Zed | One Dark (встроенная) | светлый редактор на тёмном столе слепит |

### Разрешение и масштаб

Разрешение сессии задаёт RDP-клиент — оно заранее неизвестно и меняется от
подключения к подключению. Отсюда две отдельные задачи.

**Разрешение.** Клиент выбирает режим из списка `xorgxrdp`, а штатный список в
`/etc/X11/xrdp/xorg.conf` заканчивается на `1920x1080`. На 2K, 4K или ultrawide
сессия упёрлась бы в этот потолок. Список расширен до `3840x2160`, `3440x1440`,
`2560x1440`, `2560x1080`, `1920x1200`.

**Масштаб интерфейса.** Фиксированный DPI не годится в обе стороны: 96 на 4K
даёт нечитаемо мелкий интерфейс, крупный DPI на 1366×768 — ничего не помещается.
Физический размер экрана в xrdp-сессии недоступен (`xrandr` показывает 0mm×0mm),
посчитать DPI честно нельзя.

Решение — `/usr/local/bin/xfce-autoscale`, вызываемый из `.xsession` по ширине
сессии. Проверено на четырёх разрешениях:

| Ширина | DPI | GDK_SCALE |
|---|---|---|
| < 2400 | 96 | 1 |
| 2400–3399 | 120 | 1 |
| ≥ 3400 | 96 | 2 |

Поэтому `Xft/DPI` в `xsettings.xml` выставлен в `-1`: любое конкретное значение
там перекрыло бы автоопределение. Ручная подстройка — переменной `FORCE_DPI`.

### Бренд OktaPlus

Палитра взята из сайта (`c:/dev/OktaPlus`), а не придумана:

| Цвет | Роль |
|---|---|
| `#0E9E82` | акцент (бирюзово-изумрудный) |
| `#16191F` | тёмный фон |
| `#F4F6F9`, `#E7EBF1` | светлые поверхности |
| `#323947` | серо-синий |

Логотипы берутся из `assets/images` сайта и копируются в образ
(`/usr/share/oktaplus`): горизонтальный локап в двух вариантах (под светлый и
тёмный фон) и марка. Wordmark набран в Cabinet Grotesk.

Где используется:

- **Обои** — тёмный градиент в брендовой гамме, марка-восьмиугольник как
  крупный водяной знак (фирменная форма вместо произвольных кругов),
  диагонали акцентным цветом, локап по центру.
- **Экран входа xrdp** — логотип и брендовый цвет фона. Это первое, что видит
  человек, ещё до загрузки темы: стандартный серый диалог портит впечатление
  раньше, чем оно успеет сложиться.

Два ограничения xrdp, из-за которых сделано именно так:

- Логотип принимается **только в BMP** — конвертируется из SVG при сборке
  (`rsvg-convert` + `magick`), в репозитории лежит исходный SVG.
- Цвет текста меток не настраивается, поэтому **фон диалога оставлен светлым**:
  на тёмном подписи «Login»/«Password» стали бы нечитаемыми. Брендовый тёмный
  ушёл на фон вокруг диалога.

Темы из репозиториев Debian (Arc, Greybird, Numix, Orchis, Yaru) отвергнуты как
устаревшие по виду. Materia и Numix Circle ставятся с GitHub, причём Materia
собирается из исходников (meson + npm + sassc) — поэтому сборка вынесена в
отдельную стадию Dockerfile, а в рабочий образ копируется только результат.
Иначе инструментарий сборки осел бы в образе лишними сотнями мегабайт.

### Две ловушки с SVG

Обе выглядят как «тема кривая», а на деле это отсутствующие компоненты.

**1. GTK не рисует SVG-иконки без `librsvg2-common`.** Это загрузчик для
gdk-pixbuf, и его нет в базовом образе. Без него любой целиком-векторный набор
(Numix Circle — 12776 SVG и ни одного PNG, Papirus — то же самое) просто не
отображается, а GTK молча откатывается на низкоразрешённые PNG из `hicolor`.
Симптомы: «иконки не применились» и «крупные иконки мыльные».
Внимание: `librsvg2-bin` — это **другой** пакет, утилита `rsvg-convert` для
сборки; на отрисовку в GTK он не влияет.

**2. xfwm4 в Debian собран БЕЗ поддержки SVG** (`ldd /usr/bin/xfwm4` не
показывает librsvg). Materia поставляет кнопки заголовка только в SVG, поэтому
окна остаются **без кнопок свернуть, развернуть и закрыть** — закрыть мышью
нечем. Темы с PNG (Arc, Greybird) работают.
Решение: при сборке конвертировать кнопки Materia в PNG через `rsvg-convert`.
Вид темы сохраняется полностью.

Три неочевидных решения:

- **`button_layout` задан явно** (`O|HMC`). Набор кнопок заголовка — настройка
  xfwm4, а не темы. Без неё Materia рисует заголовок **без кнопок свернуть,
  развернуть и закрыть**: окно нечем закрыть мышью.
- **Композитор включён, но все его эффекты выключены.** Сам он дёшев —
  перерисовка только при изменениях; дороги тени, прозрачность и анимации.
  Но без композитора нечем рисовать альфа-канал, и скруглённые углы тем
  вырождаются в чёрную рамку вокруг каждого окна.
- **Настройки GTK продублированы в `gtk-3.0` и `gtk-4.0`.** XSETTINGS
  (`xfsettingsd`) управляет только GTK3; приложения на GTK4/libadwaita его не
  слушают и сами решают, быть им светлыми или тёмными — отсюда эффект
  «темы смешались». Панель XFCE имеет свой `dark-mode`, выключен отдельно.

- **Субпиксельное сглаживание выключено** (`Xft/RGBA=none`). По RDP оно даёт
  цветную бахрому на тексте: клиент пережимает картинку, и расчёт на RGB-порядок
  субпикселей перестаёт быть верным. Серое сглаживание выглядит чище.
- **Обои не хранятся в репозитории**, а описываются скриптом ImageMagick:
  правятся параметрами, не раздувают историю git, весят 100 КБ вместо 10 МБ
  (PNG того же градиента).

Сделано и проверено скриншотами: обои с логотипом, тёмная тема XFCE и Zed,
брендированный экран входа, индикатор раскладки на панели, LSP с живой
диагностикой в редакторе.

Мелочь на потом: иконка Zed без прозрачных полей — на тёмном фоне видна
квадратная подложка.

## Несколько разработчиков

Один контейнер на всех: три рабочих места (`dev1`, `dev2`, `dev3`, пароль
совпадает с логином) с собственными домашними каталогами, и общие службы —
Gitea и llama.cpp. Запуск через `docker run`, без compose: образ переносится на
podman и любой другой движок без переписывания обвязки.

Первоначально планировалось обратное — контейнер на разработчика, разделение по
имени проекта Docker. От этого пришлось отказаться по физической причине:
сервер модели занимает всю видеопамять карты, и держать его копию на каждого
негде. Раз модель всё равно общая, общими становятся и контейнер с git-сервером.

Цена решения принята осознанно: экземпляры `bsl-analyzer` делят память и ядра
без изоляции, и на конфигурации масштаба ЕРП индексация у одного будет заметна
другим. Смягчается кешем у каждого в своём домашнем каталоге (повторная
индексация не нужна) и, при необходимости, режимом `--mode broker` — один
тёплый процесс анализатора на всех вместо трёх.

Общий контейнер добавил свой класс ошибок: настройки, написанные под
единственного пользователя `dev`, продолжают выглядеть рабочими, молча не делая
ничего — абсолютные пути в `/home/dev` (кеш анализатора, закладки Thunar,
автозапуск редактора) и проверки доступности файлов, которые пользователю по
замыслу недоступны (`[ -f app.ini ]` на конфиг Gitea с правами `600 gitea:gitea`
отключал настройку `tea` целиком). Признак один и тот же: функция не работает,
но и не жалуется.

## Состояние и тома

Что обязано пережить пересборку образа:

| Том | Путь | Зачем |
|---|---|---|
| `zed-state` | `~/.local/share/zed/db` | история, открытые проекты, отметка о пройденном онбординге |
| `bsl-cache` | `~/.cache/bsl-analyzer` | индекс; на ЕРП его пересборка — десятки минут |
| `projects` | `~/proj` | рабочие файлы |

Настройки и расширения **намеренно не на томах**: ими владеет образ, они должны
обновляться вместе с ним.

Грабля: точки монтирования обязаны существовать в образе с владельцем `dev`.
Иначе docker создаёт их от root, и Zed падает с `permission denied when
creating directory` ещё до появления окна.

## Раскладка Zed: Classic

Онбординг Zed предлагает выбрать между «Agentic» и «Classic». Это не одна
настройка, а набор дефолтов для доков — в `default.json` такого ключа нет:

| Панель | Agentic (умолчание) | Classic |
|---|---|---|
| `project_panel` | справа | слева |
| `outline_panel` | справа | слева |
| `agent` | слева | справа |

Выбран **Classic**: дерево объектов слева привычно всем, кто пришёл из любой
другой IDE, включая Конфигуратор и EDT. Задаётся тремя ключами `dock` в
`settings.json` — тогда выбор не зависит от того, что человек нажмёт в
онбординге.

## Командная строка

В образе, помимо редактора, нужен рабочий терминал — иначе среда полуфабрикат:

- `git`, `git-lfs` — без git Zed не показывает статус файлов и историю, а
  выгрузка конфигурации живёт именно в git
- `ripgrep`, `fd-find` — на выгрузке ЕРП (сотни тысяч файлов) обычный `grep`
  неприемлемо медленный; ripgrep использует и человек, и агент
- `libxml2-utils`, `xmlstarlet` — XML основной формат исходников 1С
- `unzip`, `zip`, `p7zip` — `.cf` и `.cfe` по сути zip-архивы
- `iputils-ping`, `dnsutils`, `netcat` — без них непонятно, почему не идёт SSH
  до платформы
- `less`, `nano`, `vim-tiny`, `tree`, `jq`, `rsync`, `htop`, `mc`
- `sudo` без пароля: контур закрытый, вход уже под паролем RDP, а упереться на
  демонстрации в невозможность доустановить пакет хуже этого риска

Настройки git заданы системно: `safe.directory '*'` (иначе «dubious ownership»
на каталогах с томов, где uid не совпадает), `core.autocrlf input` (выгрузка
приходит с Windows, в репозитории держим LF), `core.quotepath false` (иначе
русские имена файлов показываются escape-последовательностями).

## Хранилище секретов

В контейнере нет `org.freedesktop.secrets`, и это не косметика, как казалось по
логам. Без него Zed не может завершить онбординг: страница приветствия
открывается, кнопка «Finish setup» молча не срабатывает, и так при каждом
запуске.

Решение: `gnome-keyring`, разблокируемый пустым паролем из `.xsession`. Второй
пароль ничего не защищает — вход в среду и так под паролем RDP.

Это же убирает ошибки загрузки учётных данных сторонних провайдеров
(`x_ai_subscribed`, `openai_subscribed`, Amazon Bedrock), которые Zed пытается
читать при старте.

## Размер образа и доставка

Образ передаётся файлом, не через реестр, поэтому размер — это время и канал
доставки каждому разработчику, а не абстракция.

Где он на сегодня, после чистки и пересборки llama.cpp:

| | распакованный | файл поставки |
|---|---|---|
| было, с готовым релизом llama.cpp | 3,39 ГБ | 1673 МБ |
| стало | — | **1328 МБ** |

Что убрано и почему:

- **Docker CLI с плагинами (153 МБ)** — стоял ради сокета демона хоста, но сокет
  внутрь больше не отдаётся: доступ к нему равносилен root на хосте, а
  пользовались им только несбывшиеся планы. Ни один скилл и ни одна служба к
  docker не обращаются.
- **`epiphany-browser` и его WebKit (~160 МБ)** — проба движка Tauri в
  xrdp-сессии своё дело сделала. Веб-клиент 1С работает в Firefox, который и
  остаётся.
- **Numix Circle (23 МБ)** — набор иконок клонировался при каждой сборке и ни
  разу не применялся: в настройках стоит Papirus.
- **`xvfb`, `imagemagick`, `librsvg2-bin`** — диагностика и генераторы картинок.
  Обои и логотип экрана входа теперь копируются готовыми файлами: картинка в
  каждой сборке получалась одна и та же, а ради неё в образе жили два пакета.
- **llama.cpp: 1,1 ГБ → 630 МБ** — см. ниже.

Что осталось и остаётся сознательно:

- `firefox-esr` (294 МБ) — веб-клиент 1С официально поддерживает Firefox;
- `papirus-icon-theme` (253 МБ) — из них 216 МБ базовый набор, который даёт 1665
  иконок типов файлов. В дереве выгрузки 1С на это смотрят целый день;
- компилятор C (`cpp-14`, 34 МБ) — удалить нельзя: `xrdb` из `x11-xserver-utils`
  использует препроцессор C, а это жёсткая зависимость сессии XFCE.

## llama.cpp: своя сборка вместо релиза

Официальный релиз несёт ядра под все поколения карт и полный cuBLAS — 1,1 ГБ,
из которых среда использует малую часть. Сборка под нужные архитектуры (86 для
Ampere, 120 для 5090, 75-virtual как PTX-запас) даёт **630 МБ**.

Главное здесь не выбор архитектур сам по себе. Первая попытка — пересборка с
`CMAKE_CUDA_ARCHITECTURES` — сэкономила всего 86 МБ, потому что три четверти
веса это cuBLAS, который приезжает готовой разделяемой библиотекой. **Готовую
`.so` обрезать нечем:** `nvprune` отвечает `not relocatable`, он работает только
с объектными файлами и статическими архивами.

Поэтому связка такая:

1. статические архивы `libcublas_static.a` и `libcublasLt_static.a` режутся
   `nvprune` под две архитектуры (1040 → 793 МБ для cublasLt);
2. ggml линкуется с ними статически — а статический архив линкуется по объектам,
   то есть в результат попадает только то, что реально используется.

Статическая линковка включается точечным патчем одной строки в
`ggml/src/ggml-cuda/CMakeLists.txt`. Штатный путь — `GGML_STATIC=ON` — не
годится: он линкует статически всё, а ggml собирает разделяемые библиотеки, и
линковщик отказывается с `failed to set dynamic section sizes`.

Сборка живёт отдельно: `Dockerfile.llama` → образ
`ghcr.io/<owner>/dev1c-llama:<версия>`, который основной Dockerfile копирует.
Причина простая: компиляция занимает около сорока минут и нужна только при смене
версии llama.cpp или набора карт, тогда как сам образ правится по несколько раз
в день. С компиляцией внутри основной сборки каждая правка комментария стоила бы
сорока минут.

Две грабли, обе стоили по сборке:

- стадию сборки пришлось перенести на Debian 12: apt в trixie с февраля 2026 не
  принимает подписи SHA1, а ключ репозитория NVIDIA подписан именно так;
- библиотеки нельзя перечислять по именам. Перечисление `libggml*` и `libllama*`
  оставило без внимания `libmtmd`, и сервер не запускался вовсе — при внешне
  исправном образе. Теперь копируется всё, что собралось, а сборка завершается
  запуском `llama-server --version`.

## Сборка в CI

Образ собирается в GitHub Actions, а не на рабочей машине: сборке нужно около
4 ГБ памяти и 10 ГБ диска, и дважды она падала здесь по памяти прямо на
экспорте слоёв. Контекст сборки — 2,4 МБ, всё остальное качается.

Проверки идут там же, и это не формальность — каждая из них ловила реальный
дефект:

- службы поднимаются (`gitea`, `xrdp`, `sshd`);
- имя модели доезжает до настроек редактора — для обоих провайдеров;
- `oscript` исполняет код с кириллицей, скиллы на месте, frontmatter валиден;
- ключа нет в окружении образа.

Отдельный workflow поднимает среду и даёт подключиться к ней по RDP через
Tailscale — для того, что скриптом не проверить: интерфейс, подсветка, поведение
агента. Это сессия для осмотра собранного артефакта, с жёсткими ограничениями
(час, без GPU, ничего не сохраняется), а не рабочее место.

## Решённые вопросы

- **SSH-профиль:** один, но вынесенный в настройку, а не зашитый в образ. Адрес
  машины с платформой меняется (сейчас хост с Бухгалтерией, в проде — 5090),
  образ при этом не пересобирается.
- **superpowers на Qwen-35B:** замерено на локальном стенде — работает, качество
  ниже, чем на старших моделях, но приемлемо.
- **`bsl-analyzer`:** нужен, это штатный LSP расширения `bsl`. Linux-сборка
  готова в релизах апстрима. Берётся asset с `-app-`: без него приезжает
  загрузчик, который в закрытом контуре идёт на сервер обновлений и не работает.
- **Ключ провайдера передаётся переменной окружения.** Имя переменной диктует
  Zed: он ищет `<ИМЯ_ПРОВАЙДЕРА>_API_KEY`, поэтому провайдер назван `custom` —
  без бренда, и в `.env` ровно те имена, что уходят в контейнер. Ручного ввода в
  интерфейсе не требуется. Переменные, переданные через `-e`, в RDP-сессии не
  видны: её поднимает PAM, собирая окружение заново, поэтому `entrypoint`
  переносит их в `/etc/environment`.
- **Адрес сервера модели и имя модели — тоже переменными.** В настройках стоят
  заглушки, `entrypoint` подставляет значения и переключает провайдера по
  умолчанию. Эталон в `/etc/skel` при этом не трогается: подстановка в него
  сжигала бы заглушки на первом запуске, и среду больше нельзя было бы
  перенацелить.
- **Поддержка `.os` в редакторе нужна.** Расширение `bsl` заявляет
  `path_suffixes = ["bsl"]`, то есть файлы OneScript не привязаны ни к какому
  языку: ни подсветки, ни анализатора. Язык тот же, поэтому достаточно
  сопоставить расширение вручную через `file_types`.
- **Как пользователь получает образ.** Скрипты `dev1c.sh` и `dev1c.ps1`:
  `docker load`, запуск, печать адресов. Compose не используется — образ
  переносится на podman и любой другой движок без переписывания обвязки.
  Инструкция для заказчика генерируется в поставку (`SETUP.md`, по-русски).
- **Браузер:** Firefox ESR остаётся, WebKit-браузер убран. Веб-клиент 1С
  официально поддерживает Firefox; `epiphany` стоял ради пробы движка Tauri и
  тянул за собой около 160 МБ.

## Открытые вопросы

1. Нужна ли Java в образе. Расширение `bsl` тянет `bsl-analyzer` на Rust, но
   `mcp-bsl-lsp-bridge` построен вокруг BSL Language Server на Java. Если мост
   после обновления умеет работать с анализатором, Java и её память уходят из
   образа — а на ЕРП это существенная экономия.
2. Версия расширения `bsl` — 0.0.2. Нужно понять, что из навигации и диагностики
   в нём реально работает на конфигурации масштаба ЕРП.
3. Параметры llama.cpp подобраны для 4B на 3060 Ti: контекст 196608, один слот,
   KV в q8_0. Для прод-модели на 5090 их надо пересчитать — контекст такого
   размера там в память не влезет. Задаются переменными, пересборка не нужна.
4. Три рабочих места делят один слот llama.cpp: запросы встают в очередь, а не
   делят контекст. Это сознательный размен (ждать лучше, чем не работать), но на
   проде стоит перемерить — возможно, памяти хватит на два-три слота.
5. Описания скиллов занимают 17 КБ в каждом запросе — больше половины
   системного промпта. Сокращение до стиля superpowers (80–100 символов вместо
   360) экономит около 10 КБ, но описание — единственное, по чему модель выбирает
   скилл, поэтому резать надо аккуратно.
6. Обратный SSH-туннель до машины с платформой не проверен ни разу. Это
   единственная часть схемы, которая вообще не работала, и самая рискованная для
   пилота.
